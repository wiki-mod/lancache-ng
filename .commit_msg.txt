CLD-1788342761 fix(dockerfile): restore COPY-based curl sharing; add proxy support

Maintainer correction, relayed by the coordinator: the previous
approach (each of dhcp/dns/ntp/proxy/ui/watchdog installing curl
independently via its own apk add curl) was architecturally wrong.
Maintainer, verbatim: "GENAU DAS IST FALSCH utilities installiert das
und der rest NUTZT ES" -- only the compile-vs-package part of Issue
#1781 was ever supposed to change (services/utilities/Dockerfile no
longer self-compiles curl, installs it via apk instead), not the
dedup mechanism: every other shared binary in that same file (find,
xargs, envsubst, libintl.so.8, lsof, rg, libgcc_s.so.1,
libpcre2-8.so.0*, verify-version-banner.sh) is still COPY
--from=utilities-tools'd by these six consumers, unchanged. Breaking
only curl out of that established pattern while everything else next
to it stayed COPY'd was an inconsistent regression.

Reverted in all six: removed the standalone apk add curl line and
its dedicated verify step; restored COPY --from=utilities-tools
for curl at its original position among the other COPY lines;
restored curl --version inside the existing combined
verify-copied-binaries RUN block (not a separate step).

One real correction to the maintainer's literal quoted line (COPY
--from=utilities-tools /usr/local/bin/curl /usr/local/bin/curl):
verified live that utilities' apk-installed curl now lives at
/usr/bin/curl (Alpine's own package convention), not
/usr/local/bin/curl (only true for the old self-compiled binary) --
adjusted the COPY source/dest path accordingly, matching how every
other apk-installed tool in utilities is already copied at its own
package-manager path (/usr/bin/find, /usr/bin/rg, etc).

Also copied curl's real shared-library dependency set, which the old
static binary never needed and nothing in these Dockerfiles copied
before: libcurl.so.4, libz.so.1, libcares.so.2, libnghttp2.so.14,
libidn2.so.0, libpsl.so.5, libssl.so.3, libcrypto.so.3, libzstd.so.1,
libbrotlidec.so.1, libunistring.so.5, libbrotlicommon.so.1 -- the
exact list ldd reports against a real build of the current
utilities image. services/ntp/Dockerfile's ca-certificates comment
was also reverted to its original pre-#1781 wording (copied curl has
a fixed CA path; ca-certificates generates it), which is accurate
again now that curl is copied rather than locally apk-installed.
services/proxy/Dockerfile needed curl available before its own first
HTTPS call (the nginx signing-key fetch), so the whole COPY block
(including curl) was moved ahead of that RUN step, and curl dropped
from that step's own local apk add list.

Second maintainer-requested addition, once alongside all these files
anyway: self-hosted-runner build proxy support, so package/download
traffic routes through the LAN proxy to save bandwidth.

Package freshness (apk update/upgrade, apt-get update/dist-upgrade):
investigated first per AG-CODE-011 rather than assumed -- already
present everywhere it's relevant. Every Alpine-based Dockerfile that
installs packages (utilities, dhcp, dns, ntp, proxy, ui, watchdog,
dhcp-proxy, tools/build-tools's alpine-final stage) already runs
apk upgrade --no-cache (several carrying their own detailed,
pre-existing comment on why apk upgrade, not apk update, is the
right call on Alpine) immediately before apk add, and
tools/build-tools/Dockerfile's Debian stage already runs apt-get
update && apt-get dist-upgrade && apt-get full-upgrade. No gap
found; no code change needed for this half.

Proxy build-arg passthrough: genuinely missing everywhere except a
dead, unconsumed ARG declaration in the pre-#1781
services/utilities/Dockerfile (removed along with curl-builder
earlier in this PR). Declared ARG HTTP_PROXY/HTTPS_PROXY/
NO_PROXY (+ lowercase) in every stage that runs apk/apt/go/cargo/
curl downloads: services/utilities, all six reverted consumers'
final stage, and all four network-touching stages of
tools/build-tools/Dockerfile (go-tools-builder, go-tools-builder-
alpine, alpine-final, and the Debian rust:latest stage) -- empty by
default, no forced proxy, matching the pre-existing Issue #1637
pattern exactly.

Wired the actual proxy values in from three existing, previously
unused repository variables (vars.PROJECT_SELFHOSTED_PROXY_HTTP/
_HTTPS/_EXCLUSION) -- confirmed via grep this is the first real
consumer of them. Critical correction mid-implementation, also
relayed by the coordinator: these values are self-hosted-LAN-only and
must never reach a GitHub-hosted runner. Investigated (not assumed)
which build jobs actually run where: build-push.yml's build job
(the one that builds every service, including all six reverted
consumers) runs exclusively on ${{ fromJSON(matrix.runner) }},
always a self-hosted label combination for every matrix entry --
confirmed by reading every matrix entry's own runner: field, not
sampling one. build-arm64 (same file) runs on ubuntu-24.04-arm,
a genuine GitHub-hosted runner, per its own comment: "hosted runners
can't reach the self-hosted LAN's ... sccache/distcc" -- the exact
same reachability problem as this proxy. tools/build-tools.yml has
the identical split: build-tools (self-hosted amd64) vs.
build-tools-arm64 (ubuntu-24.04-arm, GitHub-hosted). Added the
three proxy build-args (+ lowercase) to build-push.yml's single,
matrix-parameterized build job's build-args list -- one place,
covers all matrix services, no per-service duplication needed -- and
to both docker invocations inside build-tools.yml's self-hosted
build-tools job (the local PR-path scan-image build and the real
publish build). Neither build-arm64 nor build-tools-arm64 was
touched, so their builds get empty/unset proxy ARGs by construction,
satisfying "must stay empty on GitHub-hosted" without needing a
runtime conditional -- the job-level self-hosted/GitHub-hosted split
already IS this repo's existing pattern for exactly this problem.

Verified live, not assumed:
- ARG-declared HTTP_PROXY/http_proxy (predefined-proxy-name Docker/
  BuildKit ARGs) are automatically visible as real process
  environment variables to RUN instructions in the same stage with NO
  explicit ENV redeclaration needed -- built a throwaway two-line
  test Dockerfile, passed --build-arg HTTP_PROXY=...
  --build-arg http_proxy=..., env | grep -i proxy inside a RUN saw
  both. This directly answers (and corrects) the coordinator's own
  assumption that ENV redeclaration was required.

  with --build-arg HTTP_PROXY= --build-arg http_proxy= still ran
  apk update && apk add curl && curl https://example.com to a clean
  HTTP 200, no error, no hang.

  NO_PROXY from the real process environment by their own standard
