## Summary
Implements issue #1176's remaining scope (Angle 1): a `setup.sh list-prompts` introspection mode that walks the install wizard's real branch logic for a supplied set of answers, and refactors both `expect`-driven simulation scripts to derive their expected prompt sequences from it instead of hand-encoding them.

## Linked Issues
Closes #1176. This diff touches only `setup.sh`, `scripts/*.sh`, `scripts/lib/*.sh`, and `tests/bats/*.bats` -- no `.github/workflows/**` or governance-doc changes, so AG-CI-019's "Refs, not Closes, until synced to master" gate does not apply here.

## What This Actually Changes
Before: `setup.sh`'s interactive install wizard prompt sequence was hand-duplicated in `scripts/setup-cli-simulation.sh` and `scripts/syslog-forwarding-simulation.sh`, each independently typing its own `expect_prompt {pattern} reply` sequence. PR #1256 (merged, Angle 2) added `scripts/check-setup-prompt-drift.sh`, a static guard that catches a new *unconditional* prompt with no matching hand-encoded pattern -- but by its own documented design it cannot catch a new prompt on a *conditional* branch a simulation script's own answers actually walk (e.g. a new prompt inside the SSL or Kea blocks), because it never executes `setup.sh`.

After: `setup.sh list-prompts [answers-file]` walks the wizard's real, current branch logic (the *exact same* `ask()`/`confirm()` call sites the interactive install uses -- not a re-implementation) and reports the ordered prompt sequence for a given set of answers, without touching the filesystem, network, or Docker. Both simulation scripts now call this, feeding it the exact reply values they already send interactively, and build their `expect_prompt` patterns from that real output. A new prompt on any branch a script's answers reach is now picked up automatically -- there is nothing left to hand-duplicate for that phase, so nothing left to drift.

## What This PR Fixes / Adds
- `setup.sh`: new `list-prompts` dispatch case (falls through into the same top-level wizard code `install|""` already falls through to, per AGENTS.md's own emphasis on not re-implementing branch logic a second time). `ask()`/`confirm()` share one new introspection-mode helper (`wizard_introspect_record_prompt`) that emits a machine-readable `PROMPT\t<text>\t<default>` line and resolves the reply from an optional answers file (one reply per line via fd 9; blank/exhausted = accept the default, same as a real Enter keypress) instead of blocking on `/dev/tty`. Every real host mutation reachable from the prompt-gathering region (`ip addr add`, `mkdir -p`+`install_quickstart_compose_assets`, Admin-UI password generation, the whole "Writing .env" -> "Installing systemd watchdog" span, and the final pull/systemctl/`docker compose up`) is skipped in introspection mode.
- `scripts/lib/setup-wizard-introspect.sh` (new): shared helper -- `build_expect_prompt_block` runs `setup.sh list-prompts` and builds Tcl `expect_prompt` lines from the real output, failing closed on a reply/prompt-count mismatch instead of silently misaligning.
- `scripts/setup-cli-simulation.sh` / `scripts/syslog-forwarding-simulation.sh`: fresh-install `expect` blocks now generated from `build_expect_prompt_block` instead of hand-typed.
- `scripts/check-setup-prompt-drift.sh`: stays in place (AG-VAL-015 -- not weakened/removed just because introspection exists), updated to recognize an "introspection-driven" simulation script (references `build_expect_prompt_block`) and skip it from the now-inapplicable static text-matching, with its own fail-closed sanity check (must still contain `spawn bash setup.sh`) so a script that regresses back to not driving the wizard at all is still caught.
- `tests/bats/setup_wizard_introspection.bats` (new, 14 tests) and updates to `tests/bats/check_setup_prompt_drift.bats` (2 new tests + 1 updated assertion for the real repo's new success message).

## Why This Matters For Users / Operators
No user/operator-visible change to the real install flow -- `list-prompts` is a new, opt-in, non-mutating subcommand that never runs during a normal `curl | bash` install. The operator-visible benefit is indirect: this closes a real, previously-documented blind spot in CI's own regression coverage for the install wizard (the exact shape that let PR #1082 silently break both simulation scripts, discovered only days later on an unrelated PR per issue #1175) for the fresh-install phase, making a future silent wizard/CI-script drift less likely.

## Scope Boundaries
- Does not touch the "Overwrite?"/"Overwrite .env?" prompts' dependency on real filesystem state (introspection mode's prompt sequence still depends on the target install directory's real state for those two prompts, exactly like the real interactive wizard already does -- callers must run `list-prompts` before the real install creates those files, which both refactored simulation scripts already do).
- Does not extend the update/backup/restore CLI paths (`cmd_update`, `cmd_backup`, `cmd_restore`) or the `secondary` subcommand -- issue #1176's scope was specifically the install wizard's prompt sequence.
- Does not attempt to make `scripts/check-setup-prompt-drift.sh` itself execute `setup.sh` -- it remains a static, non-executing second net by design (see its own header for the updated rationale).

## Risk / Rollback / Follow-up
Risk is low and contained: `list-prompts` is new, additive, and unreachable from the default `install` path; the real install wizard's own control flow is unchanged except for the introspection-mode guards, which are all `if [[ "$WIZARD_INTROSPECT_MODE" != "1" ]]`-gated and no-ops for a real interactive run. Rollback is a plain revert. No follow-up work is required to close #1176's remaining scope; a real, previously-undocumented bug (introspection mode fabricating a random Admin-UI password on every call, found by this PR's own repeat-run bats test on a real Linux runner) was found and fixed in the same pass rather than deferred.
