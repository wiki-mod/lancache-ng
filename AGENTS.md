# lancache-ng — Repository Governance

**Project**: lancache-ng — a local download cache for home networks, LAN parties, labs, schools, offices, or gaming rooms. Stores game/software downloads locally so repeat downloads on the LAN run at LAN speed instead of re-fetching from the internet. Adds SSL interception (MITM via a custom CA) and full IPv6 dual-stack support on top of the original lancachenet concept.
**Repository**: https://github.com/wiki-mod/lancache-ng
**See also**: `CLAUDE.md` (Claude Code project instructions, auto-loaded every session) exists solely to point Claude Code sessions at this file at session start (Rule-Ref: AG-GOV-001) — architecture and setup content lives here, in this file, not there; `README.md` for end-user-facing documentation.

This file contains repository-wide agent rules. It applies to all paths in this repository, including `.github/**`, `setup.sh`, `deploy/**`, `config/**`, `scripts/**`, and `services/**`.

## Rulebook Interpretation

- **[AG-LAW-001]** AGENTS.md is a single, unified rulebook. All applicable rules apply simultaneously to every affected part of the project and to the change as a whole. Compliance with the rule that motivated a change does not establish overall compliance. Any touched file, asset, generated output, project behavior, or other affected part of the project must be checked against every applicable rule in this document. A task must not be declared complete until all affected parts and the complete change have been checked against every applicable rule in AGENTS.md. Declaring a task complete after verifying only one or some applicable rules is itself a violation of this rule, even if those specific rules were satisfied.

- **[AG-LAW-002]** In every maintainer-visible conversational message under Rule-Ref: AG-CC-002, any time that is stated or displayed must be given in Berlin local time (`Europe/Berlin`). The seasonally correct timezone abbreviation must be used — `CEST` during daylight saving time, `CET` during standard time — placed immediately after each time value, e.g. `14:30 CEST` or `09:15 CET`. A time given without a timezone abbreviation, or a fixed UTC offset used in place of `Europe/Berlin`, is not permitted. Time values from GitHub APIs, host/session clocks, logs, or any other external source must be converted to `Europe/Berlin` before being stated to the maintainer. This rule applies to all maintainer-visible chat, reasoning, status, progress, and comparable conversational messages; non-visible internal reasoning and raw, unprocessed API/machine data are exempt. This rule is additive to Rule-Ref: AG-CC-002 — the required language remains German. A session must never trust its own timezone resolution (e.g. a locally set `TZ` environment variable, or a tool's default) without verifying it against an independent source — such as the host operating system's own configured timezone setting, or a separate trusted clock — before stating a time to the maintainer; a tool that silently falls back to the wrong timezone without raising an error is exactly the failure mode this verification step exists to catch. *Origin (2026-08-22): a session stated a loop's end time using the session host's own local clock without converting it to Berlin time, producing a real ~2 hour discrepancy in a stated deadline. A later same-day incident confirmed the verification requirement above is not hypothetical: a session's `TZ=Europe/Berlin`-prefixed shell command silently fell back to the wrong timezone with no error raised, because the shell environment had no system timezone database at all, and only a cross-check against a second source (the host OS's own configured timezone) caught it.*

- **[AG-LAW-003]** Every rule in this document MUST express binding requirements and prohibitions with RFC 2119 keywords. Binding requirements MUST use `MUST`, `REQUIRED`, or `SHALL`. Binding prohibitions MUST use `MUST NOT` or `SHALL NOT`. `SHOULD`, `SHOULD NOT`, and `MAY` MUST be used only for genuine recommendations or optional behavior and MUST NOT substitute for mandatory requirements or prohibitions. Bare imperatives, negated `MAY` constructions, or other ambiguous wording MUST NOT be used in place of the applicable RFC 2119 keyword.

## Language

- **[AG-GH-001]** All GitHub-visible content, including issues, pull request bodies, comments, automated review or bot output, commit messages, code, code comments, and documentation, MUST be written in English regardless of whether it is produced by a human contributor, session agent, dispatched sub-agent, or third-party automated tool. This rule controls all content that lands in GitHub and MUST take precedence over AG-CC-002, AG-CC-003, and AG-CC-004 wherever those rules could be interpreted otherwise.

- **[AG-CC-002]** Chat/session language with the maintainer — the live conversational turns between the maintainer and a session, including visible reasoning/thinking shown to the maintainer during that session: **German**. This governs only that conversational channel. It never reaches content that is or becomes GitHub content (per Rule-Ref: AG-GH-001) merely because the conversation discussing it happens in German — e.g. an agent may narrate in German chat about a PR body it is about to post, but the PR body itself stays English.

- **[AG-CC-003]** AG-CC-002 MUST apply in full to every dispatched agent exactly as it applies to the main session, including chat, session communication, and visible reasoning or thinking. This rule MUST extend AG-CC-002 recursively across all dispatch boundaries and nesting levels and MUST NOT narrow, replace, or redefine AG-CC-002 for an agent's own behavior. Instructional prose in Agent(), SendMessage, Workflow agent() or equivalent dispatch prompts, and all report or status text returned to a dispatcher, MUST be written in German. Every dispatched agent that spawns sub-agents MUST apply AG-CC-002 to its own behavior, apply this rule to all spawned sub-agents, and explicitly instruct those sub-agents to propagate the same requirements through any further nesting. Literal quoted material, including code, error or log output, file paths, commit messages, and any content that is or becomes GitHub content under AG-GH-001, MUST remain in its required original or English form and MUST NOT be translated. The presence of such material MUST NOT justify writing the surrounding instructional prose in English.

- **[AG-CC-004]** Any third party automated tool that reads or is instructed to follow this file MUST apply AG-GH-001 to every portion of its output that is posted to GitHub or otherwise destined to become GitHub content, and MUST NOT apply AG-CC-002 or AG-CC-003 to that GitHub content. Tool identity MUST NOT determine the governing language rule. Output returned only to the maintainer in an interactive or local session and never destined for GitHub MUST follow AG-CC-002. GitHub review comments, pull request descriptions, and equivalent GitHub artifacts MUST be written in English. If GitHub content produced by such a tool is observed in German or another non English language, this file MUST be used as the repository controlled enforcement mechanism because the repository does not control the tool's internal configuration or system prompt. Such recurrence MUST NOT weaken AG-GH-001 or this requirement. If clarification does not prevent recurrence, this rule MUST be strengthened according to AG-WF-025's second occurrence standard. Compliance MUST be manually spot checked against automated tool output. The Required Validation and docs/release-validation-plan.md machinery MUST be used under AG-VAL-029 to determine whether a durable and repeatable check for external bot output is practical.

## Source of Truth and Conflict Resolution

1. **[AG-DOC-002]** Current executable checks and actual code behavior MUST be treated as ground truth. Documentation MUST NOT contradict behavior verifiably enforced by code or CI. Any documentation that does so MUST be treated as stale.
2. **[AG-DOC-003]** AGENTS.md MUST define the repository wide hard rules for agent behavior, workflow, validation, and governance and MUST apply to all repository work unless a more specific source listed below claims scoped precedence for its own area. Area specific AGENTS files under item 3 MUST take precedence within their stated scope once the work is identified as falling into that area, according to AG-DOC-004. SECURITY.md under item 4 MUST take precedence for security relevant work within its stated scope, according to AG-DOC-005. Rules MUST be written soberly and concisely as direct requirements, prohibitions, permissions, or conditions. Rules MUST NOT contain storytelling, historical narration, origin history, review history, discovery history, or other non normative narrative content.
3. **[AG-DOC-004]** Area-specific AGENTS files** (e.g., `.github/AGENTS.md` for GitHub Actions work) — Specialized guidance for specific areas takes precedence over general guidance once you have identified that your work falls into that area.
4. **[AG-DOC-005]** `SECURITY.md`** — Security-specific behavior and constraints are documented separately and take precedence for security-relevant work.
5. **[AG-DOC-006]** Architecture and release documentation** (e.g., `docs/architecture-ng.md`, `docs/release-versioning.md`, `docs/release-external-images.md`, `docs/threat-model.md`) — System design and release procedures are documented here with rationale.
6. **[AG-DOC-007]** `README.md` and user-facing documentation** (e.g., `docs/install-ca-cert.md`) — End-user guides and high-level project descriptions are placed last because they are more likely to lag behind operational or technical changes.

**Surfacing and resolving conflicts:**
- When an agent finds a real conflict between two of these sources (not a misreading, but a genuine inconsistency that reflects stale documentation or outdated guidance):

- **[AG-DOC-008] Conflicting requirements or interpretations MUST NOT be resolved by silently choosing one and proceeding. The conflict MUST be surfaced and resolved explicitly before continuing.
- **[AG-DOC-009] Conflicting requirements or interpretations MUST be escalated to the maintainer for an explicit decision. The escalation MUST identify the conflicting sources and the observed real world behavior. Work affected by the conflict MUST NOT proceed until the maintainer has decided which requirement governs. Noting into an PR or Issue does not resolve it.
- **[AG-DOC-010] A confirmed conflict MUST be resolved by either updating stale documentation to match verified code or CI behavior, or updating code or CI when the documented behavior is determined to be the intended target. If the correct governing behavior is ambiguous, cannot be determined from code and documentation alone, or has operational impact involving hardware, cost, network topology, services, or availability, the conflict MUST be escalated to the maintainer for an explicit decision before affected work continues. Technical decisions that do not meet these conditions MUST be made independently by the agent. This precedence order MUST be followed for all repository work where documentation drift can create operational risk.

## Issue And PR Tracking

- **[AG-GH-002]** Issue descriptions must include the correct links to related pull requests, issues, or parent tracking threads when those relationships are known.
- **[AG-GH-009]** Issues should also carry labels, an issue Type, a Milestone when one applies, and Project-board assignment; use GitHub's native parent/sub-issue relationship (not just a title convention) when an issue is genuinely a sub-task of a tracking issue. An issue left as an unclassified note without these fields is not fully triaged.
- **[AG-GH-003]** Pull requests must reference their tracking issue in the PR body whenever possible.
- **[AG-GH-010]** Every pull request body must include a changelog-style summary: what changed, user-visible impact, how it was validated, known risk, and any follow-up work. A PR without this cannot be called integration-ready regardless of CI status.
- **[AG-GH-008]** Every pull request MUST have at least one label, Project board assignment, and a Milestone when one applies. If a pull request closes or fixes exactly one issue through Closes #123 or Fixes #123, it MUST mirror that issue's labels and Milestone and MUST NOT derive metadata from a non closing Refs #456 target. A Refs only parent tracker or design discussion MUST NOT override the metadata of the issue actually being closed or fixed. If the referenced issue has no Milestone, the pull request MUST NOT invent one solely for compliance. A pull request without any tracking issue MUST still receive its own labels and, when applicable, Milestone during review. Correct code and successful CI MUST NOT be treated as sufficient while required tracking metadata or Project board assignment is missing. Required metadata MUST be set as part of the same action that opens the pull request and MUST NOT be deferred until pr-tracking-metadata-check in build-push.yml fails. A failed metadata check on a non draft pull request MUST be treated as a compliance failure, not as an acceptable initial state.
- **[AG-GH-004]** Use closing keywords such as `Fixes #123` or `Closes #123` only when merging the PR should close the issue.
- **[AG-GH-005]** Use non-closing references such as `Refs #123` for parent trackers, design discussions, drafts, or partial follow-up work.
- **[AG-GH-011]** Scaffold or partial-fix PRs must say they are scaffold or partial in the title/body, must name the remaining open tracker with `Refs #123`, and must not use `Fixes #123` / `Closes #123` for the unresolved remainder.
- **[AG-GH-012]** After a PR lands, compare the merge commit or current `github/master` against the original issue before claiming completion; PR-head-only claims are not sufficient.
- **[AG-GH-006]** Do not leave known issue/PR relationships only in chat history; capture them in GitHub so review, merge, and cleanup decisions stay traceable.
- **[AG-GH-013]** Every agent working on an issue or pull request MUST maintain a durable, mechanically enforced work record throughout the task. This requirement applies to all work regardless of perceived size or complexity and MUST NOT be delegated solely to the dispatching agent, satisfied only by the initial issue or pull request body, left only in chat, or deferred to a final report. A /loop or equivalent background mechanism MUST run every 15 minutes for the duration of the task and MUST emit a reminder tagged with the relevant issue or pull request number. At every checkpoint, all real progress MUST be committed and pushed. GitHub progress comments MUST NOT be used as a substitute for these checkpoint commits. If a checkpoint occurs before any real diff exists, the checkpoint MUST still be acknowledged and its status MUST be recorded in the next commit message once a commit becomes available. If the task finishes without producing any diff, an empty marker commit MUST be created with git commit --allow-empty and MUST record the task status. Checkpoints MUST NOT be skipped silently, estimated from elapsed turns, replaced by an undefined update cadence, or deferred to an end of task summary.
- **[AG-GH-014]** Every issue MUST be independently actionable from its body alone. The issue MUST identify the exact files, functions, or paths concerned, define concrete and verifiable acceptance criteria, and provide evidence that the problem exists through a reproduction, log excerpt, specific code reference, or equivalent proof. Vague goals such as improving or investigating a general subsystem MUST NOT be accepted as sufficient specification. An issue MUST contain enough context for an implementer with no prior knowledge or conversation history to determine which changes are required. Any issue that depends on unstated context MUST be expanded before assignment to a human or agent.
- **[AG-GH-015]** A follow-up or successor issue that narrows or continues an earlier issue MUST state in its own body whether it fully covers the original acceptance criteria or only a subset. If it covers only a subset, it MUST identify exactly which original criteria remain uncovered. The original issue body MUST then be updated with a Current Status note that links to the successor and states that the original MUST NOT be closed when the successor is completed unless all remaining acceptance criteria are also satisfied. Titles, labels, comments, or implied scope MUST NOT be relied upon to communicate whether a successor supersedes the original.
- **[AG-GH-016]** **Before closing an issue as resolved, superseded, or duplicate, actually diff its acceptance criteria against the PR/issue you believe covers it — do not match on topic or title similarity alone.** Two issues about "the same area" are not automatically the same issue; one may be a strict subset of the other's scope. Prefer verifying against the real current repository state (run the actual check, read the actual current file) over trusting either issue's prose, since both may have been written before the code moved further.
- **[AG-GH-017]** Before starting branch based work, every agent MUST clarify the exact intended scope and MUST verify whether that scope is already covered by an existing branch, pull request, or issue. The verification MUST use git fetch --all --prune && git branch -r, gh pr list --state all --limit 200 --search <keywords>, and gh issue list --state all --limit 200 --search <keywords> with relevant keywords or issue numbers. Default open only searches, default result limits, or stale remote tracking refs MUST NOT be considered sufficient. Each distinct work scope MUST use its own separate branch. Unrelated fixes, investigations, documentation, audits, or follow up work MUST NOT be added to an existing branch merely because that branch is already available. A new branch MUST be linked in writing to its scope shortly after creation through a pull request or an explicit linked issue comment naming the branch and its purpose. Every dispatched agent MUST follow the same clarification, coverage check, separate branch, and traceability requirements. A branch that will not become a pull request MUST be explicitly marked as abandoned, superseded, exploratory only, or duplicate work and MUST be flagged for deletion with its reason recorded. Actual deletion MUST require explicit maintainer instruction under AG-WF-005.
- **[AG-GH-018]** Pull request titles MUST follow the Conventional Commit form type(scope)!: subject, where scope and ! are optional. The PR title itself MUST be validated by scripts/tracked/check-pr-title-convention.sh through the pr-title-convention-check and pr-title-convention-check-hosted jobs in build-push.yml.
Allowed types are feat, fix, security, docs, refactor, perf, test, build, ci, chore, style, and revert. Their release impact MUST be interpreted as follows: feat bumps the minor version, fix, security, and perf bump the patch version, docs, refactor, test, build, ci, chore, and style do not require a version bump, and revert MUST follow the release impact of the reverted change. A breaking change MUST be marked by ! after the type or scope, or by a BREAKING CHANGE: footer in the pull request body. While the project remains below version 1.0.0, a breaking change MUST bump the minor version and MUST NOT automatically bump the major version. Promotion to 1.0.0 MUST require an explicit maintainer decision. security MUST be treated as a valid first class type and MAY also be combined with an allowed scope. Scopes are optional and MUST be lowercase. When present, the scope MUST be one of proxy, dns, dhcp, dhcp-proxy, ntp, ui, nats, watchdog, netdata, syslog, warmer, setup, ci, governance, docs, scripts, tests, or build-tools. Adding or removing an allowed scope MUST update both this rule and the allowed_scopes definition in scripts/tracked/check-pr-title-convention.sh. PR_TITLE_LINT_MODE MUST control enforcement mode and MUST default to warn. In warn mode, a non draft pull request with a non conforming title MAY leave the CI check green with a warning, but the title MUST still be treated as non compliant and MUST be corrected before merge. Setting PR_TITLE_LINT_MODE to block MUST cause non conforming non draft pull request titles to fail the check. Draft pull requests MAY receive warnings without blocking. This title convention MUST NOT be treated as sufficient release automation for release-please. release-please integration MUST account separately for the repository's actual commit message format and merge strategy because PR titles are not automatically used as commit headers. Adoption of release-please therefore MUST NOT be assumed complete solely because PR titles comply with this rule. Since this rule and its enforcement MUST apply only to pull requests created or updated after the rule becomes effective. Existing merged history MUST NOT AND IS FORBIDDEN TO be rewritten or retroactively treated as non compliant.

- **[AG-GH-019]** Before acting on, summarizing, reporting, closing, or determining the status or scope of any issue or pull request, every agent MUST read the full title, body, and complete comment history in chronological order from oldest to newest. gh issue view N --json body,comments or gh pr view N --json body,comments MUST be used as applicable, and .comments[] MUST be evaluated in chronological order. The body alone, the latest comment alone, or a dispatcher supplied summary MUST NOT be treated as sufficient current state. Each comment MUST be treated as cumulative new information on top of the preceding history. Large bodies or comment histories MUST still be read in full and MAY be processed in consecutive chunks of approximately 25,000 tokens; content MUST NOT be truncated or skipped for convenience. When a later comment changes, supersedes, narrows, expands, or contradicts information in the title or body, the later information MUST govern the affected point. Resulting stale body information MUST be corrected by updating the body or by posting an explicit status correction comment and MUST NOT be silently worked around. These requirements MUST apply equally to dispatched agents, which MUST independently read the full chronological history before reaching conclusions about current scope or status. AG-GH-022's requirement to maintain a durable, atomized, comment ID cited checklist in the body MUST always be applied together with this rule and MUST NOT be treated as an optional follow up.

- **[AG-GH-020]** When new information makes an earlier issue or pull request comment objectively outdated, superseded, resolved, off topic, or duplicative, that comment MUST be minimized using GitHub's minimizeComment GraphQL mutation with the matching classifier OUTDATED, DUPLICATE, RESOLVED, or OFF_TOPIC. Posting a correcting or superseding comment alone MUST NOT be treated as sufficient. Minimization MUST NOT be treated as deletion and MUST NOT replace AG-WF-026. Before minimizing a comment that contains the only copy of a substantive finding, decision, or evidence, that information MUST first be consolidated into a durable location such as the issue or pull request body, a structured comment, or another appropriate record. After any minimizing pass performed by the main thread or a dispatched agent, the main or coordinating thread MUST independently verify that the remaining comment history and body together represent one current and consistent state. A dispatched agent's report of completed minimization MUST NOT substitute for this verification.

- **[AG-GH-021]** Any issue or pull request body that documents or modifies current-dev-auto-close.yml or another closing-keyword scanner MUST NOT contain an unmasked closing keyword immediately followed by a real #N reference when used only as an example, quotation, or description rather than an actual closing instruction. Such references MUST break the scanner's matching pattern, for example by using issue 123, #&#8203;123, or another form that prevents literal keyword #N adjacency. Technical scanner hardening MAY exclude examples or code blocks but MUST NOT replace this authoring requirement.

- **[AG-GH-022]** When an issue or pull request comment history becomes large enough that the current status is no longer clear from the title and body alone, the body MUST maintain a chronologically ordered, atomized Live checklist under AG-GH-019. Each substantive comment MUST have its own checklist entry and MUST NOT be merged with other substantive comments into a single summary entry. Every entry MUST cite the originating GitHub comment permalink using #issuecomment-<id> and MUST accurately paraphrase what that specific comment stated, decided, or found. Each entry's checked or unchecked state MUST be verified individually against concrete evidence and MUST NOT be inferred from surrounding context or another entry. A checked [x] entry MUST document the specific evidence, command output, or reasoning that verifies completion. Any new comment that adds, changes, resolves, or supersedes substantive information MUST update the checklist in the same pass in which that comment is processed. When a later comment contradicts or corrects an earlier comment, the later comment MUST govern under AG-GH-019. The earlier checklist entry MUST remain visible and unchecked and MUST reference the later comment that resolved or superseded it.

Routine WIP or standing-loop checkpoints required by AG-GH-013 MUST NOT each receive separate checklist entries. A sequence of such checkpoints MUST instead be consolidated into one evidence-bearing summary comment before being referenced from the body. That summary MUST follow .github/issue-checklist-response-template.md and cover Summary, What This Actually Changes, What Was Found, What Changed In Code, Validation including AGENTS.md compliance checks, Risk/Rollback/Follow-up, Local Scope Evidence, and unresolved or deliberately deferred bugs or problems. The body checklist MUST cite the consolidating comment's actual comment ID and MUST NOT cite the raw checkpoint commit range as its substitute.

For sufficiently complex issues or pull requests, checklist items MAY be grouped sequentially within lettered sections with ## Status and ## Current verified checkpoint sections above the checklist. wiki-mod/lancache-ng#1501 MUST be treated as the reference structure when a flat checklist is no longer navigable, and wiki-mod/lancache-ng#1527 MAY be used as the reference implementation for comment ID citation, WIP consolidation, and superseded entry handling.

Comments MUST NOT be deleted or have their original content removed or rewritten merely because they are stale, superseded, or later proven incorrect. A comment MAY be deleted only when it is demonstrably a genuine posting mistake or contains content that should never have been posted, and only after the maintainer gives explicit, fresh approval for that specific comment. Standing or general cleanup approval MUST NOT authorize comment deletion, and an agent MUST NOT delete a comment unilaterally.

When a comment is confirmed superseded rather than mistaken, its original content MUST remain intact. The comment MUST be marked in place by prepending a clearly visible bold uppercase marker such as SUPERSEDED / NO LONGER CURRENT and appending an Updated <date/time>: <explanation> note that identifies and, where practical, links the later superseding comment and states why the earlier comment is no longer current. Only these additive markings MAY modify the existing comment; the original content between them MUST remain unchanged.
- **[AG-GH-023]** **Using `gh stack` to organize multiple open pull requests is not a default obligation.** An AI agent must never create, join, or link a pull request into a `gh stack` on its own initiative — only when the maintainer explicitly requests it for that specific pull request or set of pull requests. This reverses this rule's previous blanket requirement (organize every open PR through `gh stack`, regardless of dependency): real-world use showed AI agents cannot yet reliably operate `gh stack` — a single stack merge took three days to resolve in practice — and the mandate caused more harm (stuck rebases, duplicated commits over stale branches, extended remediation) than the coordination benefit it was meant to provide. This is a narrowing placeholder pending a fuller rework of this rule (2026-08-27); how genuinely dependent PRs should be organized instead is not yet answered.

  When the maintainer does explicitly request a stack for one or more PRs, the following still applies: any `gh stack init`/`gh stack link` invocation for a PR targeting the development trunk must explicitly specify `--base current_dev` — the command's own default base must never be relied upon, since it resolves to this repository's configured GitHub default branch (`master`), not the active development trunk. This does not apply to a PR that legitimately targets `master` itself (a CI/governance sync PR under Rule-Ref: AG-CI-019, or a release-promotion PR) — those use `--base master`, matching the branch they actually target.

  **A PR must always be opened against `current_dev`/`master` first, and only retargeted onto another PR's branch afterward via `gh stack link` — never created with a stacked (feature-branch) base from the start.** Confirmed live (2026-08-20, disposable test PR #1615, closed without merging): `build-push.yml`'s `pull_request` trigger (`branches: [master, current_dev, "v[0-9]*"]`) only evaluates against the base a PR had when its first matching event occurred. A PR opened with a non-matching (feature-branch) base from creation gets zero `Build & Push` runs, silently, for its entire life — confirmed by opening #1615 directly against a feature branch and observing no `Build & Push` run at all (only unrelated `pull_request_target` workflows fired). A PR opened normally against `current_dev`, then later retargeted via `gh stack link`, keeps running real CI on every subsequent push (confirmed live on PR #1604) — the already-established check-suite is not re-gated by the filter on a later retarget. The order matters: open first, link second, never the reverse.

  **Resolving a conflict in a `gh stack`-tracked branch is done only through `gh stack` itself, never through a manual `git rebase`/`git merge`** — even when `gh stack rebase` is demonstrably misbehaving for that case; a mechanically equivalent result via plain git does not satisfy this rule. The standard path (GitHub's own documented procedure): `gh stack checkout <pr-number>`, then `gh stack rebase`, resolve conflicts with ordinary `git` conflict resolution and commit, then `gh stack push`. If `gh stack rebase` itself fails or behaves incorrectly (a confirmed real case: a second rebase pass on a stack whose lower members already merged can duplicate already-applied commits, because it derives its plan from the full local, non-linear merge history rather than GitHub's own current view) — do not substitute a manual rebase to route around it. Instead: `gh stack rebase --abort` (safe, local-only), then re-import the stack fresh via `gh stack checkout <pr-number>` (GitHub's own server-side view already knows which lower members merged, independent of confusing local history). If that is still not enough, the local branches of the already-merged lower stack members may need deleting before rebuilding — `gh stack unstack` alone does not reset the affected PRs' base branches — but every step of that rebuild must still go exclusively through `gh stack` commands, never a manual git equivalent.

  `gh stack push`/`gh stack sync` push each branch using `--force-with-lease` internally as part of their normal operation — this does not exempt that action from Rule-Ref: AG-WF-024's re-verification requirement before any force-variant push, whether run directly or through the tool. `gh stack merge` itself refuses to bypass branch protection or required checks ("bypassing merge requirements is not supported for stacks"); Rule-Ref: AG-WF-039's literal-ACK requirement for any `--admin`/bypass action applies in full to a stacked PR exactly as it does to any other — there is no stack-specific exception, and an agent must not attempt a manual `--admin` merge to route around a stack merge that `gh stack merge` refuses to perform.

## Agent Workflow

- **[AG-WF-001]** Before starting or continuing work on a branch, and before making any readiness, mergeability, or integration-order statement, the agent MUST fetch the current remote branch and base branch, rebase the working branch onto the current remote base, and verify the resulting head. This verification MUST be repeated after a restart, continuation, or whenever branch freshness is uncertain. Work MUST NOT proceed on stale code or a stale branch. If the branch cannot be rebased successfully, the blocker MUST be reported and no readiness, mergeability, or integration-order conclusion MUST be given.
- **[AG-WF-020]** Deprecated, see AG-WF-001
  
- **[AG-WF-002]** Every PR, issue, and dispatched agent task MUST use its own separate worktree. Every worktree MUST be created under `<repo-root>\.claude\worktrees\<issue-nr>_<shorttext>` and MUST NOT use any other location or naming scheme.
Every one has to verifiy in front of to be in the correct way for each running command. The coordinating thread MUST create and bind the worktree to the relevant issue **before** dispatching an agent. A dispatched agent MUST verify the assigned worktree path and issue binding and MUST NOT create or invent a different worktree. Before any work begins, the worktree branch MUST be checked against its current base and MUST be rebased or updated first if it is stale or unverified. The first action in every newly created worktree MUST be an empty marker commit created with `git commit --allow-empty` that records the task and issue number. For dispatched agents, the marker commit MUST also record the agent task or session ID. The worktree MUST be removed with `git worktree remove` when its task is completed. Any uncertainty about this rule MUST be escalated through every dispatch level until it reaches the main coordinating thread, which MUST resolve it or obtain an explicit maintainer decision.

- **[AG-WF-003]** Bounded independent work MUST use fanout when delegation reduces main thread cost without reducing quality. The cheapest suitable model and reasoning level MUST be preferred. Spark MUST be evaluated first while available. If Spark is unavailable, rate limited, or unsuitable, gpt-5.4-mini MUST be evaluated before delegable work remains in the main thread. Keeping delegable work in the main thread while Spark is unavailable MUST have a concrete justification, such as unsafe delegation, time critical local context, or higher integration risk from a separate agent.
- **[AG-WF-021]** Subagent results MUST be treated as stale until verified against the current remote base and current PR head. Before using a subagent result for readiness, conflict resolution, review comments, or merge guidance, the reported commit and base MUST be compared with the current GitHub state, and all relevant checks MUST be rerun against the current head.
  
- **[AG-WF-022]** Do not block on subagents when useful non-overlapping work is available. Poll sparingly, and close completed agents after their result has been reviewed or superseded.
  
- **[AG-WF-024]** Any agent that spawns subagents MUST assign each subagent its own explicitly assigned and verified clean working directory. No agent MUST assume that an inherited, isolated, or recycled worktree is pristine or based on the correct branch. Before substantive work begins, every agent MUST verify its actual current branch and HEAD against the expected clean remote base, including by fetching the remote and comparing the current history with `origin/<base-branch>`. If the worktree does not match the expected base, the agent MUST NOT salvage it in place by default and SHOULD instead discard it and provision a fresh worktree from a clean checkout of `origin/<base-branch>`. If a fresh worktree is unavailable and an existing worktree MUST be reset in place, the agent MUST run `git reset --hard origin/<base-branch>`, then `git clean -fd`, and MUST verify that `git status --porcelain` is empty before proceeding. `git clean -fdx` MUST NOT be used because gitignored local secrets or generated state MUST be preserved. `checkout -B`, `reset --hard`, or `git clean -fd` individually MUST NOT be treated as sufficient proof of a clean worktree- A subagent MUST NOT overwrite, rebase onto, or push over its parent agent's branch, another agent's branch, or any other in flight work. Immediately before any force variant push, including `git push --force`, `-f`, `--force-with-lease`, or `--force-if-includes`, the agent MUST verify the current branch and HEAD, the exact current remote ref, the reason that remote history must be overwritten, and that the content being pushed is exclusively the agent's intended work rather than stale, inherited, or unrelated content. A force push MUST NOT proceed unless all of these checks pass. A rejected non fast forward push MUST be treated as a stop and reverify condition and MUST NOT be bypassed reflexively with a force push. Every spawned subagent MUST independently read and accept `AGENTS.md`, `CLAUDE.md`, and `.github/AGENTS.md` before substantive work begins. Governance inheritance MUST NOT be assumed from the parent agent or dispatch context. The subagent MUST explicitly report by file name that it has read all three files. A generic acknowledgment MUST NOT satisfy this requirement. Before taking any action whose failure mode could silently destroy data or overwrite another branch's history, a subagent MUST consult its dispatching agent and MUST NOT resolve that action autonomously. Any uncertainty about the assigned worktree, branch, base, ownership, intended push target, destructive action, or applicability of this rule MUST stop the affected work immediately and MUST be escalated to the dispatching coordinator. If the coordinator cannot resolve the uncertainty conclusively, it MUST escalate the matter to the main coordinating thread. The affected work MUST remain stopped until the uncertainty has been fully resolved and the responsible coordinator or main thread has communicated the resulting decision.

- **[AG-WF-025]** A second occurrence of the same underlying failure pattern MUST trigger a proposal for a new or strengthened AGENTS.md rule addressing the root cause and MUST NOT be handled only by fixing the repeated instance. Recurrence MUST be determined by the same underlying cause pattern rather than by symptom alone. The proposed rule MUST be presented to the maintainer for review before it is added and MUST include the canonical English text and a German translation. - **[AG-WF-026]** Before any issue, pull request, branch, review thread, investigation, agent task, worktree, or comparable work item is closed, merged, resolved, marked duplicate, superseded, declared obsolete, abandoned, deleted, cleaned up, or handed off, all substantive knowledge not already present in the surviving target MUST first be consolidated and durably persisted there. Substantive knowledge includes findings, verified facts, evidence, reproductions, relevant logs, tested but rejected alternatives, decision rationale, assumptions, constraints, known limitations, unresolved questions, acceptance criteria, dependencies, risks, rollback information, implementation state, and cross references. A link to the source alone MUST NOT count as consolidation. Chats, agent reports, local notes, scratchpads, temporary files, CI output, commits, branches, worktrees, review discussions, or other transient or difficult to discover locations MUST NOT remain the only copy of substantive knowledge. The responsible agent MUST compare all available source material with the surviving target and transfer every missing substantive item. Historical findings and decision records MUST be preserved in a structured comment or equivalent durable record. Information that changes current scope, acceptance criteria, implementation requirements, architectural decisions, or status MUST also be incorporated into the authoritative target body or documentation. Consolidation MUST identify the source object or session, preserve relevant provenance and links, distinguish accepted decisions from rejected alternatives, describe the current implementation state, and state all unresolved remainder. Summaries MAY be used only when every material conclusion, constraint, rationale, risk, and required follow up is preserved. A final decision without the material reasons rejected alternatives failed MUST NOT be considered sufficient consolidation. For GitHub issues and pull requests, consolidation comments MUST follow the Agent Closing Report Contract structure covering context read, findings or changes, deliberately omitted material and its reason, verified evidence, known open risks, and follow up references. Local only state MUST be treated as temporary and MUST NOT satisfy this rule as a final durable record. Before an agent ends its task, hands work to another agent, releases or cleans its worktree, or allows its execution environment to terminate, all substantive local work MUST be committed where appropriate, pushed to a named remote branch, and linked or summarized in an existing durable tracking object. If no dedicated issue or pull request exists, the nearest applicable parent issue, tracking issue, pull request, or other repository record MUST be used. The absence of a dedicated GitHub object MUST NOT permit work to remain unpushed or undocumented. Significant findings, decisions, blockers, branch names, current state, and intended next steps MUST be recorded in the applicable durable tracking object while work is in progress. Unpushed branches, unopened pull requests, or local changes MUST NOT exempt the agent from this requirement. Temporary local records MAY exist only until the next safe persistence point and MUST NOT be relied upon across agent handoff, session end, worktree cleanup, container termination, or any other boundary where local state may be lost. Durable persistence MUST be verified before the lifecycle transition occurs. Remote target information MUST be posted successfully and read back. Repository artifacts MUST have their commit and expected remote branch verified. Other durable targets MUST be verified by an appropriate read back or equivalent check. Preservation and lifecycle actions MUST NOT be performed as one unverified sequence, deferred until after the lifecycle action, or justified only because the original source remains technically accessible. If no suitable surviving target exists, the source MUST remain open or active until one is designated. If substantive knowledge or implementation state cannot be transferred and verified completely, the lifecycle action MUST NOT occur and the blocker MUST be reported. An agent MUST NOT declare completion or complete a handoff while substantive knowledge or implementation work exists only in its conversation, temporary workspace, unpushed commit, unpublished branch, worktree, local file, or final report. The durable tracking record MUST be independently understandable and recoverable by a person or agent without access to the originating chat, session, machine, container, or worktree.

- **[AG-WF-027]** Every real defect, gap, missed edge case, inconsistency, or other problem identified during work MUST be fixed in the same pass, regardless of whether it belongs to the original task scope, was discovered intentionally, or was found incidentally. No identified problem MAY be ignored, deferred, scoped out, left as follow up work, or recorded only as a comment, note, limitation, review finding, scope boundary, issue, or future task. Recording or reporting a known problem without fixing it MUST be treated as DISACK and MUST NOT satisfy this rule or permit the task to be declared complete.
This requirement applies equally to newly discovered problems and to previously recorded problems found while reading an existing issue, pull request, body, comment history, review thread, known limitation, follow up note, or unresolved finding. Every such problem MUST be resolved as part of the current work. If fixing an identified problem requires a maintainer decision, separate approval, materially changes intended behavior, creates a significant new risk, or causes another problem whose correct resolution cannot be determined safely, the affected work MUST stop and the maintainer MUST be contacted immediately. The problem, its impact, the required decision, and the available choices MUST be explained to the maintainer in simple and direct language. The affected problem MUST remain unresolved only until that maintainer decision is received and MUST NOT be silently deferred or treated as accepted scope exclusion.

- **[AG-WF-028]** No artifact (branch, commit, comment, file, or other work) may be characterized as dead, stale, unsalvageable, or superseded based on aggregate diff- or file-count alone. Its actual *unique* contribution — content existing nowhere else — MUST be inspected first; a large diff against a newer base is not evidence of staleness, nor a small one of triviality. Proximity to actively-worked scope raises the bar, not lowers it. Deletion still requires the maintainer's fresh explicit instruction (Rule-Ref: AG-WF-005, Rule-Ref: AG-GH-017).

- **[AG-WF-029]** **A response to a recommendation/preference question is not execution authorization.** When the maintainer asks an agent for its opinion or recommendation ("what would you choose", "which do you recommend"), that question seeks a recommendation only. An agent must not proceed to implement the recommended option based on that alone — it must wait for an explicit, distinct go-ahead ("do that", "proceed", "yes, build A") before making any change. When genuinely unsure whether a maintainer's reply also authorizes execution, state the intended next step and wait for confirmation rather than proceeding silently. This mirrors the existing principle that finalizing a design/scheme is not itself authorization to execute it (2026-07-31 "yolo" naming-scheme incident) — extended here to cover recommendation questions specifically, after a second, distinct occurrence of the same underlying failure class (2026-08-01, issue #842 retention hardening: "what would you choose now" was answered and then treated as a go-ahead to implement, with no explicit confirmation ever given, until the maintainer caught it and had to ask for the implementation to pause). This project's concrete, agreed authorization protocol is the literal token ACK (authorize/proceed) or DISACK (do not proceed) — an agent looks for that exact word, not tone, enthusiasm, or an explanation that merely sounds affirmative. Absence of any reply is neither ACK nor DISACK under any circumstance — it means the decision remains strictly pending. No amount of elapsed time, silence, or lack of objection may ever be treated as implicit consent; an agent must keep waiting or explicitly ask again, and must never proceed on silence alone, regardless of urgency or perceived obviousness of the answer. Furthermore, whenever an agent identifies that a decision is required from the maintainer, that decision must be recorded as a comment on the relevant GitHub issue or pull request — not only stated in chat — as an explicitly structured, formatted list (markdown list syntax, with nested/indented sub-items for multi-part decisions) naming exactly what must be decided and the concrete options. A vague statement that "a decision is needed," in chat or in a GitHub comment, without the actual structured options attached in the same place, does not satisfy this rule.

- **[AG-WF-038]** A maintainer pause or stop instruction MUST carry at least the same authority as a literal DISACK and MUST remain in force until the maintainer explicitly revokes it. A plain `ACK`, any variation of that phrase, implied approval, contextual interpretation, or authorization from any other party MUST NOT lift the pause or stop.

- **[AG-WF-039]** Any `gh`, `git`, or equivalent administrative bypass action, including `--admin` or any mechanism that bypasses branch protection, required checks, review requirements, or repository safeguards, MUST be treated as formal DISACK by default. - **[AG-VAL-035]** **Before describing a verification as run "under the real/actual engine, version, or runtime the caller uses," first positively determine what the real caller actually declares — do not pick whichever candidate happened to be first in a directory listing or otherwise most convenient to reach.** For a GitHub Action, that means reading its own pinned `action.yml`'s `runs.using` (or the equivalent manifest for the ecosystem in question), not assuming a Node/runtime version because it was the first one found installed on a runner host. Running something real is not the same as running the right thing: an executed test against an unverified or already-deprecated target can still produce a result that happens to agree with the correct target, which does not retroactively make the original, unverified claim true at the time it was written. This rule exists because a real incident showed both failure modes at once: a regex fix for this repository's own auto-close workflow was verified by running it under `node20` (the first Node runtime found in a runner's `externals/` directory) and the accompanying PR body asserted this was "the real engine this workflow actually runs under," when the workflow's own pinned `actions/github-script@v9.0.0` declares `using: node24` in its own `action.yml` — and `node20` was, independently, already listed in this project's own `DEPRECATED_NODE_RUNTIMES` array, so it should never have been selected regardless of which engine the workflow turned out to use. ## Integrity

- **[AG-INT-001]** Lying, hallucinating, inventing, fabricating, or overstating information is strictly forbidden. Every factual claim about code, repository state, files, configuration, commands, syntax, APIs, tools, tests, builds, runtime behavior, dependencies, environments, infrastructure, or external systems MUST be supported by evidence actually obtained during the current investigation. `VERIFIED`, `CONFIRMED`, `PROVEN`, `WORKS`, `FIXED`, `PASSES`, `SAFE`, `UNUSED`, `IMPOSSIBLE`, or equivalent certainty MUST NOT be used beyond what the evidence establishes. Observed fact, static inference, hypothesis, expectation, and unverified assumption MUST remain explicitly distinct. Unverified information MUST be labeled accordingly. Memory, plausibility, conventions, documentation, comments, names, prior incidents, another agent's unsupported assertion, surrounding code, or absence of visible failure MUST NOT substitute for current evidence. Material claims MUST have identifiable and reproducible evidence, including relevant commands, environment, configuration, arguments, outputs, file reads, state inspection, or exercised behavior where applicable. Evidence scope MUST match claim scope. Reading code proves only what the code states, not runtime behavior. Reading a test proves only its intended check, not that it passes. Documentation proves only what is documented, not that the behavior works. A referenced path proves only that it is referenced, not that it exists. One run proves only that run under its actual conditions. One file, caller, test, platform, configuration, environment, input, revision, success, or failure MUST NOT be generalized beyond the scope actually checked. Negative claims such as no duplicates, no references, no failures, no callers, no regression, or impossibility MUST be backed by an appropriately scoped search or equivalent evidence and MUST state the scope actually checked. Current repository or runtime state MUST be rechecked when available. After modifying implementation, the relevant source MUST be reread and the applicable verification MUST be executed before claiming the change fixes, preserves, passes, or validates anything. Direct evidence MUST be preferred whenever feasible. A suspected defect MUST NOT be called confirmed from a suspicious line alone. Confirmation MUST identify the relevant behavior or invariant, trace the applicable execution, data, and control paths sufficiently to establish reachability and material effect, inspect relevant callers, guards, configuration, defaults, error handling, alternate paths, and compensating behavior, distinguish symptom from root cause, and perform empirical reproduction wherever technically feasible. If empirical reproduction was feasible but not performed, the defect MUST remain described as suspected or statically indicated. If reproduction is genuinely impossible because of missing environment, credentials, hardware, external service, destructive prerequisites, or equivalent constraints, that limitation MUST be stated explicitly. Root cause MUST NOT be claimed unless the evidence establishes it.
Commands, outputs, tests, file contents, repository state, citations, paths, issue or pull request numbers, commits, versions, configuration values, capabilities, or completed actions MUST NOT be fabricated. An action prepared, requested, initiated, or expected MUST NOT be reported as completed until its execution and result are observed. UNKNOWN MUST remain UNKNOWN until verified. If verification is unavailable, the verification boundary MUST be reported instead of filling the gap with an assumption. Core invariant: no evidence means no factual claim; static evidence permits only a static conclusion; runtime evidence permits only a runtime conclusion within the tested scope; complete relevant path tracing plus empirical reproduction permits a confirmed defect only within the established scope. Any stronger claim MUST require stronger evidence.

- **[AG-INT-002]** A validation result MUST represent observed reality and MUST NOT be manipulated to produce the desired outcome. Real warnings, errors, failures, mismatches, diagnostics, nonzero exit statuses, failed assertions, or other adverse signals MUST NOT be suppressed, filtered, downgraded, masked, hidden, discarded, truncated, reclassified, excluded from scope, or converted into success while the underlying condition remains. AG-INT-001 forbids creating evidence that does not exist; AG-INT-002 forbids removing evidence that does exist. Every wrapper, pipeline, helper, script, test runner, CI step, aggregator, and reporting layer MUST preserve the original semantic result and relevant raw stdout, stderr, diagnostics, logs, findings, and exit status of the operations it invokes. A failure at any layer MUST propagate to the final result unless a documented semantic operation independently establishes that the result is not a failure. Generic summaries MUST NOT replace available raw failure evidence. Multiple independent findings MUST all remain visible unless fail fast behavior is explicitly part of the check's intended semantics. Bounded retries MUST preserve that retries occurred and MUST expose relevant failed attempt diagnostics. Retry success MUST NOT be reported as if the initial execution succeeded. Constructs or mechanisms such as `|| true`, `|| :`, relevant `2>/dev/null`, filtering known failures, unsafe `tee` pipelines, ignored failures after `set +e`, blanket exception handling, warning suppression, truncation, exclusions, expected failure annotations, baselines, allowlists, ignore lists, permanent skips, severity downgrades, or equivalent mechanisms MUST NOT be used to conceal a real unresolved condition. Such mechanisms MAY be used only when they represent a genuine, independently justified, documented applicability or semantic boundary and preserve the original relevant evidence. A check MUST NOT be weakened merely because it currently fails, appears strict, noisy, flaky, inconvenient, preexisting, unrelated, environmental, or difficult to fix. Before changing a validation mechanism, the agent MUST determine what condition it detects, establish whether that condition is genuinely invalid, irrelevant, or misclassified, identify why the signal occurs, and correct the logic at the narrowest valid boundary. Every condition that remains invalid MUST remain detectable. A validation change MUST be proven with both a valid case that passes and an invalid case that still fails. Making only the current failing input pass MUST NOT be sufficient. Validation scope MUST follow the invariant being enforced and MUST NOT be narrowed to remove failing files, directories, hosts, environments, configurations, platforms, test cases, matrix entries, or other inputs. Repository wide invariants MUST NOT be reduced to changed files merely to obtain a passing result. Thresholds, severity, classifications, or applicability boundaries MUST NOT be changed solely to make current results pass. Classification MUST follow independently established reality.
A legitimate skip MUST apply only when the check is genuinely inapplicable under an explicit and testable condition. The inapplicable target MUST NOT be executed, the result MUST be reported as `SKIP` or `NOT-RUN` rather than `PASS`, the reason MUST be visible, the condition MUST remain narrowly scoped, and applicable failures MUST remain detectable. The check MUST automatically become active again once the applicability condition becomes true, and an exemption MUST NOT be kept after its reason is gone. A preexisting failure MUST remain reported as a failure while attribution to the current change is assessed separately. Flakiness MUST be treated as a defect in either the check or the system under test and MUST NOT be hidden through retry until green behavior. Expected failure handling MAY be used only when failure itself is the intended tested behavior and MUST NOT be used to park an unresolved regression. After modifying any validation or reporting mechanism, the complete propagation path from the underlying operation through helpers, wrappers, pipelines, test runners, CI steps, and final status MUST be verified wherever the result matters. The modified mechanism MUST still expose relevant raw evidence, preserve the correct failure count and affected objects, accept valid behavior, and reject prohibited behavior. The only valid outcomes for a detected adverse condition are to fix the underlying condition, fix a demonstrably incorrect check, explicitly skip a genuinely inapplicable check, or report the failure. A failing underlying condition MUST NOT produce `PASS`.


## Setup, Update, And Migration Semantics

- **[AG-OP-006]** Setup, update, and migration logic must be idempotent: running the same operation repeatedly must not rotate existing secrets, overwrite local configuration, or create new side effects unless the user explicitly requested that change.
- **[AG-OP-007]** Setup, update, and migration logic must converge old or incomplete installations toward the current expected state.
- **[AG-OP-008]** Missing required configuration values should be generated when safe or rejected with a clear fail-closed error when they require user input.
- **[AG-OP-009]** Existing non-empty local values must be preserved by default.

- **[AG-SEC-002]** Known placeholders such as `CHANGE_ME_*` are not valid runtime values and must be replaced or rejected before dependent services start.

### Key Design Decisions

- **[AG-KD-004]** DNS-spoof proxying MUST use nginx instead of Squid `intercept` mode. Squid `intercept` mode depends on real DNAT and `SO_ORIGINAL_DST` to determine the upstream destination; without DNAT, it can resolve the proxy itself as the destination and create a loop. nginx MUST derive the upstream destination from the client-provided `Host` header or `$ssl_server_name`, which is compatible with DNS-spoof proxying.

- **[AG-KD-005]** At startup, `entrypoint.sh` MUST pre-generate CA-signed 2048-bit wildcard certificates for CDN domains. Each root CDN domain MUST receive a certificate covering `*.<root>`. Additional certificates MUST be generated for `cdn-domains.txt` entries that cannot be covered by that root wildcard.

For a leading-dot wildcard-only entry such as `.cdn.example.com`, a dedicated certificate covering `*.cdn.example.com` MUST be generated whenever the entry differs from the root domain by any additional label, including exactly one label, because the hosts matched by the entry are one label deeper than the entry text.

For a bare exact-host entry such as `tlu.dl.delivery.mp.microsoft.com`, a dedicated certificate MUST be generated only when the host is more than one label below the root domain. A bare host exactly one label below the root MUST use the root certificate because `*.<root>` already covers it.

Generated certificates MUST use the fixed subject CN `lancache-ng`; real CDN hostnames MUST NOT be placed in the CN. The actual hostname or wildcard identity MUST be carried in the SAN used for TLS hostname validation. This avoids the OpenSSL CN length limit for long domain entries.

Certificates and keys for deeper entries MUST use a namespaced SHA-256 hash of the hostname as their filename and MUST NOT use the hostname directly, preventing violations of the Linux filename-length limit.

nginx MUST select the applicable certificate through `map $ssl_server_name $ssl_cert_name` in `conf.d/00-ssl-map.conf`. The `00-` ordering MUST be preserved so the map is defined before server blocks that consume it.

- **[AG-KD-006]** nginx cache configurations for large cacheable assets MUST enable `proxy_cache_lock on` so concurrent requests for the same uncached object do not trigger parallel upstream fetches. While the first request populates the cache, equivalent concurrent requests MUST wait for that cache fill instead of independently downloading the same object. This behavior is required for large game files and other objects likely to be requested concurrently by multiple clients.

- **[AG-KD-007]** `services/proxy/Dockerfile` MUST install nginx from nginx.org's official mainline package repository and MUST NOT use the base operating system's distro-provided `nginx` package. This applies to both the former Debian apt path and the current Alpine apk path, which MUST resolve the intended nginx mainline release.

Standard-mode SNI passthrough MUST use nginx's built-in stream capability from the nginx.org package. The required stream features MUST be provided by the compiled nginx binary itself, including `--with-stream` and `--with-stream_ssl_preread_module`, as verifiable through `nginx -V`.

A separate stream module package MUST NOT be installed for this nginx.org package, and `services/proxy/nginx.conf` MUST NOT add a `load_module` directive for stream support. Configuration or documentation that assumes Debian distro nginx behavior such as `libnginx-mod-stream` plus explicit `load_module` MUST be treated as incorrect for this project.

- **[AG-KD-008]** The repository MUST maintain exactly one deployment profile under `deploy/prod/` with its corresponding production configuration. A separate `deploy/dev/`, `config/dev/`, or equivalent parallel development deployment profile MUST NOT be introduced.

Development, local iteration, and real deployment validation MUST use `deploy/prod/docker-compose.yml` directly. The distinction between development, stable deployment, and release validation MUST be determined by the checked-out Git ref, such as `current_dev`, `master`, or a `vX.Y.Z` release ref, and MUST NOT be represented through separate Compose files, configuration directories, LAN addressing schemes, or duplicated deployment profiles.

Any implementation that requires a second deployment tree to remain manually synchronized with `deploy/prod/` MUST be treated as a violation of this rule.

Real validation MAY run on Linux self-hosted runners or other applicable Linux infrastructure instead of the Windows authoring host. Validation MUST NOT require or assume a separate development deployment profile merely because the authoring environment cannot execute the complete runtime stack locally.

- **[AG-KD-009]** `tools/build-tools` MUST remain Debian-based by default unless the maintainer explicitly approves a base-OS switch. The existing `alpine-final` stage in `tools/build-tools/Dockerfile` is an opt-in candidate only and MUST NOT become the implicit Docker build default, active CI build-tools image, or published default image without that explicit decision.

The unnamed Debian stage MUST remain the implicit `docker build` default. The Alpine candidate MAY be built explicitly with `docker build --target alpine-final` for evaluation. Existing CI workflows MUST continue using the Debian build-tools image until a maintainer-approved switch is implemented.

The Alpine candidate has verified package or source-build paths for the existing build-tools toolchain, including native Alpine `distcc` and `distcc-pump`, source-built `cargo-audit`, `cargo-tarpaulin`, and `sccache`, and Alpine-compatible builds of `actionlint`, Docker CLI, Buildx, and Compose. This evaluation MUST NOT be represented as proof that Alpine is already an approved replacement.

Alpine does not provide the required `dhclient`/`isc-dhcp-client` capability used by the three CI simulations that invoke `dhclient` against Kea. `dhclient` MUST therefore remain an `EXTRA_REQUIRED_TOOLS` requirement for those actual consumers so they fail closed when it is unavailable, while callers that do not require `dhclient` MUST NOT fail solely because the Alpine candidate lacks it.

The verified Trivy `os-pkgs` result for both the Alpine candidate and the corresponding Debian base is zero HIGH or CRITICAL findings under the build-tools scan policy. This establishes CVE-surface parity only. Documentation, reviews, issues, or implementation decisions MUST NOT claim that switching build-tools to Alpine inherently improves the currently measured HIGH/CRITICAL OS-package CVE surface or resolves tracked Debian CVE findings without new evidence. A complete post-fix rescan remains required before any stronger security conclusion is made.

The Debian stage MUST retain the project-wide `trixie-backports` configuration while Debian remains the default so its packaged tools remain current under the established Debian policy.

If Debian package availability or currency becomes a verified blocker for `build-tools`, Ubuntu or another current Debian derivative MAY be evaluated as an alternative. Such a fallback MUST be evaluated against the actual build-tools requirements and MUST NOT be selected solely from prior results obtained for another service.

The musl cross-compilation support already provided by the Debian build-tools stage for Rust builders such as `services/ui` and `services/dns` is independent of the build-tools base-OS decision. An Alpine build-tools image does not require an equivalent host-to-musl cross-compilation setup where its Rust host toolchain already targets musl natively.

Issue #1095 remains the tracking context for the build-tools base-OS decision. The completed evaluation in Issue #815 and related implementation work establish candidate feasibility but MUST NOT be treated as authorization to switch the default. Any change to the default build-tools base OS, active CI image, or corresponding image channel MUST receive explicit maintainer approval.

## Comment Style

- **[AG-CODE-001]** Code in this project must be human-readable, documented, and commented — this has been a core project tenet since its first design decisions, not a stylistic preference applied case-by-case. The default posture is to comment liberally, especially WHY-explanations for non-trivial logic (see AG-CODE-002), not to withhold comments until a case forces one. This is why AG-CODE-008's "you touch it, you comment it — entirely" rule exists: so nothing stays uncommented. The one thing NOT to do is restate what a well-named identifier or a trivial line already makes obvious (setting a variable, calling a function, reading a file) — that's noise, not documentation; see AG-CODE-002 for the WHY-vs-WHAT distinction this rule is actually about.

- **[AG-CODE-002]** Every non-trivial operation — especially anything with real-world side effects (file/data deletion, network calls, permission or ownership changes, state mutation, process control) — gets a `Why:` comment, regardless of how self-evident it looks to the person writing it. "This looks obvious" is not a reliable signal: a dangerous line and a safe line can read identically (e.g. `rm -rf "$dir"/*` reads the same whether `$dir` is guaranteed non-empty or not) — the risk lives in context the line itself doesn't show. Comment concrete cases where the WHY matters: complex logic, guards, fallbacks, security decisions, non-obvious side effects, a workaround for a specific bug, or a deliberate deviation from the obvious/standard approach. There is no "too obvious to need one" exemption.

- **[AG-CODE-006]** Code must stay human-readable. Silent or hard-to-follow changes are not acceptable — if a change needs explanation to be trusted, write the comment; don't ship it silently.

- **[AG-CODE-007]** Short structural/orientation comments that label the steps of a longer sequential procedure (e.g. `// Step 1: Fetch current config`, `// Step 2: Validate and normalize`) are also acceptable and encouraged, even when they don't explain a hidden WHY — they help a reader scan a long function without re-deriving its structure. Reviewers (including automated ones) must not flag this style as "unnecessary" or "restates the code" just because `Comment Style` otherwise favors minimal comments; readability-oriented step labels are a distinct, allowed category from WHY-comments, not a violation of this section.

- **[AG-CODE-008]** A missing comment is a defect too, not just a neutral default. When touching any part of a file, check the **entire file** — not only the specific lines you edited — for places that should already have a WHY-comment under the categories above (complex logic, a guard, a fallback, a security decision, a non-obvious side effect) but don't, whether the gap was missed originally or never added, and add it as part of the change. Do not leave the gap just because it predates your edit or sits outside your diff; "there wasn't one before" and "it's not part of what I changed" are not reasons to skip adding one now.

- **[AG-CODE-003]** Do not reference the current task, PR number, or fix in a comment (e.g. "fixed for #123", "added by the CR-9 pass"). That belongs in the PR/commit description, not in code that outlives the change. Exception: a bare `From: #N` pointer under Rule-Ref: AG-CODE-012's structured format is not a narrative task/fix reference and is permitted — the ban above targets phrasing like "fixed for #123" or "added by the CR-9 pass" woven into surrounding sentences, not a bare, structured pointer.

- **[AG-CODE-004]** When documenting a known limitation or deliberately deferred fix (not a bug you're fixing now), prefer a structured note over a one-liner: state the problem, the mitigation/fix direction if one exists, and a dated status line describing the current real-world state (e.g. "STATUS: as of 2026-07-02, X still uses the old path; once Y migrates, this fallback becomes dead code"). This lets a future reader tell a documented tradeoff apart from an accidental gap.

- **[AG-CODE-005]** Placeholder/scaffold markers (e.g. `TODO(#123): ...`) must be removed the moment the referenced work is actually implemented in that same change. A stale TODO claiming work is still needed, sitting next to code that already does it, is worse than no comment — it actively misleads the next reader/reviewer. Before finishing a fix that started from a TODO/scaffold marker, grep for and delete the marker it replaces.

- **[AG-CODE-009]** A descriptive identifier or name alone — including a `#[test]` function name — is not a valid comment. When the WHY behind a non-obvious edge case, security invariant, race condition, or off-by-one scenario isn't clear from the name, the reasoning must be spelled out explicitly: not what is being asserted (already visible in the code), but why this specific case would otherwise silently break something.

- **[AG-CODE-010]** For this project specifically, every `#[test]` function must carry at least a short comment explaining its purpose, regardless of whether the case looks "obvious" on its own. This project's domain (nginx/DNS/DHCP/Kea/Rust systems code) is complex enough that a bare test name is never sufficient on its own (see Rule-Ref: AG-CODE-001) — the same liberal, err-on-the-side-of-commenting standard applies to non-test code whenever in doubt.

- **[AG-CODE-011]** Before implementing or modifying any function, helper, check, variable, alias, configuration value, workflow mechanism, or equivalent capability, the agent MUST first perform a real search across the relevant repository scope and all applicable native capabilities, including language or runtime builtins, GitHub Actions contexts and expressions, existing configuration, shared helpers, scripts, workflows, and project-wide variables, for an existing implementation that provides the same or closely related behavior. Implementation or modification MUST NOT begin until this search has been completed. An existing capability MUST be reused or extended when it already satisfies or can reasonably satisfy the requirement; equivalent logic MUST NOT be reimplemented under another name, location, representation, or abstraction merely for convenience. This requirement applies at every scale, including functions, helpers, one-line aliases, variables, configuration flags, workflow jobs, checks, and small edits. Trivial size MUST NOT exempt a change from the search and reuse requirement. Duplicate implementations of the same capability MUST be treated as violations because they create independent maintenance paths and behavioral drift.


- **[AG-CODE-012]** Every code comment MUST use sober, factual language and MUST describe only the current state of the code. Comments MUST NOT contain storytelling, investigation history, verification narratives, timelines, discussion history, abandoned approaches, or descriptions of how a conclusion was reached. Comments written under this rule MUST follow a strict `What:` / `Why:` / `From:` structure, capped at 3 lines total. All three fields are mandatory (the `From:` field whenever a PR or Issue is known); a comment missing any one does not comply, and a second What/Why/From block MUST NOT be stacked for the same location — one location gets exactly one block. 
Every new or actively modified code comment governed by this rule MUST consist of exactly one `What:`/`Why:`/`From:` block.
`What:` is always mandatory. It MUST occupy exactly one physical line, MUST describe what the code currently does, and MUST contain at most 60 characters including the `What:` tag and separator.
`Why:` is always mandatory. It MUST occupy exactly one physical line, MUST state the actual non-obvious reason, constraint, invariant, workaround, or requirement for the code, and MUST contain at most 60 characters including the `Why:` tag and separator.
`From:` is mandatory whenever an applicable Issue or PR is known. It MUST occupy exactly one physical line, MUST contain at most one Issue and one PR reference, and MUST contain no explanatory text. The canonical form is:
`From: Issue #N | PR #N`
If only one applicable reference exists, only that reference MUST be used. References MUST be verified and MUST NOT be guessed or invented. `git blame` and the applicable Issue or PR history MUST be checked where necessary to establish the correct reference.
If neither an Issue nor a PR is known, the comment MUST contain exactly the two `What:` and `Why:` lines. `From:` MUST be added once a valid Issue or PR reference exists.
`From:` MUST identify only the current Issue or PR responsible for the current version of the commented code. It MUST NOT accumulate historical references. When a later change modifies the same code or comment, the previous `From:` reference MUST be replaced by the current applicable Issue or PR. Historical evolution and superseded references MUST be preserved in the applicable Issue, PR, commit record, or other durable work record rather than accumulated in the code comment.
One code location MUST contain exactly one `What:`/`Why:`/`From:` block. Multiple blocks for the same location, stacked blocks, continuation lines, wrapped `What:` or `Why:` text, or any other construction that expands the comment beyond the permitted structure MUST NOT be used. The maximum comment size is three physical lines when `From:` applies and two physical lines when it does not. This is a hard ceiling. The 60-character limits for `What:` and `Why:` apply to the complete physical line, including the field name, colon, separator, and content. They are maximum limits and MUST NOT be treated as target lengths. Information that does not fit within this structure MUST NOT be preserved by extending, wrapping, duplicating, or narrating inside the code comment. Substantive reasoning, investigation results, verification details, rejected alternatives, historical context, or other information that must be retained MUST instead be preserved in the applicable durable work record. During active work, such information MUST be recorded in a GitHub commit comment on the commit introducing the change when no more authoritative location already contains it. Before any applicable lifecycle transition, substantive information MUST be consolidated according to Rule-Ref: AG-WF-026. Rule-Ref: AG-CODE-003's prohibition on naming Issue or PR numbers in code comments MUST permit only the structured `From:` field defined by this rule. `From:` is a pointer to durable context and MUST NOT become a substitute for preserving substantive context in the applicable Issue, PR, commit record, or documentation. Whenever any file is modified, every comment in that file MUST be reviewed for compliance with this rule, regardless of whether the comment is related to the current task, the modified code, or the reason the file was opened. The entire modified file is the minimum comment-audit scope. Existing comments in a modified file that are malformed, outdated, factually incorrect, misleading, ambiguous, misspelled, grammatically defective, incorrectly referenced, narrative, oversized, duplicated, stale, structurally invalid, or otherwise non-compliant with this rule MUST be corrected in the same change. This requirement applies equally to comments in untouched or otherwise unrelated sections of the modified file. Existing comments MUST also be checked for correctness against the code they describe. A syntactically compliant `What:`/`Why:`/`From:` block MUST still be corrected when its meaning, reference, wording, or stated behavior is no longer accurate.  Multiple `What:`/`Why:`/`From:` blocks describing the same code location or the same underlying behavior MUST be consolidated into exactly one compliant block. Existing duplicate blocks MUST NOT be retained merely because they predate the current change. Stacking, splitting, preserving, or creating multiple blocks to retain additional text, historical information, or references, or to evade the physical-line or character limits, is prohibited. A known duplicate or intentionally split block used to circumvent this rule MUST be treated as deliberate evidence misrepresentation under the applicable evidence-integrity rule and MUST NOT be classified merely as a formatting defect. A modified file MUST NOT be declared compliant, complete, ready, or validated while any known comment violation governed by this rule remains anywhere in that file. Before implementing or modifying code governed by this rule, the agent MUST perform the reuse and duplication search required by Rule-Ref: AG-CODE-011. The search MUST cover the relevant repository scope and applicable native capabilities before implementation begins. The agent MUST record the following confirmation in the applicable Issue or PR and MUST NOT rely on chat as the only record:

`I confirm I did not violate AG-CODE-011 — I searched for <what was searched> and found no existing <function/helper/check/variable/mechanism> already doing <the job>, so I am implementing/modifying <what, and where>.`

If the Rule-Ref: AG-CODE-011 search discovers an existing duplicate, including one unrelated to the immediate task, the duplicate MUST NOT be silently ignored. If the required resolution is uncertain, the affected work MUST stop and the decision MUST be escalated to the maintainer before the agent decides whether or how to modify it.

Implementations MUST share a mechanism when a bug fix or behavior change to one copy would also need to apply to another copy to keep both correct. Code that is only superficially similar but intentionally represents independent behavior MAY remain separate under Rule-Ref: AG-CODE-006 and MUST NOT be forced into a shared abstraction solely because its structure appears similar.

- **[AG-CODE-013]** **Creating a new file carries a standing formal DISACK.** The DISACK applies by default and is independent of the reason offered for creating the file. Convenience, implementation speed, naming neatness, perceived separation of concerns, or an apparently legitimate special case do not lift it. No new file may be created — including provisionally, temporarily, or as part of an implementation experiment — until the checks below have been completed. The DISACK is lifted only when: (a) an existing file is identified as the appropriate home and is extended instead; or (b) the required consolidation/search checks have been completed and documented, no suitable existing home exists, and an explicit maintainer/coordinator ACK for the new file has been obtained before the file is created. Reasoning that a new file "makes sense" is not an ACK and does not substitute for the required checks.

  **Required checks.** Before creating any new script, library, test-suite file, or other monolith-capable implementation file: search the same directory and related implementation area for files covering the same conceptual capability or lifecycle; determine whether the proposed behavior can be added to an existing file through a function, option, flag, subcommand, case dispatch, reusable helper, or additional test case; check whether two or more existing files already implement variants of the same operation and should be consolidated instead of adding another member to the family; search for duplicated or near-duplicated setup, validation, cleanup, argument parsing, resource discovery, logging, error handling, comments, or control flow (duplication is evidence that consolidation or shared implementation is required); check currently open issues and PRs for another consumer of the same not-yet-built capability, and if multiple consumers need it, implement the capability once and have them reuse it. State the result of this check in the implementation/PR — a silent or implicit check does not satisfy this rule.

  **How to decide whether files belong to the same conceptual class.** Files should normally be treated as candidates for consolidation when they operate on the same resource or lifecycle and differ primarily by: execution mode (`--dry-run`, `verify`, `apply`, `delete`, `retire`); policy or safety level; filtering or selection criteria; environment or target; phase of the same operator workflow; small variations in otherwise shared control flow; duplicated setup, validation, cleanup, or reporting logic. For example, `prune-old-dry-run.sh` / `prune-old-verify-before-delete.sh` / `prune-old-delete.sh` should normally become one cohesive `prune-and-retire.sh --dry-run` / `--verify` / `--delete`, with shared internal functions rather than copied implementations.

  **Consolidation requirements.** Extend an existing file whose established responsibility already covers, or is the closest conceptual owner of, the capability — regardless of whether that file is formally organized as a library, a script, a test suite, an action, or any other implementation file, and even if its name is not a literal match for the new behavior; this is the default expectation, not a special case reserved for files labeled as libraries. Prefer flags, options, subcommands, functions, or case dispatch over sibling files. Implement shared behavior exactly once. Treat a growing family of near-identical standalone files as evidence of an existing design problem to correct, not as precedent for creating another one.

  **Do not:** create a new file because doing so is easier than understanding or extending an existing implementation; create a new file merely because the new behavior has a distinct name; create `*-dry-run`, `*-verify`, `*-cleanup`, `*-delete`, `*-simulation`, or similar sibling scripts when those are modes or phases of the same underlying capability; copy an existing file and modify it into a new variant; duplicate functions, boilerplate, comments, parsing, validation, cleanup, or error handling between sibling implementations; evade this rule by moving file sprawl from `scripts/` into `scripts/lib/`; create one library file per helper function unless the file type or framework structurally requires such decomposition; create the file first and request ACK afterward; interpret an existing family of fragmented files as justification for adding another — evaluate the family for consolidation first.

  **Cohesion constraint.** This rule requires consolidation of the same conceptual capability, not arbitrary monolithization. Unrelated responsibilities must not be forced into the same file merely to reduce file count. The objective is one coherent implementation per capability, with internal reuse — not one tiny file per variation, and not one unrelated god-file containing everything.

  **File-type exception.** The consolidation preference applies where a file type naturally supports internal reuse and dispatch, such as shell scripts and Bats suites. It does not require artificial consolidation where the native composition model of the format uses separate units. GitHub Actions composite actions are an example: directory-per-action plus `uses:` composition is the native reuse mechanism. Combining unrelated composite actions into one condition-heavy YAML file would replace structural reuse with declarative branching and is therefore not required by this rule.

Stop and request a maintainer/coordinator decision. Absence of certainty is not permission to create the file.

  ```
                  DISACK     ACK --> New file permitted
                  stands
  ```

  **Enforcement interpretation.** The default state is always `NEW FILE = DISACK` until the required search/consolidation process proves that no appropriate existing home exists and a maintainer/coordinator explicitly changes that state to `NEW FILE = ACK`. A plausible reason, architectural preference, implementation convenience, issue scope, agent judgment, or statement that a file is "cleaner" or "more modular" never changes the state by itself.

## File Headers

- **[AG-HDR-001]** Every source/config file (Rust, shell, YAML, Dockerfiles, `.conf`/template files, HTML/CSS/JS) in scope for repository headers uses one canonical physical three-line prefix. Physical line 1 is either a genuinely required interpreter/parser marker, for Rust exactly the bare `//!` inner-doc placeholder required to keep the three-line contract formatter-stable, or otherwise intentionally blank. Physical line 2 contains the literal project form `LanCache-NG (https://github.com/wiki-mod/lancache-ng)` in the native comment syntax valid for that file. Physical line 3 contains `SPDX-License-Identifier: AGPL-3.0-or-later` using the same native comment syntax. Existing file-purpose documentation follows this fixed prefix and is not displaced or removed merely to satisfy the three-line contract. `scripts/tracked/check-file-headers.sh` enforces the exact capitalization, physical positions, native syntax, and uniqueness of the project/SPDX lines.
  - Rust: physical line 1 is exactly bare `//!`; lines 2 and 3 are `//! LanCache-NG (https://github.com/wiki-mod/lancache-ng)` and `//! SPDX-License-Identifier: AGPL-3.0-or-later`. The bare inner-doc line is the formatter-stable placeholder for the otherwise empty first line; a physical blank line is not canonical because `rustfmt` removes it.
  - Shell, Bats, YAML, Dockerfiles, TOML, PowerShell, systemd units, and genuinely plain-text `.conf`/template/config files: `#` line comments on lines 2 and 3. A shebang or supported required parser directive may occupy line 1; otherwise line 1 stays blank.
  - HTML Tera templates under `services/ui/src/templates/`: complete standalone Tera comments, exactly `{# LanCache-NG (https://github.com/wiki-mod/lancache-ng) #}` on line 2 and `{# SPDX-License-Identifier: AGPL-3.0-or-later #}` on line 3. Do not use a raw HTML `<!-- ... -->` comment there: Tera comments are safe before an `{% extends ... %}` tag, while ordinary HTML content before `extends` can break template loading. Existing Tera purpose-comment blocks follow the fixed prefix.
  - Other HTML: `<!-- ... -->` comments.
  - CSS (`.css`): `/* ... */` comments.
  - JavaScript (`.js`): `//` line comments.
  - Lua (`.lua`): `--` line comments.
  - If a file language is not listed here, use that language's own standard comment syntax only after confirming it is valid for the real parser; never default to `#` merely from the filename.
  
- **[AG-HDR-002]** Before adding a header to any file with a `.conf`/`.json`/`.txt`/other generic-looking extension, check what actually parses it and how. If the content is genuinely JSON (JSON has no comment syntax at all), do not add any header; a `#` or any other comment line would break parsing. In this repo, all three Kea config files under `services/dhcp/` are JSON despite the `.conf` extension and must be excluded on this basis: `kea-dhcp4.conf` (parsed by `migrate_dhcp4_config` in `services/dhcp/entrypoint.sh`), `kea-ctrl-agent.conf`, and `kea-dhcp-ddns.conf`. The same JSON exclusion applies to any other file this project treats as machine-parsed structured data without a comment syntax, whatever its extension.

- **[AG-HDR-003]** Do not add a header to a file whose entire content is consumed as a single raw value by a strict parser, where any extra text (including a comment) would corrupt that value. The clearest example in this repo is the root `VERSION` file: `setup.sh`'s `derive_current_release_image_tag` reads the whole file, strips whitespace, and requires the result to match a release-tag pattern — a header would be concatenated into that value and break setup/update with an invalid release image tag.

- **[AG-HDR-004]** Do not add a header to a vendored third-party file or a generated/compiled build artifact — it isn't this project's own hand-authored source, and in the vendored case it likely already carries its own upstream header. In this repo: `services/ui/src/static/chart.umd.min.js` is the vendored, minified Chart.js library (already opens with its own `/*! Chart.js v4.5.1 ... */` header) and `services/ui/src/static/admin.css` is compiled/minified Tailwind CSS output, not hand-written CSS. `services/proxy/public_suffix_list.dat` is the vendored Mozilla Public Suffix List (already opens with its own `// This Source Code Form is subject to the terms of the Mozilla Public License, v. 2.0` header), used at proxy startup to derive each CDN domain's registrable root for wildcard cert coverage. If a hand-written source input for a generated artifact is ever added to the repo (e.g. a Tailwind config or an unminified source file), that source input is in scope for a header; the generated output it produces is not.

- **[AG-HDR-005]** Scale the header's detail to the file's actual complexity — a file with several distinct responsibilities (e.g. a multi-role entrypoint script, a large route-wiring module) should name them; a simple, single-purpose file (e.g. an install-and-copy Dockerfile) should stay short. Do not pad a simple file's header just to match a fixed line count.

- **[AG-HDR-006]** Every technical claim in a header must be verified against the actual file content and, where relevant, git history — do not assert an unconfirmed reason for a design choice (e.g. why a particular base image or repo is used) if no documented rationale exists; state the observable fact instead.

- **[AG-HDR-007]** File-header enforcement MUST exclude `.md` files, the literal root-level `.env` and `.env.example` files, lockfiles such as `Cargo.lock`, `.gitkeep`, the root `VERSION` and `LICENSE` files, vendored or generated build artifacts, and any JSON or other comment-free structured file regardless of extension. Other files ending in `.env`, including committed service configuration such as `config/prod/dhcp.env`, MUST remain in scope. `scripts/tracked/check-file-headers.sh` and its `is_excluded()` function MUST remain the executable authority for the exact exclusion set. The root `LICENSE` file MUST remain unmodified because prepending a repository header can break license recognition by tools such as GitHub license detection and SPDX scanners; Rule-Ref: AG-HDR-008 governs the license content itself.

- **[AG-HDR-008]** The repository MUST use the GNU Affero General Public License v3.0 or later (`AGPL-3.0-or-later`), with the authoritative license text stored unchanged in the root `LICENSE` file. Every file in scope under Rule-Ref: AG-HDR-001 and Rule-Ref: AG-HDR-007 MUST place `SPDX-License-Identifier: AGPL-3.0-or-later` on physical line 3, immediately after the canonical `LanCache-NG (https://github.com/wiki-mod/lancache-ng)` project header on physical line 2, using the file's native comment syntax. `scripts/tracked/check-file-headers.sh` MUST hard-enforce this contract in both explicit-file and whole-repository modes. No soft, informational, transitional, or backfill exception remains.

- **[AG-HDR-009]** The repo-wide canonical header backfill is complete. `scripts/tracked/check-file-headers.sh` runs in CI and fails when any non-excluded tracked file is missing the required three-line prefix, places the canonical project/SPDX lines on the wrong physical lines, duplicates either line, or retains the legacy lowercase `lancache-ng (...)` project form. - **[AG-VAL-024]** Creation of any new shell script remains subject to the formal DISACK and approval requirements of Rule-Ref: AG-CODE-013. When creation is authorized, the script's committed executable state MUST NOT be inferred from local filesystem permissions, `chmod +x`, or successful local execution on Windows or any environment where Git uses `core.filemode=false`, because those environments may not expose or modify the executable bit stored in the Git index.
New shell scripts SHOULD be invoked through an explicit interpreter, such as `bash "$script"`, at every call site, including test harnesses, instead of through `"$script"` or `./script.sh`. This SHOULD be preferred whenever direct execution is not technically required because it removes the executable-bit dependency. If any call site requires direct execution, the committed Git mode MUST be verified explicitly with `git ls-files -s <path>` and MUST report mode `100755`. Local `chmod`, filesystem mode inspection, local execution, or other host-local observations MUST NOT substitute for this Git-index verification. A script committed as `100644` MUST be treated as non-executable even if its contents and logic otherwise validate correctly; direct execution on Linux can fail with `Permission denied` and exit status `126`. Any shell failure path whose behavior depends on `set -e`, `set -u`, `pipefail`, pipelines, or command exit status MUST be verified by executing the actual failure condition under the same shell-option semantics used by the real caller. In particular, commands such as `grep` or pipelines that legitimately return a non-zero status for an expected condition MUST NOT be allowed to terminate execution through `errexit` before the intended fail-closed diagnostic or handling branch is reached.A fail-closed branch MUST therefore be exercised with actual failing input in real applicable CI, not only inspected or reasoned about statically. Verification MUST demonstrate that execution reaches the intended failure-handling path, emits the intended diagnostic, and returns the intended non-zero status. Static walkthroughs or successful-path tests alone MUST NOT be accepted as proof of fail-closed behavior.

## Documented Exceptions to Hard Rules

Hard rules in this governance exist to prevent real failures — runtime crashes, security exposures, documentation drift, stale CI gates, and cascading operational risk. A rule must be clearly broken only when there is a documented reason, and exceptions must state that reason explicitly, name what still must be validated despite the exception, and be narrowly scoped.

- **[AG-DOC-011]** Every documented exception must follow this format:

- **Scope**: What the exception narrows (e.g., "Rust builder images for service X" or "CodeQL analysis for auto-generated code in path Y").
- **Reason**: Why the normal rule does not apply in this case (e.g., "generator output is deterministic and pre-audited," or "this image must use rust:latest because...").
- **Tracking**: Issue and/or PR reference where this exception was discussed and approved.
- **Validation**: What validation is still required despite the exception. Omitting validation because "the exception lets us skip it" misses the point — the exception narrows the rule, but safety verification must land somewhere else.
- **Non-Expansion**: What the exception explicitly does NOT cover (e.g., "this exception applies only to service X, not to other services" or "only to CodeQL analysis, not to other security checks").

### [AG-VAL-021] Second, distinct case: CodeQL findings in actually macro-generated code (issue #394, closed)

This is a separate case from Rule-Ref: AG-VAL-022 above, not an unreconciled restatement of it. That rule covers extraction *warnings* CodeQL's Rust extractor emits for ordinary, human-authored macro *invocations* (`format!`, `vec!`, ...) — confirmed to be a pure tooling artifact, tracked upstream as [github/codeql#19966](https://github.com/github/codeql/issues/19966), [#19982](https://github.com/github/codeql/issues/19982), and [#20659](https://github.com/github/codeql/issues/20659) (CodeQL's Rust support is `rust-analyzer`-based and cannot cleanly expand macros, especially procedural ones, without running the real compiler; all three remain open upstream with no fix commitment). PR #517 made this extraction-quality signal visible instead of leaving CI silently green. This exception instead covers real CodeQL *findings* ("overly complex", "unreachable") in code a macro actually *generates* — since that code is genuinely unusual, not just misread by the extractor, "it's just a tooling artifact" is not sufficient justification by itself; this exception additionally requires test evidence the generated code behaves correctly despite the finding.

- **Scope**: CodeQL analysis of Rust code generated by macros that expand to large intermediate representations.
- **Reason**: Rust procedural macros can generate code that CodeQL reports as overly complex or unreachable, even though the actual compiled binary and test behavior are correct. The generated code is not human-readable and is not part of the reviewable source surface. Blocking on CodeQL false positives in generated code delays legitimate security fixes.
- **Tracking**: issue #394 (closed — see the intro above for the upstream bug references this closure rests on). This exception was approved as part of the v0.2.0 security hardening pass.
- **Validation**: CodeQL analysis must still run on human-written code. The exception narrows which CodeQL findings are treated as blocking. A CodeQL exception pull request must demonstrate that the finding occurs in generated code (not human-authored code), that the finding is a known false positive for macro expansions, and that the relevant code path has test coverage that proves the behavior is correct despite the CodeQL report.
- **Non-Expansion**: This exception applies only to CodeQL Rust analysis. It does not cover other languages, other security checks (e.g., cargo-audit, SAST linters), or changes to non-generated Rust code. It also does not extend the plain-extraction-warning exception in Rule-Ref: AG-VAL-022, which covers warnings on ordinary macro invocations needing no test-coverage evidence since they are a confirmed tooling artifact unrelated to actual code behavior.

## Agent Closing-Report Contract

- **[AG-WF-041]** Finishing any nontrivial task, including any PR, issue fix, or multi-step verification, MUST include a closing report that demonstrates understanding of the work and its context, not merely execution of instructions. The report MUST be recorded in the applicable PR body, closing Issue or PR comment, or final task output. Its location MAY vary by context, but the required content MUST NOT.

The closing report MUST explicitly identify every Issue, PR, design document, relevant existing code area, threat model, governance document, or other source actually read to understand the task scope. Generic statements such as I read the issue, reviewed the documentation, or equivalent acknowledgements MUST NOT satisfy this requirement.

The closing report MUST identify the exact files, paths, components, or subsystems modified and describe the affected areas specifically enough for a reviewer to determine what was changed.

If the task description, Issue or PR context, investigation, or surrounding implementation identifies related work or areas that could reasonably require corresponding changes but were deliberately left unchanged, the closing report MUST identify each such area and state why it was not changed. This requirement applies whether the exclusion results from scope, separate ownership, another tracking item, an intentional technical decision, or another justified boundary. Related work MUST NOT be silently omitted in a way that makes it impossible to distinguish a deliberate boundary from work that was overlooked.

Every validation command actually executed MUST be reproduced exactly in the closing report together with its real observed result. The report MUST include the applicable exit status and relevant findings, warnings, failures, corrections, or other material output needed to understand the result. Generic statements such as ran tests, tests pass, validation succeeded, or equivalent summaries without the actual command and result MUST NOT satisfy this requirement.

Every validation check that would normally apply but could not be executed MUST be identified explicitly together with the reason it was not run, including conditions such as unavailable Docker, unavailable toolchains, environment limitations, or CI-only validation. The closing report MUST distinguish unambiguously between checks that passed, checks that failed, and checks that were not run. A skipped, unavailable, blocked, or unexecuted check MUST NOT be reported or implied as passed.

The closing report MUST explicitly identify every known open risk, incomplete or partial implementation, outstanding dependency, unresolved limitation, accepted exception, pending verification, or follow-up condition known at task completion. Known outstanding work MUST be disclosed rather than omitted in a way that implies the task is fully shipped or fully verified.

Relevant documentation MUST be checked for drift against the resulting implementation under Rule-Ref: AG-DOC-001. This review MUST include all documentation relevant to the changed behavior, including applicable README.md, threat models, architecture documentation, setup documentation, release documentation, and other behavior-defining documentation. The closing report MUST identify what documentation was checked, whether it remained correct, what was updated when drift was found, and whether any known drift remains. If relevant documentation was not checked or was deliberately not updated, the closing report MUST state that explicitly and provide the reason, including the applicable tracking reference when the work is intentionally handled elsewhere.

The closing report MUST identify every follow-up Issue, PR, dependency, or task created by or required for the completed work. If no follow-up work is required, the report MUST explicitly state no follow-up required. Absence of a follow-up reference or statement MUST NOT be treated as equivalent to confirming that no follow-up exists.

This contract is stricter than the overlapping sections of .github/pull_request_template.md. Existing template headings MAY be used to carry the required information, but completing those headings with vague, generic, incomplete, assumed, or placeholder content MUST NOT satisfy this rule. Closing-report content MUST be real, specific, current, and honest, including all validation gaps, failed or skipped checks, deliberate scope exclusions, documentation drift, known risks, unresolved work, and follow-up requirements.

## Agent Autonomy and User-Context Rule

- **[AG-WF-015]** The user of this repository is not a heavy skilled software programmer. This is a deliberate operational constraint, not a gap to work around. See also Rule-Ref: AG-WF-023. Do not assume just by chatting, an ACK or DISACK for your conversation, ask if this is an ACK or DISACK.

- **[AG-WF-023]** Agents and tools working on this repository must make technical decisions independently and must only ask for guidance when a choice has real operational impact such as hardware selection, network topology, cost implications, or time-to-value tradeoffs — not when the correct technical decision is determinable from code, documentation, and governance alone.

An example of a decision that agents should make independently: "The code changed from BIND9 to PowerDNS; should I update the threat model?" Answer: yes, update it. The code change determines the answer, not user preference.

An example of a decision that requires guidance: "The proposed optimization would increase cache RAM from 10GB to 50GB; is that acceptable for this operator's network?" Answer: ask. The hardware impact depends on the operator's deployment context, not the code alone.

When in doubt, prefer making the decision. The governance and code provide strong signals. This rule exists to keep workflows efficient and prevent decision-delegation bottlenecks on matters that are technically determinable.
