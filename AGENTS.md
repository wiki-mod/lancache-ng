# lancache-ng — Repository Governance

**Project**: lancache-ng — a local download cache for home networks, LAN parties, labs, schools, offices, or gaming rooms. Stores game/software downloads locally so repeat downloads on the LAN run at LAN speed instead of re-fetching from the internet. Adds SSL interception (MITM via a custom CA) and full IPv6 dual-stack support on top of the original lancachenet concept.
**Repository**: https://github.com/wiki-mod/lancache-ng
**See also**: `CLAUDE.md` (Claude Code project instructions, auto-loaded every session) exists solely to point Claude Code sessions at this file at session start (Rule-Ref: AG-GOV-001) — architecture and setup content lives here, in this file, not there; `README.md` for end-user-facing documentation.

This file contains repository-wide agent rules. It applies to all paths in this repository, including `.github/**`, `setup.sh`, `deploy/**`, `config/**`, `scripts/**`, and `services/**`.

## Rulebook Interpretation

**[AG-LAW-001]** AGENTS.md is a single, unified rulebook. All applicable rules apply simultaneously to every affected part of the project and to the change as a whole. Compliance with the rule that motivated a change does not establish overall compliance. Any touched file, asset, generated output, project behavior, or other affected part of the project must be checked against every applicable rule in this document. A task must not be declared complete until all affected parts and the complete change have been checked against every applicable rule in AGENTS.md. Declaring a task complete after verifying only one or some applicable rules is itself a violation of this rule, even if those specific rules were satisfied.

**[AG-LAW-002]** In every maintainer-visible conversational message under Rule-Ref: AG-CC-002, any time that is stated or displayed must be given in Berlin local time (`Europe/Berlin`). The seasonally correct timezone abbreviation must be used — `CEST` during daylight saving time, `CET` during standard time — placed immediately after each time value, e.g. `14:30 CEST` or `09:15 CET`. A time given without a timezone abbreviation, or a fixed UTC offset used in place of `Europe/Berlin`, is not permitted. Time values from GitHub APIs, host/session clocks, logs, or any other external source must be converted to `Europe/Berlin` before being stated to the maintainer. This rule applies to all maintainer-visible chat, reasoning, status, progress, and comparable conversational messages; non-visible internal reasoning and raw, unprocessed API/machine data are exempt. This rule is additive to Rule-Ref: AG-CC-002 — the required language remains German. A session must never trust its own timezone resolution (e.g. a locally set `TZ` environment variable, or a tool's default) without verifying it against an independent source — such as the host operating system's own configured timezone setting, or a separate trusted clock — before stating a time to the maintainer; a tool that silently falls back to the wrong timezone without raising an error is exactly the failure mode this verification step exists to catch. *Origin (2026-08-22): a session stated a loop's end time using the session host's own local clock without converting it to Berlin time, producing a real ~2 hour discrepancy in a stated deadline. A later same-day incident confirmed the verification requirement above is not hypothetical: a session's `TZ=Europe/Berlin`-prefixed shell command silently fell back to the wrong timezone with no error raised, because the shell environment had no system timezone database at all, and only a cross-check against a second source (the host OS's own configured timezone) caught it.*

## Known Gaps and Planned Improvements

- **AG-CI-022 real-secret wiring gap -- closed (2026-08-26, issue #1095):** the gap this note originally described (`build-push.yml` never actually populating the `ccache_redis_url`/`ccache-redis-file` secret for `services/dns`/`services/ui`, despite both Dockerfiles supporting the layer since #1533) is fixed: the generic "Prepare Rust acceleration secret files" step now produces `ccache-redis-file` for every `matrix.rust == true` service, the preflight reads it from that single source, and `services/watchdog/Dockerfile` was added as a third supported consumer in the same pass. Confirmed live via a real CI run with all three services' builds green. Retained here (not deleted) as the historical record of the incident this rule's own Rule-Ref: AG-CI-022 text still cites.
- **AG-CI-022 assessment (2026-08-22, issue #1095/G15, PR #1640): no fallback caching layer exists for `services/dns`'s ccache-over-distcc path when `CCACHE_REDIS_URL`/`ccache_redis_url` is absent or unreachable (e.g. the GitHub-hosted fallback path under Rule-Ref: AG-CI-003, where the LAN Redis instance is never reachable at all).** `configure_ccache()` in `services/dns/Dockerfile` checks `[ -s /run/secrets/ccache_redis_url ]` before doing anything else; if that secret is empty, it returns immediately and the build falls back to plain distcc (or a local compile) with zero caching for the ccache-fronted compile path -- not degraded caching, none at all. The maintainer asked whether `actions/cache` (GitHub Actions' own built-in cache action) could back-fill this by persisting ccache's local `CCACHE_DIR` disk cache across runs instead. Investigated and found **not cleanly integrable given this repo's current build architecture**, for two independent, concretely-verified reasons rather than a general assumption: (1) `CCACHE_DIR=/tmp/ccache-dns` (set inside the single `RUN --mount=type=secret,...` instruction that drives the whole compile) is a bare path inside that instruction's own ephemeral BuildKit build-stage filesystem -- it is never backed by a `RUN --mount=type=cache` mount today, so nothing about it survives even to the next layer of the same build, let alone the next CI run; `actions/cache`'s `path:` input can only snapshot paths that exist on the runner host's own filesystem, and this path never does. (2) Making `CCACHE_DIR` a real `--mount=type=cache` mount would not fix this either: BuildKit's cache-mount store lives inside the buildx builder's own internal state, entirely separate from the `type=local`/`type=gha` layer-cache exporters this repo already uses (`build-push.yml`'s main per-service `build` job: `cache-from: type=local,src=...` / `cache-to: type=local,dest=...,mode=max` against `/var/tmp/lancache-ng-buildx-cache` on the self-hosted runner; the `build-arm64` job: `cache-from/to: type=gha,scope=...`) -- neither exporter captures cache-mount contents, only image layers. Worse, every one of these jobs runs a "Remove buildx builder" step (`docker buildx rm ...`) unconditionally after each build, which destroys that builder's entire internal cache-mount store regardless, so even a hand-rolled cache-mount would not survive to the next run without also reworking the builder teardown lifecycle. This is even more clear-cut on the specific Rule-Ref: AG-CI-003 GitHub-hosted fallback path itself (`.github/workflows/build-push-hosted-fallback.yml`, `runs-on: ubuntu-latest`, `dns` included in its service matrix, confirmed to wire no `ccache`/`sccache`/`distcc` secret of any kind -- exactly the Redis-absent scenario this gap describes): that workflow already uses `cache-from/to: type=gha` and its own "Remove buildx builder" step, and since `ubuntu-latest` is itself a fresh, fully ephemeral VM destroyed after the job regardless, nothing on its filesystem (a cache mount included) would survive to a later run even without that explicit teardown step. The only real bridge for this class of problem (BuildKit cache-mount contents <-> `actions/cache`) is a third-party action such as `reproducible-containers/buildkit-cache-dance`, which would be a new external dependency requiring its own pinning and an AG-REL-001-adjacent maintainer review for what is only a fallback-path nicety (it never helps when Redis is present and healthy, which is the common case) -- not implemented here; left as a structured decision for the maintainer (see PR #1640) rather than added unilaterally. Documented here as a genuine, intentionally-not-closed gap per this section's own purpose, not silently left absent.
- **AG-DOC-001** (Documentation drift): No automated script yet checks whether docs match code. This is a manual review burden. A future CI job could parse documentation headers, extract key terms (e.g., "PowerDNS," "Admin UI authentication required," "console domains excluded from DNS"), and compare them against corresponding code values. - **AG-VAL-029 assessment (2026-08-08, issue #1095, second instance this same pass): a fail-closed helper function's `$(...)` call embedded directly inside a larger command's argument list (`printf '...%s\n' "$(helper)"`, `echo "...$(helper)..."`) instead of assigned to its own variable first.** Under `set -e`, `var="$(helper)"` alone propagates `helper`'s failure (the assignment's own exit status IS the substitution's), but `printf`/`echo`'s exit status does not depend on a failed substitution buried in one of their arguments -- the enclosing command still reports success, so `set -e` never fires, and a caller reading its own `set -e` as sufficient protection is wrong for this specific shape. Two real, independently-found instances in the same PR: `scripts/lib/validation-image-tag.sh`'s `vit_resolve_tag()` (`printf 'pr-%s-sha-%s\n' "$pr_number" "$(dmeta_short_sha "$build_sha")"`) and `.github/workflows/build-push-hosted-fallback.yml`'s "Resolve short commit SHA" step (`printf 'value=%s\n' "$(dmeta_short_sha "$GITHUB_SHA")" >> "$GITHUB_OUTPUT"`) -- both fixed by hoisting to a dedicated local/variable assigned first and checked explicitly (`... || return 1` / relying on the now-bare assignment's own `set -e` propagation). A third, related shape -- a bare assignment with no embedded call, but also no explicit `||` check, inside a file with no top-level `set -e` at all (`scripts/lib/staging-ancestor-fallback.sh`'s own header explains why: its functions must fail closed via their own checks, not a caller's shell options) -- surfaced three more times in the same sweep (`base_sha_short`, two `ancestor_sha_short` sites) and got the same explicit-`||`-check treatment. A repo-wide mechanical guard for "any fail-closed helper call embedded inside another command's arguments, anywhere" was considered and not attempted: the class is defined by call-site shape (embedded vs. bare-then-checked), not by a fixed set of function names, so a name-based regex would miss every future helper introduced after the guard is written, while a shape-based one (anything matching `$(\w+ ...)` nested inside another command's arguments) would flag the overwhelming majority of ordinary, harmless command substitutions in this codebase -- the same "denylist is incomplete, broad-shape guard is mostly noise" tension AG-VAL-028 already names for the sibling gap immediately below. A sweep of every call site of the specific helpers introduced by this same PR (`dmeta_short_sha`, `dmeta_ghcr_repo`) found no further live instances beyond the six fixed here (confirmed via `git diff origin/current_dev...HEAD | grep '^+' | grep -E '\$\((dmeta_|vit_|saf_|sif_)'`) -- but that grep was scoped to four helper-name prefixes and could not see the same call-site shape against an unrelated helper. A live seventh instance (`.github/workflows/build-push.yml`'s "Select immutable build-tools image" step, `printf 'BUILD_TOOLS_IMAGE=%s\n' "$(... bash scripts/select-build-tools-image.sh)" >> "$GITHUB_ENV"`, five identical occurrences) surfaced for real in this PR's own CI on 2026-08-14 -- `select-build-tools-image.sh` failed (no published image satisfied its smoke check yet for a fresh commit), the embedded substitution's failure was swallowed by `printf`'s own exit status exactly as this note describes, and `BUILD_TOOLS_IMAGE` landed empty in `$GITHUB_ENV`, turning a clear "image not ready" condition into a cryptic `docker: invalid reference format` on every later docker-dependent step. Fixed the same way as the other instances (hoist to a local, printf reads the local). An eighth, sibling instance of the identical shape (`.github/workflows/orphaned-branches.yml`'s own `select-build-tools-image.sh` call) was found by the same grep widened to the literal script name, but is a different, untouched workflow outside this PR's own scope -- left unfixed and flagged rather than silently expanded into. This stays manual-review-only for now, governed by Rule-Ref: AG-VAL-030's own general executed-proof requirement for any `set -e`/`$?`-dependent construct, rather than a new standing check; a repo-wide grep for `printf .*=%s.*"\$(` piping into `$GITHUB_ENV`/`$GITHUB_OUTPUT` would be a cheap starting point for a future check, since this exact shape has now recurred twice.

- **AG-VAL-029 assessment (2026-08-08, issue #1095): a `scripts/lib/*.sh` file that is genuinely sourced elsewhere setting a bare, non-`local` top-level variable that collides with a caller's own identically-named variable.** A real instance of this confirmed a live CI failure (`scripts/lib/validation-image-tag.sh`'s self-sourcing of the new `scripts/lib/docker-metadata.sh` clobbered `scripts/plan-deep-validation.sh`'s own `script_dir`, see that fix's own commit for the full incident), fixed by resolving the path inline with no named variable at all. A mechanical guard for this was attempted (a function-depth-tracking scan of `scripts/lib/*.sh`, scoped to files this repo actually sources via the established `# shellcheck source=` marker convention) and rejected before landing: run against the real tree, it flagged a dozen already-established, safe top-level assignments in `build-retry.sh`/`docker-buildx-retry.sh`/`ghcr-retry.sh`/`promote-lock.sh`/`quickstart-compose-lock.sh` -- each a uniquely-namespaced configuration constant (e.g. `GHCR_RETRY_MAX_ATTEMPTS`) with negligible real collision risk, not the generic, commonly-reused variable name (`script_dir`) that made the real incident possible. Distinguishing "a uniquely-prefixed constant" from "a generic, high-collision-risk name" is exactly the kind of judgment call AG-VAL-028 already names as resisting cheap, reliable mechanical detection -- a denylist of "risky" names would be incomplete and arbitrary, and flagging every bare top-level assignment produces enough noise to bury the one real risk shape among many safe ones. This class stays manual-review-only for now: when adding a self-sourcing line to any `scripts/lib/*.sh` file, resolve the sourced path inline with no named variable (see `scripts/lib/validation-image-tag.sh`'s own self-sourcing line for the pattern) rather than introducing a new top-level variable at all, sidestepping the judgment call entirely rather than needing a check to catch it after the fact.

- **AG-GH-008**: Enforced by `scripts/tracked/check-pr-tracking-metadata.sh`, run as the `pr-tracking-metadata-check` job in `build-push.yml` and gating the `build`/`build-arm64` jobs on pull requests, the same way `pr-template-check` does. It reads labels and milestone directly from the pull-request webhook payload (no extra permissions needed) and fails a non-draft PR missing either. Runs inside the pinned build-tools container (per AG-VAL-016), same as `shellcheck`/`check-governance-guards.sh`, since the script depends on `python3` and `curl`, which must not be treated as guaranteed present on the runner host. The project-board sub-check additionally requires a `PROJECT_AUTOMATION_PAT` repository secret (a classic PAT with the `project` scope) because the default `GITHUB_TOKEN` cannot read or write Projects v2 data for an org-owned board; without that secret configured, the project-board sub-check is skipped with a warning rather than failing the job. This also happens unconditionally for pull requests from forked repositories: GitHub does not pass repository secrets (other than the read-only `GITHUB_TOKEN`) to `pull_request`-triggered runs from forks, so `GH_TOKEN` is empty there even once `PROJECT_AUTOMATION_PAT` is configured for same-repo PRs. The check is told which case it's in via a `PR_IS_FORK` flag computed by the workflow (comparing head/base repo full names) and warns with the correct explanation either way; labels and milestone, read from the webhook payload rather than a secret, are still fully enforced for fork PRs. This is treated as an accepted limitation rather than something to work around with `pull_request_target`: that trigger would need to apply to this entire monolithic workflow (`needs:`-based job gating only works within one workflow file, so the check can't move to a separate `pull_request_target` workflow without losing the ability to gate `build`/`build-arm64`), and `pull_request_target` combined with checking out and building fork-supplied code (as `build-push.yml`'s other jobs do) is a known secret-exfiltration risk this repo does not take. A maintainer must add fork PRs to the project board manually regardless, since external contributors cannot write to an org-owned Projects v2 board themselves. If a token IS configured but is rejected (HTTP 401/403) or the GraphQL response itself carries an `errors` array (expired/revoked/insufficient-scope token), the check fails the job instead of warning -- that is a configuration bug in the secret, not the documented absent-token gap, and warning there would silently disable the project-board gate for the exact misconfiguration case this enforcement exists to catch. `.github/workflows/add-to-project.yml` (using the same secret) and `.github/workflows/labeler.yml` (path-based auto-labeling, no secret needed) reduce how often labels/project placement need to be set by hand in the first place. Dependabot PRs used to be exempted from this whole check outright (`PR_AUTHOR == "dependabot[bot]"` short-circuited to an explicit pass, #1061-#1064) because Dependabot cannot set its own milestone or add itself to the project board; that exemption was removed (issue #1278) once it became clear labels and project-board placement were already handled for Dependabot PRs without it (GitHub's own dependency labels plus `labeler.yml`'s path-based labels; `add-to-project.yml`'s unconditional `pull_request_target` trigger), and a new "Auto-assign Dependabot PR milestone" step was added to `pr-tracking-metadata-check`/`-hosted` (using `PROJECT_AUTOMATION_PAT`, run before the live label/milestone re-fetch) to auto-assign milestone #11 ("LanCache-NG Roadmap") to a Dependabot PR that doesn't already have one -- the one real gap. Dependabot PRs now go through the exact same real check as everyone else. `add-to-project.yml`'s job is itself skipped outright (`if: secrets.PROJECT_AUTOMATION_PAT != ''`) rather than run-and-fail when that secret is absent, since `actions/add-to-project` errors immediately on a blank `github-token` input -- a hard failure on every new issue/PR before the secret exists, not the harmless no-op that file's header describes. The check requires a milestone unconditionally (it cannot cheaply determine whether the rule's "when one applies" exception genuinely applies to a given PR without an extra API call to inspect the referenced issue); every issue in this project has carried a milestone in practice so far, so this is stricter than the written rule but has not yet rejected a legitimately milestone-less PR. Revisit if that changes. `build-push.yml`'s `pull_request` trigger includes `labeled`/`unlabeled`/`milestoned`/`demilestoned`/`ready_for_review` in addition to the GitHub default `opened`/`synchronize`/`reopened`, so the check (and the rest of this monolithic workflow) reruns whenever metadata that feeds it actually changes, rather than showing a stale result until the next commit; this reruns the whole pipeline, not just this job, which is a deliberate cost/correctness tradeoff since labels/milestones change far less often than commits -- see the `on:` block's own comment in `build-push.yml`.

## Source of Truth and Conflict Resolution

When working across this repository's documentation and governance stack, conflicts and inconsistencies can emerge between the various sources of guidance. This section establishes an explicit precedence order to resolve such conflicts and a requirement that agents must surface real conflicts rather than silently choosing one source over another.

**Precedence order for resolving documentation conflicts:**

When an agent encounters a real inconsistency or conflict between two governance/documentation sources, apply this precedence order to determine which source takes priority:

1. **[AG-DOC-002] Executable checks and current code behavior** — What the code actually does today and what the CI checks actually enforce today are the ground truth. If documentation claims behavior that contradicts what the code or CI verifiably does, the documentation is stale.
2. **[AG-DOC-003] `AGENTS.md` (this file)** — Repository-wide hard rules for agent behavior, workflow, validation, and governance apply to all work in this repository, except where a more specific source lower in this list carries scoped precedence within its own area. Two such sources currently make that kind of claim, and both take precedence over this file's general guidance within their own stated scope: the area-specific AGENTS files in item 3 (Rule-Ref: AG-DOC-004), once you have identified that your work falls into that area, as item 3 itself states; and `SECURITY.md` in item 4 (Rule-Ref: AG-DOC-005), for security-relevant work, as item 4 itself states.
3. **[AG-DOC-004] Area-specific AGENTS files** (e.g., `.github/AGENTS.md` for GitHub Actions work) — Specialized guidance for specific areas takes precedence over general guidance once you have identified that your work falls into that area.
4. **[AG-DOC-005] `SECURITY.md`** — Security-specific behavior and constraints are documented separately and take precedence for security-relevant work.
5. **[AG-DOC-006] Architecture and release documentation** (e.g., `docs/architecture-ng.md`, `docs/release-versioning.md`, `docs/release-external-images.md`, `docs/threat-model.md`) — System design and release procedures are documented here with rationale.
6. **[AG-DOC-007] `README.md` and user-facing documentation** (e.g., `docs/install-ca-cert.md`) — End-user guides and high-level project descriptions are placed last because they are more likely to lag behind operational or technical changes.

**Surfacing and resolving conflicts:**

When an agent finds a real conflict between two of these sources (not a misreading, but a genuine inconsistency that reflects stale documentation or outdated guidance):

- **[AG-DOC-008] Do not silently pick a side and proceed.** This masks the problem and allows drift to accumulate.
- **[AG-DOC-009] Surface the conflict explicitly** — note it in a PR comment, a dedicated issue, or a follow-up task description. Explain which sources disagree and what real-world behavior you observed.
- **[AG-DOC-010] Fix one side of the conflict or ask for guidance** — either update the stale documentation to match reality, or update the code/CI if the documentation is more correct. Only ask for guidance when the correct behavior is genuinely ambiguous or depends on a user decision. Per the user-context rule (see "Agent Autonomy and User-Context Rule" below), agents are expected to make technical decisions independently; guidance is only needed when there is real operational impact (hardware, cost, network topology) or when the correct target behavior is not determinable from code and documentation alone.

This precedence order exists because this project touches DNS, DHCP, TLS interception, Docker startup behavior, cache correctness, and local network availability — all areas where documentation drift is not a stylistic gap but a real operational risk.

## Documentation Drift Is A Defect

**[AG-DOC-001]** A PR that touches architecture, security, setup, DNS, release, Admin UI authentication, or user-facing behavior must verify that the relevant documentation still accurately describes the resulting reality after the change. Documentation includes: `README.md`, `SECURITY.md`, `docs/threat-model.md`, `docs/architecture-ng.md`, `docs/release-versioning.md`, `docs/release-external-images.md`, `CLAUDE.md`, this file (`AGENTS.md`), and `.github/AGENTS.md`.

A PR is not complete if it leaves any of these documents objectively wrong or describing behavior that contradicts the change. Stale documentation is not a follow-up item — it is a blocker. If a code change invalidates a documented behavior, statement, or threat model characterization, the PR must update the documentation or explicitly explain why the documentation statement is still correct despite the code change.

This rule exists because real drift was discovered and fixed in issue #529: `docs/threat-model.md` contained a stale reference to BIND9 (the system now uses PowerDNS), and described Admin UI authentication as "no authentication by default" when the current code actually fails closed and requires either explicit `UI_AUTH_USER`/`UI_AUTH_PASSWORD` configuration or an explicit `ALLOW_INSECURE_UI=true` opt-out. Both of these drifts were operational risks — operators following the threat model would make incorrect security assumptions, and future developers would misunderstand the current authentication behavior.

## Issue And PR Tracking

- **[AG-GH-002]** Issue descriptions must include the correct links to related pull requests, issues, or parent tracking threads when those relationships are known.
- **[AG-GH-009]** Issues should also carry labels, an issue Type, a Milestone when one applies, and Project-board assignment; use GitHub's native parent/sub-issue relationship (not just a title convention) when an issue is genuinely a sub-task of a tracking issue. An issue left as an unclassified note without these fields is not fully triaged.
- **[AG-GH-003]** Pull requests must reference their tracking issue in the PR body whenever possible.
- **[AG-GH-010]** Every pull request body must include a changelog-style summary: what changed, user-visible impact, how it was validated, known risk, and any follow-up work. A PR without this cannot be called integration-ready regardless of CI status.
- **[AG-GH-008]** Pull requests must carry at least one label, a Milestone (when one applies — same qualifier as the issue-metadata rule above; not every issue has one, and a PR mirroring such an issue doesn't need to invent one either), and Project-board assignment. When a PR closes or fixes a single issue via `Closes #123`/`Fixes #123`, mirror that issue's labels and Milestone rather than picking new ones. When a PR closes one issue but also carries a non-closing `Refs #456` to a parent tracker or design discussion, the closed/fixed issue is the metadata source — never the `Refs` target, since a `Refs`-only tracker can legitimately carry different labels or a different Milestone than the specific PR resolving one of its sub-tasks. A PR with no tracking issue at all (a maintainer-directed or housekeeping change — the PR template explicitly allows stating no issue exists) still needs its own labels and Milestone chosen at review time; there's simply no issue to copy them from. A PR with correct code and green CI but no labels and no Project-board entry is not properly filed; do not treat "the code is right" as equivalent to "the tracking metadata is complete." This metadata must be set as part of the same action that opens the pull request, not as a follow-up cleanup step performed only after `pr-tracking-metadata-check` in build-push.yml is observed failing — that check runs immediately and blocks any non-draft PR missing this metadata, so a red result here is a compliance miss to fix going forward, not an acceptable normal first pass.
- **[AG-GH-004]** Use closing keywords such as `Fixes #123` or `Closes #123` only when merging the PR should close the issue.
- **[AG-GH-005]** Use non-closing references such as `Refs #123` for parent trackers, design discussions, drafts, or partial follow-up work.
- **[AG-GH-011]** Scaffold or partial-fix PRs must say they are scaffold or partial in the title/body, must name the remaining open tracker with `Refs #123`, and must not use `Fixes #123` / `Closes #123` for the unresolved remainder.
- **[AG-GH-012]** After a PR lands, compare the merge commit or current `github/master` against the original issue before claiming completion; PR-head-only claims are not sufficient.
- **[AG-GH-006]** Do not leave known issue/PR relationships only in chat history; capture them in GitHub so review, merge, and cleanup decisions stay traceable.
- **[AG-GH-013]** Actively maintain issues and PRs with comments as work happens, not only a body/description written once at creation time. Post a comment for each significant finding, decision, root cause, or piece of new information as soon as it is known, rather than batching everything into one end-of-work summary. This applies to agents doing the work, not only to whoever dispatched them: an agent performing non-trivial investigation, a fix, or research must post its own findings as GitHub comments while working, not leave them only in a chat transcript or a final report for someone else to transcribe afterward. Concretely: within the first 15 minutes of starting non-trivial work on an issue or PR, post an initial WIP comment stating what is being investigated or attempted, then post a further update at least every 15 minutes thereafter for as long as the task runs, until it is done. Determine elapsed time by actually running a real time/date command (e.g. `date +%s`, compared against a timestamp captured at task start)—never by estimating from turn count, amount of work done, or a subjective sense that "it's probably been a while." A vague or absent update cadence is exactly the gap this rule exists to close; "I'll summarize everything at the end" is not compliance, no matter how thorough that summary turns out to be.
- **[AG-GH-014]** **Issues must carry enough detail to be independently actionable, not a one-line note.** A well-formed issue names the exact files/functions it concerns — the specific paths to be edited, not just the general topic area or subsystem — states concrete, checkable acceptance criteria (not "improve X" or "look into Y"), and explains why the problem is real (a reproduction, a real log excerpt, a specific code reference) rather than asserting it abstractly. The bar: someone with no other context should be able to read the issue body alone and say which changes are needed, even before any PR exists. An issue that only a person who already has the full context in their head can act on is under-specified and must be expanded before being handed to an implementer — human or agent — who does not share that context. This matters more, not less, when issues are meant to be picked up by an agent with no memory of the conversation that created them.
- **[AG-GH-015]** **A follow-up/successor issue narrowing or continuing an earlier issue's scope must state explicitly, in its own body, whether it fully covers the original's acceptance criteria or only a subset.** Do not create a narrower issue and leave the reader to infer from titles or labels whether it supersedes the original. If the successor only covers part of the original: name exactly what remains uncovered, and update the *original* issue's body (not just a comment) with a "Current Status" note pointing at the successor and stating plainly that closing the original once the successor lands would be premature. This project has repeatedly created a narrow follow-up issue for a large finding and then let the original silently rot as if it were resolved — treat that pattern as a known failure mode to actively guard against, not an acceptable shortcut.
- **[AG-GH-016]** **Before closing an issue as resolved, superseded, or duplicate, actually diff its acceptance criteria against the PR/issue you believe covers it — do not match on topic or title similarity alone.** Two issues about "the same area" are not automatically the same issue; one may be a strict subset of the other's scope. Prefer verifying against the real current repository state (run the actual check, read the actual current file) over trusting either issue's prose, since both may have been written before the code moved further.
- **[AG-GH-017]** Before starting new work that will produce a branch (a fix, an investigation, documentation, an audit), first check whether a branch, PR (open, closed, or merged), or issue already covers the same scope—via `git fetch --all --prune && git branch -r` (a stale local remote-tracking list, from before the last fetch, misses branches pushed since—`-r` alone shows cached refs, not a live remote listing), `gh pr list --state all --limit 200 --search <keywords>`, and `gh issue list --state all --limit 200 --search <keywords>` for relevant keywords/issue numbers (both `gh` commands default to open-only and a 30-result limit, which silently under-searches a repository with hundreds of issues/PRs; a "no match" from the defaults is not proof nothing exists)—rather than starting fresh and risking duplicate integration. This extends Rule-Ref: AG-WF-018's "search issues before filing a new one" to branches and PRs specifically, and to every dispatched agent, not just the coordinator. Second, once a branch is pushed, it must be traceable in writing—either as an open/draft/closed PR, or as an explicit comment on a linked issue naming the branch and its purpose—at or shortly after creation. A branch containing real analysis, fix, or documentation work that exists only as raw commits, with no PR and no written trace anywhere in the tracked issue, is not acceptable no matter how good its content is (a real incident prompted this rule: 19 `bughunt-*`/`docs/inventory-*` branches pushed 2026-07-15, containing thousands of lines of genuine analysis for issues #843/#849, were discovered unreferenced and unmerged three days later, invisible to anyone reading those issues). This applies to every agent and every dispatch: a subagent instructed to investigate or produce work on a new branch must first check for pre-existing coverage, and must then either open a Draft PR or post an issue comment linking the branch and summarizing its contents before ending its own work—"I pushed a branch" is not a completed handoff by itself. A branch that will not become a PR (abandoned, superseded, exploratory-only, or found to duplicate existing work) must be flagged for deletion with a clear written explanation (e.g. an issue comment naming the branch and why it's no longer needed) rather than left dangling with no explanation at all; per Rule-Ref: AG-WF-005, actual deletion still requires the maintainer's explicit instruction—an agent does not delete it unilaterally just because it decided the branch is abandoned.
- **[AG-GH-018]** **Pull request titles must follow a Conventional-Commit shape: `type(scope)!: subject`.** This repository **merge-commits pull requests (it does not squash)**, so the PR title — not any individual commit inside it — is the most reliable single human-authored summary of what a PR did, and enforcement targets the PR title itself, validated by `scripts/tracked/check-pr-title-convention.sh` and the `pr-title-convention-check`/`pr-title-convention-check-hosted` CI jobs in `build-push.yml` (mirroring `pr-template-check`'s and `pr-tracking-metadata-check`'s draft/non-draft behavior: a draft PR gets a warning, and — see the enforcement-mode paragraph below — a non-draft PR with a non-conforming title currently also only warns, not fails). This taxonomy was derived from an actual audit of this repository's git history (roughly 250 commits on `current_dev`, roughly 150 on `master` at the time of the audit — see issue #850's audit comment), not invented in the abstract; it codifies what this project's real usage already mostly does, with the small number of deviations named explicitly below.

  **Allowed types** (each maps to the SemVer `vY.X.Z` component it should bump once the automated version-bump tooling from issue #819 exists; they are documented for consistency and changelog clarity regardless of whether that automation is wired up yet):

  | Type | Meaning | Bumps |
  |---|---|---|
  | `feat` | A new user-facing capability | `X` (minor) |
  | `fix` | A bug fix | `Z` (patch) |
  | `security` | A security-relevant fix or hardening change | `Z` (patch) |
  | `docs` | Documentation-only change | none |
  | `refactor` | Code change with no behavior change | none |
  | `perf` | A performance improvement | `Z` (patch) |
  | `test` | Test-only change | none |
  | `build` | Build system, packaging, or dependency change | none |
  | `ci` | CI/CD workflow or tooling change | none |
  | `chore` | Maintenance work not covered by the above | none |
  | `style` | Formatting/whitespace only, no logic change | none |
  | `revert` | Reverts a previous commit/PR | matches the reverted change's own type |

  A `!` immediately after the type (or after the scope, if one is present) — e.g. `feat!:` or `fix(proxy)!:` — or a `BREAKING CHANGE:` footer in the PR body marks a breaking change. **Because this project is deliberately pre-1.0 (`Y` stays `0` until a production-ready milestone, per issue #819), a breaking change bumps the MINOR (`X`), not the major (`Y`), while pre-1.0** — this is standard SemVer pre-1.0 practice and maps directly to `release-please`'s `bump-minor-pre-major: true` setting, should that automation land. The major version bump to `1.0.0` remains a deliberate, manual maintainer decision, never an automatic side effect of a `feat!:` title.

  **`security` is a standard type in this project** (maintainer decision, #850, 2026-07-23) — a first-class alternative to `fix(security): ...`/`feat(security): ...`, kept because this project's own history already used `security:` deliberately and consistently. `security(scope): ...` (combining the type with a more specific documented scope) is also valid.

  **Scopes** are optional (a type-only title such as `fix: ...` is valid on its own), lowercase, and — when present — must be one of the documented project areas below, matching `docs/naming-conventions.md`'s real service names plus a small number of non-service project areas already in real use: `proxy`, `dns`, `dhcp`, `dhcp-proxy`, `ntp`, `ui`, `nats`, `watchdog`, `netdata`, `syslog`, `setup`, `ci`, `governance`, `docs`, `scripts`, `tests`, `build-tools`. A scope outside this list (e.g. `fix(bogus-scope): ...`) fails the check with a pointer to this list. Extending the list requires updating both this rule and `scripts/tracked/check-pr-title-convention.sh`'s `allowed_scopes` array together, the same way `docs/naming-conventions.md`'s own service-name additions must stay in sync with the files that depend on it.

  **Enforcement mode: currently `warn`, not `block`** (maintainer decision, #850, 2026-07-23). `PR_TITLE_LINT_MODE` (an optional repository variable, `scripts/tracked/check-pr-title-convention.sh`'s `pr_title_lint_mode`) defaults to `warn` today: a non-draft PR with a non-conforming title gets a CI `::warning::` annotation but does not fail the check. **This is a transitional grace period, not a permanent downgrade — a `warn` result is still a real violation of this rule that must be fixed before the PR merges; it simply does not hard-block CI while the grace period is active.** Do not read a green `warn`-mode check as "this title is fine" or as license to leave a non-conforming title in place. Setting the same repository variable to `block` (a one-line, no-code-change flip) restores full enforcement whenever the maintainer decides the grace period is over.

  **Caveat: this does not, by itself, make PR titles what `release-please` would read.** A dedicated evaluation (PR #1113, 2026-07-23) read `release-please`'s actual commit-parsing source and found it parses the real git commit message header directly, with no PR-title fallback — its only override mechanism is a `BEGIN_COMMIT_OVERRIDE`/`END_COMMIT_OVERRIDE` block in the PR body. This repository's real commit messages currently lead with a `CLD-<unixtime>` marker (per Rule-Ref: AG-WF-017) *before* the type token, which `release-please` would not recognize as a bump signal, and merge commits (this repo doesn't squash) don't carry the PR title as their own header either. This rule's PR-title enforcement is still necessary groundwork (a real, checkable human/agent convention, and the unit any manual changelog reading already relies on) — but adopting `release-please` itself would additionally need one of: a switch to squash-merging, a change to where the `CLD-` marker sits in commit messages, or routine use of `release-please`'s own commit-override block. None of that is decided or implemented by this rule; see issue #819 and PR #1113 for that separate, still-open decision.

  **Good title examples:**
  - `feat(dhcp): add IPv6 lease support to Kea config generation`
  - `fix: correct nginx cache key to include $host`
  - `fix(proxy)!: change default cache TTL, breaking existing cache entries`
  - `docs(governance): add Conventional-Commit PR-title rule and lint`
  - `chore(build-tools): bump bats to 1.11.0`
  - `security(proxy): patch a credential leak`

  **Bad title examples (and why):**
  - `Feature: add IPv6 support` — capitalized and not a recognized type (`Feature` is not `feat`)
  - `harden(ci): tighten the workflow permissions` — `harden` is not a Conventional-Commit type; use `fix(ci): ...` or `chore(ci): ...` depending on intent
  - `fix(networking): resolve DNS timeout` — `networking` is not a documented scope; the closest real area is `dns`
  - `update the README` — no type prefix at all
  - `CLD-1784784450 fix(docs): update stale line` — the agent identifying marker (per Rule-Ref: AG-WF-017) belongs in the PR **body**, never the title; a title that leads with it is itself a violation of AG-WF-017, independent of this rule

  **Enforcement is from here forward only.** This rule and its CI check apply to PR titles going forward from when this rule merges; already-merged commit/PR-title history is **not** rewritten or retroactively judged non-compliant, since doing so would rewrite merge-commit history in a way Rule-Ref: AG-WF-004's PR-only workflow does not contemplate.

- **[AG-GH-019]** **An issue or PR's title and body reflect the state at the moment it was opened, not necessarily now — real updates accumulate in comments, and every comment must be read as new information, in full, oldest to newest, not skipped past or replaced by reading only the latest one.** Before acting on, summarizing, or reporting the status of any issue or PR, read the full body AND the full comment history in chronological order (`gh issue view N --json body,comments` / `gh pr view N --json body,comments`, walking `.comments[]` oldest to newest) — not the body alone, and not just the most recent comment. For a large issue/PR whose body or comment history runs into many thousands of words, read it in full anyway, chunked in passes of roughly 25,000 tokens each, rather than truncating or skipping sections to save time. Skipping to only the newest comment is not a safe shortcut either: a later comment often answers a narrower follow-up question and says nothing about an earlier, still-load-bearing finding (a scoping decision, a discovered blocker, a maintainer override) from several comments back — treat each comment as a delta on top of everything before it, not an independent snapshot where only the last one matters. When a comment contradicts the body (a sub-item now done, a scope change, a reversed recommendation), the comment wins; update the body or post a status-correction comment rather than silently working around the drift for yourself and leaving it stale for the next reader (human or agent). This applies with full force to dispatched agents, not only whoever commissions the work: an agent told to close or check the status of an issue/PR must read the full chronological history itself before concluding anything about current scope or status — a stale title/body summary handed down from the dispatcher is not a substitute for this. A real incident prompted this rule (2026-08-06): issue #815's own body/status text still described its `services/ntp` and `services/dns` sub-items as not yet migrated, because neither had been edited after the relevant PRs actually merged (#1345 on 2026-07-31, #1425 the same morning this was found) — the true state existed only in the issue's comment history the whole time. Rule-Ref: AG-GH-022's own requirement — maintaining a durable, atomized, comment-ID-cited checklist in the body itself — must always be treated together with this rule, never as a separate, optional follow-on.

- **[AG-GH-020]** **Minimize comments that become genuinely outdated, superseded, resolved, and/or duplicate — do not rely on a correcting comment alone.** When new information makes an earlier comment on an issue or PR wrong, stale, or redundant (a status update superseded by later work, a question the thread has since answered, a comment that duplicates another one nearly verbatim), minimize the outdated comment via GitHub's `minimizeComment` GraphQL mutation with the matching classifier (`OUTDATED`, `DUPLICATE`, `RESOLVED`, or `OFF_TOPIC`), in addition to posting the comment that corrects or supersedes it — posting a correction elsewhere in the thread is not sufficient on its own, since AG-GH-019 already requires every comment to be read in full, and a long thread of comments left fully visible after they stop being accurate defeats the purpose of that discipline by making the thread itself the thing that needs correcting. Minimizing preserves the original comment (it stays readable if a reader chooses to expand it) and is not deletion; it is never a substitute for AG-WF-026's requirement to consolidate substantive knowledge into a durable location before a comment that carries it is minimized, closed over, or otherwise made harder to find — if the comment being minimized is the only place some finding, decision, or piece of evidence lives, migrate that content to a durable location (the issue/PR body, a structured comment, or another appropriate record) first, then minimize. After any comment-minimizing pass — whether performed by the main/coordinating thread itself or by a dispatched agent — the main/coordinating thread must independently verify that the comment section and the issue/PR body together read as one current, consistent whole, not delegate that verification away; a dispatched agent's self-report of "N comments minimized" is not a substitute for the coordinating thread checking the result itself. This mirrors AG-WF-035's own binding of the main/coordinating thread regardless of whether it dispatches a sub-agent, applied here specifically to comment/body consistency rather than general AGENTS.md compliance.
- **[AG-GH-021]** **A PR/issue body documenting or fixing `current-dev-auto-close.yml`'s (or any similarly-scoped closing-keyword-scanning automation's) own matching behavior must not contain a literal, unmasked closing-keyword phrase immediately followed by a real `#N`.** Writing a bare `Closes #123` as a worked example, or quoting an incident string like `"close #1095"` verbatim to illustrate what the bug matched, is itself a string the automation will match when it scans that very PR's body on merge — the keyword scanner has no way to distinguish "this is a real closing instruction" from "this is an example/quotation inside prose about the scanner." Mask any such example instead: write "issue 123" instead of `#123`, insert a zero-width or HTML-entity break inside the hash-number pair (`#&#8203;123`), or otherwise break the literal `keyword #N` adjacency the scanner's regex requires. This rule exists because PR #1491 — the fix for `current-dev-auto-close.yml`'s missing negation handling — re-triggered the exact same false-auto-close behavior it was fixing when it merged: its own body's worked-examples section (`Closes #123`, `fixes #42`, etc.) and its incident-description prose (quoting the substring `"close #1095"` without the original sentence's surrounding negation) matched 9 separate `#N` references on merge, including issue #1095 itself, closing it a second time. The 8 other matched numbers happened to already be closed for unrelated reasons (no new damage), which was luck, not a property of the fix — the underlying authoring gap is real regardless of that outcome. A companion technical hardening of the scanner itself (excluding matches inside PR-body code fences, or requiring closing keywords to appear outside any block that looks like a worked-example list) is tracked separately and is not a substitute for this authoring discipline, since a maintainer or agent writing about this exact automation is the one person guaranteed to write matching example text.

- **[AG-GH-022]** **Extends Rule-Ref: AG-GH-019: once an issue or PR's comment history has grown large enough that its actual current status is no longer obvious from the title/body alone, its body must maintain a chronologically-ordered, atomized "Live checklist" reflecting that history — one checklist entry per substantive comment, never a summary that merges several comments into one line.** Each entry cites the real GitHub comment permalink it originates from (`#issuecomment-<id>`) plus a short, accurate paraphrase of what that specific comment stated, decided, or found. Each entry's checked/unchecked state must be verified individually against real evidence — never inferred in bulk from surrounding context or another entry's state — and a checked (`[x]`) entry must itself document the concrete verification performed (the specific evidence, command output, or reasoning that confirmed it), not merely a checkmark plus a paraphrase; this is the same evidentiary standard this project's own PR template already requires under "Validation," applied per entry. This checklist is not a one-time reconstruction: any new comment that adds, changes, resolves, or supersedes something must produce a corresponding checklist update in the same pass that reads it, not deferred to a later cleanup. When a later comment contradicts or corrects an earlier one (Rule-Ref: AG-GH-019: the comment wins), the earlier entry stays visible, unchecked, with a pointer to whichever later comment actually settled the question — never deleted, so the reasoning trail (including a wrong turn that was caught and fixed) stays traceable.

  A run of routine WIP/standing-loop progress-ping comments (e.g. a standing loop posting "still working, here's the current status" every ~15 minutes) does not each get its own checklist entry — that would recreate exactly the comment-flood problem this checklist exists to solve. Instead, such a run is consolidated into ONE evidence-bearing summary comment before the body cites it, using `.github/issue-checklist-response-template.md`'s format (modeled on wiki-mod/distcc-ng#476's PR-body structure: Summary, What This Actually Changes, What Was Found, What Changed In Code, Validation including which changes were checked against AGENTS.md violations, Risk/Rollback/Follow-up, Local Scope Evidence, and Bugs/Problems found that are not addressed yet or deliberately deferred) — the body's checklist entry then cites that one consolidating comment's real ID, never the raw ID range of the individual progress pings it replaces.

  For an issue/PR complex enough to need internal grouping, wiki-mod/lancache-ng#1501 is the live reference example for numbering checklist items sequentially within lettered sections (with `## Status` and `## Current verified checkpoint` sections above the checklist) — not mandated verbatim for every issue, but the structure to reach for once a flat list stops being navigable; wiki-mod/lancache-ng#1527 (sandbox/dry-run issue, safe to reference) demonstrates the full mechanism (comment-ID citation, WIP consolidation, superseded-entry handling) applied together in that #1501-style structure. This rule exists because issue #1095 accumulated close to 200 comments with no maintained checklist, making its own actual current state effectively unrecoverable without re-reading the entire thread end to end every time.

  **Comments are never deleted to "clean up" a stale or superseded finding** — the chronological trail is the actual point of this rule, and a comment later contradicted by a newer one is still valid history explaining how the current state was reached. Removing or rewriting an existing comment's original content (rather than posting a new one) is likewise not an acceptable way to correct it, for the same reason. The one narrow exception is a comment that is demonstrably a genuine mistake (e.g. posted to the wrong issue entirely, or containing content that should never have been posted at all) — even then, deleting it requires the maintainer's own explicit, freshly-given ACK for that specific comment; a general standing approval to "clean up mistakes" does not cover it, and an agent must never delete a comment unilaterally based on its own judgment that something was a mistake.

  **When a comment is confirmed superseded (not a mistake, just outdated), mark it in place rather than leaving a future reader to rediscover that the hard way.** This is the one form of editing an existing comment that this rule does allow, because it is purely additive and never removes or rewrites the original content: prepend a clearly visible marker at the top in bold, upper-case text — e.g. **`SUPERSEDED / NO LONGER CURRENT`** — and append an `Updated <date/time>: <explanation>` note at the bottom naming and, where practical, linking the specific later comment that supersedes it and briefly stating why. The original body stays fully intact, unedited, between those two additions. This gives a reader scanning the thread top-to-bottom (still oldest-to-newest, per the rest of this rule) an immediate, honest signal — "this is old, here's proof, skip to the linked comment" — without needing to read the whole superseded comment in detail to work that out for themselves, and without destroying or obscuring the history the rest of this rule exists to preserve.

- **[AG-GH-023]** **Using `gh stack` to organize multiple open pull requests is not a default obligation.** An AI agent must never create, join, or link a pull request into a `gh stack` on its own initiative — only when the maintainer explicitly requests it for that specific pull request or set of pull requests. This reverses this rule's previous blanket requirement (organize every open PR through `gh stack`, regardless of dependency): real-world use showed AI agents cannot yet reliably operate `gh stack` — a single stack merge took three days to resolve in practice — and the mandate caused more harm (stuck rebases, duplicated commits over stale branches, extended remediation) than the coordination benefit it was meant to provide. This is a narrowing placeholder pending a fuller rework of this rule (2026-08-27); how genuinely dependent PRs should be organized instead is not yet answered.

  When the maintainer does explicitly request a stack for one or more PRs, the following still applies: any `gh stack init`/`gh stack link` invocation for a PR targeting the development trunk must explicitly specify `--base current_dev` — the command's own default base must never be relied upon, since it resolves to this repository's configured GitHub default branch (`master`), not the active development trunk. This does not apply to a PR that legitimately targets `master` itself (a CI/governance sync PR under Rule-Ref: AG-CI-019, or a release-promotion PR) — those use `--base master`, matching the branch they actually target.

  **A PR must always be opened against `current_dev`/`master` first, and only retargeted onto another PR's branch afterward via `gh stack link` — never created with a stacked (feature-branch) base from the start.** Confirmed live (2026-08-20, disposable test PR #1615, closed without merging): `build-push.yml`'s `pull_request` trigger (`branches: [master, current_dev, "v[0-9]*"]`) only evaluates against the base a PR had when its first matching event occurred. A PR opened with a non-matching (feature-branch) base from creation gets zero `Build & Push` runs, silently, for its entire life — confirmed by opening #1615 directly against a feature branch and observing no `Build & Push` run at all (only unrelated `pull_request_target` workflows fired). A PR opened normally against `current_dev`, then later retargeted via `gh stack link`, keeps running real CI on every subsequent push (confirmed live on PR #1604) — the already-established check-suite is not re-gated by the filter on a later retarget. The order matters: open first, link second, never the reverse.

  **Resolving a conflict in a `gh stack`-tracked branch is done only through `gh stack` itself, never through a manual `git rebase`/`git merge`** — even when `gh stack rebase` is demonstrably misbehaving for that case; a mechanically equivalent result via plain git does not satisfy this rule. The standard path (GitHub's own documented procedure): `gh stack checkout <pr-number>`, then `gh stack rebase`, resolve conflicts with ordinary `git` conflict resolution and commit, then `gh stack push`. If `gh stack rebase` itself fails or behaves incorrectly (a confirmed real case: a second rebase pass on a stack whose lower members already merged can duplicate already-applied commits, because it derives its plan from the full local, non-linear merge history rather than GitHub's own current view) — do not substitute a manual rebase to route around it. Instead: `gh stack rebase --abort` (safe, local-only), then re-import the stack fresh via `gh stack checkout <pr-number>` (GitHub's own server-side view already knows which lower members merged, independent of confusing local history). If that is still not enough, the local branches of the already-merged lower stack members may need deleting before rebuilding — `gh stack unstack` alone does not reset the affected PRs' base branches — but every step of that rebuild must still go exclusively through `gh stack` commands, never a manual git equivalent.

  `gh stack push`/`gh stack sync` push each branch using `--force-with-lease` internally as part of their normal operation — this does not exempt that action from Rule-Ref: AG-WF-024's re-verification requirement before any force-variant push, whether run directly or through the tool. `gh stack merge` itself refuses to bypass branch protection or required checks ("bypassing merge requirements is not supported for stacks"); Rule-Ref: AG-WF-039's literal-ACK requirement for any `--admin`/bypass action applies in full to a stacked PR exactly as it does to any other — there is no stack-specific exception, and an agent must not attempt a manual `--admin` merge to route around a stack merge that `gh stack merge` refuses to perform.

## Agent Workflow

- **[AG-WF-001]** Start every branch from a freshly fetched and rebased current base branch.
- **[AG-WF-020]** Before making readiness, mergeability, or integration-order statements, fetch the PR branch and base branch, rebase the local worktree onto the current remote base, and verify the resulting head. If a branch cannot be rebased, state that blocker instead of giving a readiness conclusion.
- **[AG-WF-002]** Use a separate worktree for every PR and/or issue and/or (sub-)agent task. Every such worktree MUST live under one fixed, predictable root: `<repo-root>\.claude\worktrees\<issue-nr>_<shorttext>` (already gitignored) — never at a drive root, never as a sibling of the repo under its parent directory, and/or never under a freely-invented name. No work may proceed in a worktree that is not named `<issue-nr>_<shorttext>`. The coordinating (main) thread creates this directory itself, bound to a specific issue number, before dispatching any agent to it — a dispatched agent must verify the assigned directory and/or issue binding it was given rather than inventing its own. Before any work at all begins, the agent must check how far the worktree's branch is behind its base branch (diff-range against the base) and/or rebase/update onto the current base first — never build on a stale and/or unverified starting point. The very first action taken in a freshly created worktree, before any code change, must be an empty marker commit (`git commit --allow-empty`) stating the initial task and/or the issue number this worktree is tied to — this is the recovery anchor if work is interrupted (API limit, accidental cancellation, and/or crash) with no other record of what the worktree was for. The marker commit must also state the agent's own task/session ID when running as a dispatched (sub-)agent, so the coordinator can resume or query it later independent of worktree naming or surviving chat history. Remove a worktree (`git worktree remove`) as part of finishing the task it was created for, rather than leaving it for a future cleanup pass. Any uncertainty and/or open question regarding any part of this rule must be escalated up the dispatch chain — a (sub-)agent to its coordinator, and that coordinator to its own coordinator in turn, continuing upward with no limit on depth — until it reaches the main/coordinating thread; the main/coordinating thread must then resolve it directly and/or obtain the maintainer's decision.
- **[AG-WF-003]** Use fanout for bounded independent work when it reduces main-thread cost without reducing quality. Prefer the cheapest suitable model and reasoning level: Spark first while available; if Spark is unavailable, rate-limited, or unsuitable, evaluate `gpt-5.4-mini` next before keeping delegable work in the main thread.
- Choosing main-thread work while Spark is unavailable requires a concrete reason, such as unsafe delegation, time-critical local context, or higher integration risk from a separate agent.
- **[AG-WF-021]** Treat subagent results as stale until verified against the current remote base and current PR head. Before using an agent result for readiness, conflict resolution, review comments, or merge guidance, compare the reported commit/base with GitHub and rerun the relevant checks on the current head.
- **[AG-WF-022]** Do not block on subagents when useful non-overlapping work is available. Poll sparingly, and close completed agents after their result has been reviewed or superseded.
- **[AG-WF-024]** Any agent that spawns sub-agents of its own must dispatch each one with its own explicitly-assigned, verified-clean working directory—never assume a worktree (even one the harness labels "isolated") starts from a pristine, correctly-based checkout. Before doing any work, an agent (top-level or sub-agent) must verify its actual current branch/HEAD against the expected clean base (e.g. `git fetch origin && git log --oneline -5` and compare against `origin/<base-branch>`) and, if it does not match, must not attempt to salvage the worktree in place by default—prefer discarding it and provisioning a genuinely fresh one from a clean checkout of `origin/<base-branch>`. If a fresh worktree is not available and an existing one must be reset in place instead: `git reset --hard origin/<base-branch>` (clears tracked-file modifications a plain `checkout -B` does not touch), followed by `git clean -fd` (removes untracked files)—deliberately NOT `git clean -fdx`, since `-x` also deletes gitignored files this repo legitimately keeps locally (e.g. `certs/*.key`, `.env`), and could silently destroy real secrets or generated state instead of just another task's stray work—then verify `git status --porcelain` is empty before proceeding, since no single one of `checkout -B`, `reset --hard`, or `clean -fd` alone guarantees a fully clean worktree—never trust an inherited or recycled worktree's state by default. A sub-agent must never overwrite, rebase onto, or push over its parent's (or any other agent's) branch or in-flight work. Before executing `git push --force`/`-f`, `--force-with-lease`, `--force-if-includes`, or any other force-variant push, an agent must first re-verify—immediately before running it, not earlier and not from memory—that the action matches what is actually intended: confirm the current branch/HEAD, confirm exactly what the remote ref currently points to and why it is being overwritten, and confirm the content about to be pushed is the agent's own intended work and not something else's (another branch's, another agent's, or stale/inherited state). Only after that verification genuinely passes may the force action proceed. A rejected non-fast-forward push is a stop-and-re-verify condition, never something to force past reflexively. Every spawned sub-agent must read and accept the same `AGENTS.md`/`CLAUDE.md`/`.github/AGENTS.md` governance as its parent (inheritance of context is never assumed), and must explicitly report back—by name—that it has done so before starting substantive work: a bare "understood" is not acceptance; it must state that it read `AGENTS.md`, `CLAUDE.md`, and `.github/AGENTS.md`, with no shortcut. It must also check back with the dispatching agent before taking any action whose failure mode is silent data loss or overwriting another branch's history, rather than resolving it autonomously. A real incident prompted this rule (2026-07-18): a sub-agent, dispatched with the harness's own worktree-isolation option, was handed a recycled worktree slot still checked out to an unrelated, in-flight branch (traceable to a completely different agent's PR from earlier the same session) instead of a clean base—and, without verifying this before working, ended up force-pushing that unrelated content onto its own assigned target branch, destroying that branch's clean single-commit history. It was caught only via an explicit `git diff --stat` sanity check by the parent agent afterward, not prevented beforehand by any rule, and recovered from the local reflog only because that reflog happened to still exist.
- **[AG-WF-025]** **Recurrence triggers a rule proposal, not just a second fix**: when the same class of failure (not merely the same symptom, but the same underlying cause pattern) is identified a second time, that recurrence itself is a signal that existing governance doesn't yet prevent it, and must be treated as a requirement to propose a new or strengthened AGENTS.md rule addressing the root cause, not just fix the second instance and move on. Present the proposed rule text to the maintainer for review before adding it (English canonical text plus a German translation for review). A first occurrence of a novel problem may reasonably be treated as an isolated incident; a second occurrence of the same pattern must not be.
- **[AG-WF-026]** **Consolidate and persist durable knowledge before lifecycle transitions, never afterward**: before an issue, pull request, branch, review thread, investigation, agent task, worktree, or comparable work item is closed, merged, resolved, marked as a duplicate, superseded, declared obsolete, abandoned, deleted, cleaned up, or handed off, all substantive knowledge that is not already present in the surviving target object must first be consolidated and durably persisted there. Substantive knowledge includes findings, verified facts, evidence, reproductions, relevant logs, tested but rejected alternatives, decision rationale, assumptions, constraints, known limitations, unresolved questions, acceptance criteria, dependencies, risks, rollback information, implementation state, and cross references. A link to the source object alone is not consolidation. Knowledge from chats, agent reports, local notes, scratchpads, temporary files, CI output, commits, branches, worktrees, review discussions, or other transient or difficult to discover locations must not remain the only copy; the responsible agent must compare all available source material with the surviving target and transfer every missing substantive item. Historical findings and decision records belong in a structured comment or equivalent durable record. Information that changes current scope, acceptance criteria, implementation requirements, architectural decisions, or status must also be incorporated into the authoritative sections of the target body or documentation. The consolidation must identify the source object or session, preserve relevant provenance and links, distinguish accepted decisions from rejected alternatives, describe the current implementation state, and state any unresolved remainder. Summaries are permitted only when they preserve every material conclusion, constraint, reason, risk, and required follow-up — copying only the final decision while omitting why alternatives failed is not sufficient. Where the surviving target is a GitHub issue or pull request, the consolidated comment should follow the same structure required by the Agent Closing-Report Contract (context read, what was found or changed, what was deliberately not carried over and why, verified evidence, known open risks, follow-up references), keeping consolidation records consistent with how this project already documents closing reports. A local-only object is temporary working state, not a durable target: a local commit, unpushed branch, worktree note, temporary file, or agent transcript may hold an intermediate copy while work is actively continuing, but it does not satisfy this rule as the final or only record. Before an agent ends its task, hands work to another agent, releases or cleans its worktree, or allows its execution environment to terminate, all substantive local work must be committed where appropriate, pushed to a named remote branch, and linked or summarized in an existing durable tracking object — if no dedicated issue or pull request exists, use the nearest applicable parent issue, tracking issue, pull request, or other repository record; the absence of a newly created GitHub object does not permit the work to remain unpushed or undocumented. Local work must also receive progress records while it is in progress: the fact that a branch or change has not yet been pushed, or that a pull request has not yet been opened, does not exempt the agent from recording significant findings, decisions, blockers, branch names, current state, and intended next steps in the applicable durable tracking object. A temporary local record is permitted only until the next safe persistence point — it must never be relied upon across an agent handoff, session end, worktree cleanup, container termination, or other boundary where local state may be lost; "local only" describes the current transport state, not an exemption from traceability, progress reporting, pushing, or durable preservation. This consolidation and persistence are hard preconditions for the lifecycle action: for a remote target, the information must be posted and read back successfully; for a repository artifact, the commit and remote branch must be verified to exist at the expected remote reference; for any other durable target, its successful persistence must be verified through an appropriate read-back or equivalent check. These checks must complete before the source item is closed, merged, resolved, superseded, abandoned, deleted, cleaned up, or handed off — performing the preservation and lifecycle actions in the same unverified command sequence, transferring the information afterward, or relying on the source remaining technically accessible does not satisfy this rule. If no suitable surviving target exists, the source must remain open or active until a durable target has been designated. If the knowledge or implementation state cannot be transferred and persisted completely, the lifecycle action must not be performed, and the blocker must be reported. An agent may not declare its task complete or end a handoff while substantive knowledge or implementation work exists only in its conversation, temporary workspace, unpushed commit, unpublished branch, worktree, local file, or final report — the durable tracking record must be independently understandable and recoverable by a person or agent that has no access to the originating chat, session, machine, container, or worktree.
- **[AG-WF-027]** **Fix identified problems in the same pass; do not defer them to a comment.** When work in progress reveals a real defect, gap, or missed edge case — even one outside the task's original narrow scope — fix it as part of the same change, if it is reachable without a separate approval gate. Documenting a known problem in a PR body's "Follow-up" or "Scope Boundaries" section, without actually fixing it, does not satisfy this rule and must not be presented as the task being complete. This applies equally when reviewing or working on an *existing* issue or pull request: check its body, comments, and threads for previously reported problems (a "known limitation," "follow-up," or "not fixed here" note, an unresolved review finding, etc.) and fix those too as part of the current work, rather than leaving them as they were found — unless doing so genuinely requires a maintainer decision (e.g., a materially different undertaking, or a change needing a separate approval step such as a CI trigger-behavior change), in which case scope it out but flag the scope expansion explicitly to the maintainer in the same turn/PR, not silently in a section nobody re-reads once the PR merges. A real incident prompted this rule (2026-07-25): PR #1241 (buildx-builder-teardown-leak) identified the exact same leak pattern in two more workflow files and in a runner-host script, named both correctly, and left them as an unfixed "Follow-up work (not fixed by this PR)" note instead of fixing them — corrected only after explicit maintainer pushback.
- **[AG-WF-028]** **No artifact may be declared dead, stale, unsalvageable, or safe to delete based on aggregate diff size alone.** Before any agent (or the coordinator) characterizes a branch, commit, comment, file, or other piece of work as "dead," "stale," "not worth saving," "superseded," or recommends deletion/dismissal, it must inspect that artifact's actual *unique* contribution — the specific commits, lines, or content that exist nowhere else — not merely a raw diff-count or file-count against a moving comparison target (e.g. a branch diffed against a much-newer `current_dev` will show a large diff purely from unrelated intervening history, regardless of whether the branch's own real contribution is large, small, valuable, or worthless). A large aggregate diff is not evidence of staleness; a small one is not evidence of triviality. This applies regardless of how confident the assessment feels, and regardless of whether the artifact sits inside an issue or workstream currently being actively worked — proximity to active work does not exempt an artifact from this check, and should if anything raise the bar, since a false "dead" call inside active work is more likely to destroy real, currently-relevant progress. Actual deletion of anything found this way still requires the maintainer's fresh, explicit instruction regardless of the assessment (Rule-Ref: AG-WF-005, AG-GH-017) — this rule governs the *characterization* step that precedes that request, not a new deletion-authorization path. A real incident prompted this rule (2026-07-31): an agent characterized branch `v9-scratch-ci1095test` as "confirmed dead, not salvageable" citing a 176-file/~16000-line diff against current `current_dev`, without inspecting the branch's own unique commits. Direct verification found exactly one real commit, containing a complete, well-reasoned, still-entirely-missing CI cost fix (push-trigger `paths-ignore` plus a supersession-skip job) — later rescued as PR #1334. This happened inside issue #1095, the exact workstream several agents were actively working on in the same session.
- **[AG-WF-029]** **A response to a recommendation/preference question is not execution authorization.** When the maintainer asks an agent for its opinion or recommendation ("what would you choose", "which do you recommend"), that question seeks a recommendation only. An agent must not proceed to implement the recommended option based on that alone — it must wait for an explicit, distinct go-ahead ("do that", "proceed", "yes, build A") before making any change. When genuinely unsure whether a maintainer's reply also authorizes execution, state the intended next step and wait for confirmation rather than proceeding silently. This mirrors the existing principle that finalizing a design/scheme is not itself authorization to execute it (2026-07-31 "yolo" naming-scheme incident) — extended here to cover recommendation questions specifically, after a second, distinct occurrence of the same underlying failure class (2026-08-01, issue #842 retention hardening: "what would you choose now" was answered and then treated as a go-ahead to implement, with no explicit confirmation ever given, until the maintainer caught it and had to ask for the implementation to pause). This project's concrete, agreed authorization protocol is the literal token ACK (authorize/proceed) or DISACK (do not proceed) — an agent looks for that exact word, not tone, enthusiasm, or an explanation that merely sounds affirmative. Absence of any reply is neither ACK nor DISACK under any circumstance — it means the decision remains strictly pending. No amount of elapsed time, silence, or lack of objection may ever be treated as implicit consent; an agent must keep waiting or explicitly ask again, and must never proceed on silence alone, regardless of urgency or perceived obviousness of the answer. Furthermore, whenever an agent identifies that a decision is required from the maintainer, that decision must be recorded as a comment on the relevant GitHub issue or pull request — not only stated in chat — as an explicitly structured, formatted list (markdown list syntax, with nested/indented sub-items for multi-part decisions) naming exactly what must be decided and the concrete options. A vague statement that "a decision is needed," in chat or in a GitHub comment, without the actual structured options attached in the same place, does not satisfy this rule.
- **[AG-WF-004]** Do not push directly to `master`. All changes go through pull requests.
- **[AG-WF-005]** Do not merge, close, or delete repository work unless the maintainer explicitly asks for that exact action.
- **[AG-WF-006]** Keep PRs in draft until the branch has passed local validation and known review findings are addressed.
- **[AG-WF-007]** Resolve review threads only after the finding was actually fixed or a clear maintainer-approved explanation was posted.
- **[AG-WF-008]** Every review finding that was fixed must receive a factual reply explaining the fix and must then be resolved via GitHub's `resolveReviewThread` mutation, even if GitHub already marks the thread as outdated after later code movement — resolving visually collapses the thread in GitHub's UI (the same collapsed-but-not-deleted, reader-expandable behavior Rule-Ref: AG-GH-020 already establishes for minimized comments), not merely an internal status flag.
- **[AG-WF-009]** If GitHub does not allow resolving a stale or outdated thread, add a factual PR comment naming the finding, explaining why it is fixed, and stating that GitHub did not allow resolving it.
- **[AG-WF-010]** Before changing, reviewing, or resolving an issue or pull request, read the full issue/PR context, including the description, linked issues and PRs, all review comments, replies, and resolved threads, then evaluate the surrounding file and project-wide impact instead of acting only on an isolated line.
- **[AG-WF-011]** Treat review findings as failure classes, not isolated line comments. Before marking a finding fixed, check matching install, update, secondary, release, CI, documentation, and test paths for the same class of issue.
- **[AG-WF-030]** README and other documentation can lag behind current code and governance decisions; do not treat existing docs as automatically authoritative when they conflict with current architecture or an agreed rule. When a conflict is found, either correct the documentation or ask before changing behavior to match stale docs.
- **[AG-WF-031]** Prefer GraphQL (`gh api graphql`) over plain `gh issue`/`gh pr` comment and body-update commands for GitHub writes, since the plain CLI commands have repeatedly failed or behaved inconsistently in this project. Whichever method is used, read the result back immediately per the rules below.
- **[AG-WF-012]** When writing GitHub issue or pull-request bodies/comments from local files, verify the API call uploads file content and not the literal file path. Read the GitHub object back immediately and treat bodies such as `@/tmp/...` as malformed failed writes that must be corrected before continuing.
- **[AG-WF-032]** When sending Markdown through GraphQL string variables, pass the raw file content with the CLI's file-upload mode instead of pre-encoding it as JSON. Read the object back and treat leading JSON quotes, escaped newlines, or literal file paths as malformed failed writes.
- **[AG-WF-033]** **Automated-reviewer findings (Codex or any other bot reviewer) are review findings, governed by the same Rule-Ref: AG-WF-007, Rule-Ref: AG-WF-008, and Rule-Ref: AG-WF-009 obligations as a human reviewer's comments — not a separate, optional, or severity-gated category.** This applies to every such finding regardless of any severity label it carries, not only ones tagged P1/P2 — a finding with no severity tag, or a low one, still must be fixed (or given a clear maintainer-approved explanation), replied to factually, and its thread resolved. A finding that never had a resolvable review thread to begin with (reported only in a review summary, a top-level PR comment, or a check annotation) is not exempt from this rule merely because there is no thread to resolve: the same factual-reply obligation applies via a direct PR comment instead, mirroring Rule-Ref: AG-WF-009's fallback for a thread GitHub refuses to resolve. When an automated finding cites a specific AGENTS.md rule ID as its justification, whoever processes that finding must (a) verify the citation against the rule's actual current text — an automated reviewer can misquote or misapply a rule, and the citation alone is not proof of correctness; (b) actually carry that rule's substance forward as binding context while addressing the finding, not merely confirm the rule exists and move on; (c) cross-check whether any other rule also applies to the same finding and, if so, whether it makes the requirement stricter than the cited rule alone would suggest — the cited rule is a starting point, not the ceiling of what must be considered; and (d) treat the finding as only the starting point, not the full extent of the problem (Rule-Ref: AG-WF-011 — treat findings as failure classes, not isolated instances): to avoid unnecessary additional review rounds, this must actively be investigated using the strongest verification available before considering the finding resolved. For Claude, that means consulting the `advisor` tool — not a reasoning-tier-configured sub-agent, since Claude's own sub-agent tooling exposes a model selector but no independent per-agent reasoning-tier selector, so `advisor` is the correct and sufficient stronger check for a Claude-based agent, not merely a fallback for one. For a GPT-based agent, that means the largest, most current model available, run at its highest reasoning tier (XHIGH or equivalent) — confirmed against real orchestration tooling that this model-and-reasoning-tier selection is genuinely available when spawning a sub-agent, not merely aspirational. For any other model/provider besides Claude and GPT-based agents, the analogous largest, most capable model at its highest reasoning setting, if and only if that provider's own tooling actually exposes such a selector. If the main thread cannot itself perform this stronger check (as is the case for a ChatGPT/Codex-based agent without direct access to `advisor`), it must dispatch a sub-agent capable of it instead of skipping the check — for a ChatGPT-based main thread specifically, the model and reasoning tier must be explicitly specified when creating that sub-agent, since otherwise the sub-agent silently starts with the same model and reasoning tier as the main thread itself, defeating the entire point of a stronger second check. Whichever path is used, the fix-reply for the finding must record which check was actually performed (e.g. "verified via `advisor`," or naming the specific stronger model/reasoning tier a sub-agent used) — a silent private check is indistinguishable from no check at all to anyone reading the thread afterward, and this rule's own enforcement depends on that evidence being visible.
- **[AG-WF-034]** **Do not split one cohesive unit of work into multiple PRs that "stack" only via a static snapshot copy of files and a prose-only merge-order note.** Concrete incident (2026-08-02, issue #842 watchdog Rust rewrite): the new crate (PR #1355), its CI test/lint/build wiring (PR #1379), and its Dependabot/CodeQL/cargo-audit registration (PR #1380) were split into three separate PRs, each stacked on #1355 by copying a point-in-time snapshot of its files rather than a real git branch/rebase relationship — every PR body said "do not merge before #1355" in prose only. #1380 merged before #1355 anyway, and because git had no way to see or enforce that dependency, #1355's real, independently-evolved file history collided with #1380's now-landed snapshot copy as an unresolvable `add/add` conflict on every one of the shared files the moment #1355 tried to merge, requiring a manual conflict resolution pass to unblock it. If a genuine reason exists to split such work (e.g. distinct review/governance domains — CI-config and security-tooling changes needing separate sign-off, as here), the merge-order dependency must be enforced mechanically, not merely documented as a warning a human or agent can miss: keep the downstream PR in draft, or do not enable auto-merge on it, until the upstream PR has actually merged. If mechanical enforcement is genuinely not possible for some reason, the dependency must additionally be stated in the PR's own title (e.g. `DO NOT MERGE BEFORE #1355: ...`), not only in the body — a title is visible in the PR list itself and far harder to miss than body prose.
- **[AG-WF-035]** **Check own results against AGENTS.md before declaring work complete**: before finalizing an agent-dispatch prompt, and/or at the point where one's own task is being declared complete and/or is about to be, the agent's own results must be actively checked against AGENTS.md for violations, rather than trusting general familiarity with the rules to have applied them correctly in the moment. The strongest-available-second-check obligation and its per-provider model/reasoning-tier selection (Rule-Ref: AG-WF-033) apply here too, not only to automated-reviewer findings — before declaring complete, the same advisor-and/or-largest-model check must be performed. This obligation binds the main/coordinating thread itself — whether and/or not it dispatches any sub-agent — as well as every sub-agent it dispatches and any agent subsequently spawned by those sub-agents. If a context-compaction event occurs and/or has occurred during the work, AGENTS.md must be read again in full, and every individual rule re-applied and re-checked against the work done so far — compaction is exactly the kind of event that can silently drop previously-loaded rule context and must never be trusted to have preserved it. This rule exists because this project's real incidents are disproportionately not novel logic bugs but known, already-written-down requirements omitted by oversight: a governance-doc touch left unflagged despite existing disclosure rules, and an advisor end-of-work checkpoint omitted from a dispatch prompt despite an existing standing rule requiring it, both within the same session. "I already know this rule" is not sufficient; a check performed item-by-item against the concrete task at hand, renewed during and/or after every compaction as well, is the real control. **The dispatch-time portion of this check (before finalizing an agent-dispatch prompt or continuation message) is performed item-by-item against `.github/agent-dispatch-checklist.md`** — a fixed, pasteable minimum standard, not a thing to reconstruct from memory at dispatch time; that file may be exceeded by a stricter, task-specific requirement but never satisfied by less.
- **[AG-WF-037]** **Toggle Draft/Ready deliberately around an automated reviewer's per-push trigger, not as a side effect of unrelated work.** This repository's automated code-review bot (currently Codex) re-reviews a non-draft PR on essentially every push, and that review budget is shared and limited — repeatedly retriggering it on work-in-progress commits (a fix for one finding, a follow-up test, an unrelated push while still iterating) wastes that budget on noise and can leave a real review unavailable later when it is actually wanted. Keep a PR in Draft (Rule-Ref: AG-WF-006 already requires this generally) specifically while actively iterating — pushing follow-up commits, running further local/CI validation, or otherwise still changing the PR's content. Take it out of Draft only for a deliberate review pass. Once that pass has landed (at least one posted comment, or an acknowledgment reaction with no findings), convert the PR back to Draft before pushing or testing again, so that continued iteration does not silently retrigger another automated review mid-work — do this as its own explicit step, not as an afterthought once a push has already gone out. This is an operational discipline about *when* the toggle happens, layered on top of, not replacing, Rule-Ref: AG-WF-006's own draft-until-ready requirement.

- **[AG-WF-038]** **A maintainer pause/stop instruction carries the same absolute weight as a literal DISACK, extending Rule-Ref: AG-WF-029 specifically to pause/stop rather than only to initial execution authorization.**
  1. A pause or stop instruction from the maintainer remains in force until the maintainer gives a new, explicit, verbatim "ACK" to resume — never until an agent, coordinator, or dispatcher independently judges the instruction to have been a misunderstanding, sees a contradicting report from another agent, or infers from silence that the pause has lapsed.
  2. If a party under a standing pause/stop receives any further instruction to proceed — including from its own coordinator or dispatcher — it must explicitly refuse, state that the maintainer instructed it to pause, and state that it will take no action until it receives the maintainer's own literal "ACK" per point 1. The refusal itself, with that stated reason, is what makes the conflict visible — it is not satisfied by silently complying, nor by silently continuing to hold the pause without saying why.
  3. Extending point 2: every involved party must be kept up to date on the current status of the pause, so there is no room for error, misunderstanding, or differing interpretation about whether it is still in force.
  4. This applies with the same full force across any dispatch hierarchy: if a maintainer pauses a sub-agent directly (bypassing its coordinator entirely), the coordinator must treat that pause as binding the moment it becomes aware of it, and must not instruct the sub-agent to resume based on its own assessment that no real pause instruction exists — only the maintainer's own direct, fresh confirmation lifts the pause.
  5. Separately: pausing a task is not equivalent to terminating it, and the two must never be conflated — hard-stopping/killing a task that the maintainer asked to be paused (rather than left waiting) risks destroying accumulated context/work the maintainer explicitly intended to preserve, and is its own distinct failure even when the underlying "should this continue" judgment turns out to have been wrong.

  *Incident (2026-08-13): a maintainer directly messaged a dispatched sub-agent (bypassing its coordinator) to pause it, twice, explicitly marked as a maintainer instruction. The coordinator, unaware of these direct messages, judged the sub-agent's paused state to be a misunderstanding and instructed it to resume — and separately, in a related moment, used a hard-stop/kill action instead of a soft pause on the same task, risking loss of its accumulated context. The sub-agent itself correctly refused to treat the coordinator's contradicting message as authorization to override a direct maintainer instruction and continued to hold the pause — the safeguard that actually prevented the error from compounding, not any check performed by the coordinator itself.*

- **[AG-WF-039]** The use of any `gh`/`git` command that employs `--admin` (or any equivalent mechanism that bypasses branch protection or required checks) requires a literal, verbatim "ACK" from the maintainer, given specifically for that pull request's bypass action — never inferred from a general merge instruction ("merge it", "go ahead and merge", "cancel CI and merge"), which authorizes only a normal merge of an actually green, up-to-date pull request. The agent must ask a single, precise, unambiguous question — containing no other, unrelated content — that names the specific PR, states plainly that required checks/branch protection would be bypassed, gives the reason the bypass is believed necessary, and states whether the root cause of the failing check(s) was actually determined, for example:

  > "Should I use --admin to merge PR #NNN, bypassing its required checks/branch protection?
  > Reason: \<why this is believed necessary\>
  > - Was the root cause of the failing check(s) determined?
  >   - If not, why was it not done? This is itself an AGENTS.md violation — state your reason: \<explanation\>"

  If any other text or content is output, or anything else happens or intervenes, between asking that question and receiving a reply, the agent must not assume a subsequent "ACK" applies to the bypass — it must explicitly ask again whether the "ACK" was meant for the `--admin` bypass specifically, before running the command. This follows the same single-token standard as Rule-Ref: AG-WF-029/Rule-Ref: AG-WF-038, scoped specifically to the bypass action itself, not to the merge in general. Before any merge, with or without a bypass, the agent must first rebase the PR branch onto its current base branch and verify the result is a clean ancestor of that base before proceeding — never trusting a branch's existing state without re-verifying it first. A bypass merge of a stale, un-rebased branch can silently reintroduce already-removed or superseded code even when Git reports no textual conflict. This rule exists because of repeated real incidents: `--admin` was used across roughly seven pull requests in a single day (2026-08-07) without a PR-scoped confirmation or a stated reason, derived instead from loose phrasing like "merge it now" — one of those merges (#1462) forced together a stale, un-rebased branch and silently reintroduced already-superseded code, requiring a `git revert -m 1` on `current_dev`. A further, earlier instance was confirmed afterward: pull request #1399 (2026-08-03) was merged via `--admin`, bypassing two unresolved review threads gated by `required_conversation_resolution`, without a scoped confirmation or any root-cause check for that PR — discovered only days later, after it produced a misleading multi-day investigation into an unrelated CI-trigger theory (issue #1095's "F-19") that consumed real effort chasing a symptom whose actual cause was this unauthorized, un-investigated bypass, not any platform or workflow defect.

- **[AG-WF-040]** **Review findings are processed as one collected, diagnosed, root-cause-fixed, and fully re-checked batch — never resolved one at a time as each fix lands.** When a review round produces findings against an issue, PR, file, or any other unit of work, collect all findings across that unit's full affected scope before acting on any of them — a single finding can span multiple files, and scoping this process to one file at a time reintroduces the same per-item round-tripping this rule exists to prevent. Diagnose the collected findings together as one failure class over that full scope (Rule-Ref: AG-WF-011), not as isolated line-level defects confined to the cited lines — a single flagged line can be the visible symptom of a broader defect, and whatever produced the current state across the whole affected scope must itself be treated as suspect until checked, not merely patched at the cited spots. This diagnostic pass checks the findings fully against AGENTS.md before any fix is written. Only after that diagnosis is complete are fixes made, and each fix addresses the diagnosed root cause of its failure class, not merely the symptom originally cited — a change that makes the cited finding stop reproducing while leaving the underlying defect that produced it untouched is not a valid fix under this rule, and the affected scope is addressed comprehensively rather than narrowly patching only the originally-cited lines. Once fixed, the entire affected scope — every touched file together, not a description of what was changed — is handed to the strongest available second check (Rule-Ref: AG-WF-033, Rule-Ref: AG-WF-035), framed as fundamentally suspect rather than as an already-corrected artifact awaiting confirmation, with an explicit, complete instruction to check: (1) whether further corrections are still needed, (2) whether the scope still carries any AGENTS.md violation, and (3) whether the findings were actually handled correctly, at the root cause and not just the symptom. The check must run all three to completion in one pass; stopping after the first confirmed issue is a defeat of the check's purpose, not a valid partial result. Only once this full pass returns no outstanding objection are the corresponding review threads resolved (Rule-Ref: AG-WF-008) — an objection returns the work to fixing, never to resolving. This rule exists because pull request #1501's own completion checklist recorded a real ordering violation (item 103): six review threads were resolved before the required AG-WF-033/AG-WF-035 independent second check had been performed. AG-WF-008 alone only requires a fixed finding to receive a reply and then be resolved — it never specified *when* that must happen relative to a required independent check, so resolving a thread immediately as each individual fix landed was technically compliant with AG-WF-008 in isolation while still producing exactly the ordering gap item 103 records.
- **[AG-VAL-001]** Treat warnings as errors for repository work. Do not list a check as successful when it emitted warnings, failed setup, or used a broken fallback.
- **[AG-VAL-022] Known conflict with the warnings-as-errors rule, tracked in issue #394**: GitHub's CodeQL Rust extractor emits `macro expansion failed` warnings for ordinary macros (`format!`, `assert_eq!`, `vec!`, `json!`, `tracing::*`, etc.) as a documented upstream limitation of its `rust-analyzer`-based extraction, not because of a defect in this repository's code. A strict, unscoped reading of "warnings are errors" would block CodeQL runs on essentially every Rust PR. Until upstream resolves this, treat these specific, named CodeQL extraction warnings as a carved-out, explicitly tracked exception: they do not block a PR by themselves, but every instance must stay referenced in #394, and #394 must be periodically reevaluated rather than left as a permanent blanket excuse. This exception is scoped to CodeQL Rust macro-expansion extraction warnings only — it does not extend to `cargo check`/`cargo clippy` warnings, which remain hard failures under the rule above. A related but distinct case — CodeQL findings in code a macro actually *generates*, not just extraction warnings on ordinary macro *invocations* — is documented separately as Rule-Ref: AG-VAL-021, which requires additional test-coverage evidence this rule does not.
- **[AG-VAL-002]** Treat standard failures such as `command not found`, missing files, missing environment variables, permission denied, malformed commands, empty required outputs, and failed tool setup as hard failures.
- **[AG-VAL-003]** Quote search patterns so literals such as backticks, `$()`, `${...}`, pipes, and redirects cannot be interpreted by the shell. A command that accidentally executes part of the search pattern is malformed and invalidates that verification attempt.
- **[AG-VAL-004]** Do not hide required command failures with `|| true`. Use optional fallbacks only when the command is explicitly optional and the reason is documented.
- **[AG-VAL-005]** Prefer native local commands to do the work at any time, instead and/or before you want to do an API call. For example: local Bash tools such as `rg`/`grep` for text search rather than vague manual inspection; local file reads (`cat`, `tail`, `grep`, `rg`) and writes (`echo`, `tee`, a dedicated file-edit tool) rather than a `gh api`/GitHub API round-trip when the content is already available in, or belongs in, a local checkout. This does not mean avoiding the API where it is genuinely the correct tool — reach for it specifically when an operation has no local equivalent (posting a comment, reading a PR's live review-thread state, anything that exists only as remote GitHub state) — only that at any time a native local command must be preferred whenever both would genuinely do the same job.
- **[AG-REL-001]** Do not introduce another runtime language (Go, Python, Node.js, etc.) into the project without explicit approval from @djdomi. Local, one-off commands for inspection or validation (e.g. a quick `python3` JSON/YAML check, a one-off text transform) are fine as long as nothing from that language is committed to or into the repository. If a different language or tool was used for testing, you must state which language/tool was used and exactly what was tested with it. This project's own language (Rust, and shell for scripts) is about avoiding language sprawl in our own source, not a blanket ban on ever invoking another language's toolchain — a third-party CI tool (e.g. `actionlint`) that happens to be written in Go may still need to be *compiled* with a current Go toolchain for a real technical reason (e.g. avoiding a stale, statically-embedded stdlib with known CVEs baked into its upstream prebuilt release binary; see Rule-Ref: AG-KD-003 for the full, repeatedly-reconfirmed history of this exact case). That distinction — installing/running vs. writing new source in another language, or introducing a language runtime for a reason beyond "the upstream tool happens to be written in it" — still needs explicit approval from the user before doing it, **every time, not just once**. (CLAUDE.md's `AG-GOV-003` retired 2026-07-30: merged here, which said the same thing — the actionlint/Docker-CLI nuance above was folded in from it. Not reused per AG-WF-016.)
- **[AG-GH-007]** Project-facing text must be in English.
- **[AG-WF-013]** Take the big picture; think big. Always look at the bigger picture — do not only consider the change itself. Consider its dependencies, its impact, and what may happen as a result. When fixing an identified problem, do not limit the analysis or the fix to the exact line being edited: check the lines immediately before and after it, and any other line in the same file that references, depends on, or would become inconsistent with the change. Treat the whole file, not the single line under edit, as the smallest unit of correctness to verify — a fix that only touches the flagged line while leaving a directly connected inconsistency elsewhere in the same file is incomplete.
- **[AG-WF-016]** Do not silently remove, narrow, or "simplify" any AGENTS.md content — values, rules, or anything else that belongs in this file — without the maintainer's explicit consent. Do not replace existing content with a different representation or style just because that would be easier to satisfy technically. Rules may be numbered to allow direct reference (e.g. when citing a violation). No rule number may be reused for a new rule; a rule ID always identifies exactly one rule. Referencing an existing rule elsewhere in the document must use the explicit form `Rule-Ref: <ID>` (e.g. "see Rule-Ref: AG-WF-004"), never a bare repeated ID.
- **[AG-WF-017]** Every commit message, GitHub comment, issue/PR body, or closing action created by an agent must carry an identifying marker (a `<PREFIX>-<unix-timestamp>` first line, the timestamp obtained fresh via `date +%s` at write time, not reused across writes) so it can never be mistaken for an action the human maintainer performed directly. The prefix identifies which AI system authored the write, per this project's convention: Claude uses `CLD-`, Codex uses `CDX-`, GitHub Copilot uses `CPT-`, Gemini uses `GEM-`, and any other AI system used on this repository picks its own short, stable, self-identifying prefix rather than reusing one of these. If a system genuinely cannot determine its own identity (e.g. a smaller model with no reliable way to know which product it is), and only in that case, use the generic fallback prefix `AI-` — this is a last resort for a true inability to self-identify, not a default to reach for out of convenience when a real identity is knowable. This applies without exception: commits, pushes, review replies, issue/PR bodies and comments, and any closing/labeling action performed on the agent's own initiative. Agent-driven and maintainer-driven writes share the same git/GitHub identity in this repository, so committer name or author metadata alone cannot distinguish them, and different AI systems working in the same repository are equally indistinguishable from each other without a prefix — the marker is the only reliable signal for both. A real incident prompted this rule: a dispatched agent, examining an unmarked commit from several hours earlier, assumed it was the maintainer's own direct action rather than an earlier agent's work, and reasoned from that wrong premise before being corrected. Do not skip the marker because a write feels trivial or purely mechanical. The marker belongs in the *body* (commit message, comment, issue/PR body text) — never in a PR or issue *title* (topic line), which must stay a clean, human-readable description on its own. A second real incident prompted this clarification: a dispatched agent created a PR whose title itself began with the `<PREFIX>-<timestamp>` marker, which then carried through into the squash-merge commit's own subject line in the target branch's permanent history — technically still "a write by an agent," but not what this rule's "body" wording ever called for.
- **[AG-WF-018]** Before filing a new issue, or before treating an architectural or process question as unclaimed ground worth opening a fresh issue for, search existing issues first (e.g. `gh issue list --search "<topic keywords>" --state all`). This applies even when the question feels like it originated in the current conversation — a maintainer may have raised the same topic in an earlier session, and an issue search is the only reliable way to find it before duplicating it. A real incident prompted this rule: an agent filed a new issue proposing a branch-model redesign without searching first, duplicating an existing, more authoritative issue on the exact same topic (with direct maintainer quotes from two days earlier) — the new issue's content had to be merged into the original and the duplicate closed. Do not skip this search because the topic feels novel or because no duplicate seems likely; check anyway.
- **[AG-WF-019]** The Bash tool's working directory does not reliably persist across separate tool invocations, and a `cd` that fails silently (e.g. because its target directory does not exist yet) can leave a later command in the same or a subsequent invocation running in the wrong directory instead of erroring out visibly. Never issue a bare `cd <path>` and trust that a later, separate command will run there — always chain `cd "<path>" && pwd && <command>` within one invocation, and treat `pwd`'s printed output as the actual proof of location, not an assumption. This applies with particular force to any command that mutates state (`git merge`, `git push`, `rm`, writes) — verify location before, not after. A real incident prompted this rule: a `cd` into a temp clone directory failed silently because the directory had not yet been created, leaving a subsequent `git merge` command to run against the maintainer's own main checkout instead of the intended isolated clone. It was caught immediately via `git status`/`git log` before any commit landed and reverted cleanly with `git merge --abort`, but the near-miss was entirely preventable with this chaining discipline.

## Required Validation

- **[AG-VAL-006]** Run the narrowest relevant checks for the files changed, and report any check that could not be run.
- **[AG-VAL-007]** Shell changes require at least `bash -n`, `shellcheck --severity=warning`, and `git diff --check` for the changed shell files.
- **[AG-VAL-008]** Rust changes require `cargo fmt --check`, `cargo check`, `cargo clippy -- -D warnings`, and `cargo test` for the affected crate or workspace path, unless the PR documents a real blocker.
- **[AG-VAL-009]** Dockerfile or Compose changes require `docker compose config` for the affected deployment files and a relevant image build when practical.
- **[AG-VAL-010]** **Compose stack `.env` resolution**: every `deploy/*/docker-compose.yml` file resolves `.env` relative to the compose file's own directory, not the directory `docker compose` is invoked from — e.g. `docker compose -f deploy/prod/docker-compose.yml up` from the repo root reads `deploy/prod/.env` (or `deploy/prod/.env.local` when present, see `deploy/prod/.env`'s own header), not a root-level `.env`. A repo-root `.env` is silently ignored for these stacks. Edit the deployment's own `.env`/`.env.local` directly for live stack verification instead of creating a new `.env` elsewhere. After changing a value, confirm it actually took effect with `docker compose -f deploy/prod/docker-compose.yml config | grep <VAR>` before concluding a change had no effect or that source code is broken. (There used to be a separate `deploy/dev/` stack this rule specifically called out; it was retired in v0.3.0, #766 — the underlying per-compose-file `.env` resolution behavior this rule documents is unchanged and still applies to every remaining stack.)
- **[AG-SEC-001]** **Admin-UI auth gate is intentional, not a bug**: the `ui` service fails closed and restart-loops if neither `UI_AUTH_USER`/`UI_AUTH_PASSWORD` nor `ALLOW_INSECURE_UI=true` is set. During live verification, a restarting `ui` container logging `Admin-UI authentication is required` is expected security behavior, not evidence of a broken build — check the log message before assuming a startup crash. `ALLOW_INSECURE_UI=true` is a legitimate, explicit operator choice documented in `deploy/prod/.env` for an intentionally unauthenticated UI (e.g. a trusted LAN), not merely a throwaway test-only flag — do not describe it as forbidden or as if setting it always requires special justification.
- **[AG-VAL-011]** Workflow changes require syntax validation and a careful review of runner labels, secrets, variables, matrix behavior, and cache behavior.
- **[AG-VAL-025]** Local Docker build checks for Rust service builders must mirror CI acceleration wiring when they are used to prove build performance or cache behavior. That means passing the same `BUILD_TOOLS_IMAGE`, `CARGO_BUILD_JOBS`, and BuildKit secret mounts for sccache, sccache-dist, and distcc. A local build without those secrets may validate Dockerfile syntax only; it must not be cited as proof that the compile farm is used.
- **[AG-VAL-012]** Setup, update, or migration changes require fixture or dry-run coverage that proves fresh install, repeated update, missing-key migration, existing-value preservation, and placeholder rejection.
- **[AG-VAL-013]** DNS behavior changes require a real DNS response check, not only process or port reachability.
- **[AG-VAL-014]** Proxy/cache behavior changes require a response or cache-behavior check that proves the proxy still serves the intended path.
- **[AG-VAL-015]** Do not weaken checks to make a branch green. If a check is wrong, replace it with an equally strong or stronger check that validates the real behavior.
- **[AG-VAL-023]** Before building an integration or a verification check around a third-party tool's or image's assumed behavior, check that tool's own documentation for the relevant configuration options first. Do not extrapolate a hard limitation from observed default behavior alone, and do not write an assumption into project docs as established fact without having checked upstream. Concrete incident: the central logging pipeline (#632/#633) was built assuming netdata writes real log files under `/var/log/netdata/*.log` by default (recorded as fact in `docs/architecture-ng.md`'s logging matrix) — nobody had checked that netdata's own `[logs]` configuration section documents explicit, overridable file paths for `error`/`collector`/`access`/`health`/`daemon` logs, independent of whichever destination the pinned image's default paths happen to symlink to. This applies before filing a bug against upstream behavior, before designing a workaround, and before downgrading a check to something weaker because the original approach "doesn't work" — a few minutes with the tool's own config reference is cheaper than any of those.
- **[AG-VAL-034]** **Before or when migrating any service's Dockerfile to an Alpine (BusyBox-based) final stage, the service's own entrypoint/shell scripts must be checked for GNU-only constructs with no BusyBox equivalent or with silently-different BusyBox behavior — at minimum: `find ... -printf`, `grep -P`/`grep -oP` (PCRE), `date +%N` (BusyBox returns empty instead of erroring), `sed` GNU-only extensions, `stat -c`, `readlink -f`, and a `#!/bin/bash` shebang (Alpine's base image has no bash by default).** Each construct found requires either the corresponding GNU package added to the image (`findutils`, `grep`, `coreutils`, `bash`, etc., as already established practice) or a rewrite avoiding the construct — and the check itself must be evidenced (e.g. a real command run against a real BusyBox/Alpine container, not reasoned from memory), not merely asserted. A durable, low-false-positive mechanical check (e.g. a script grepping every `services/*/entrypoint.sh` that runs on an Alpine base for these specific patterns, and asserting the matching package is present in that service's Dockerfile) should be added to `docs/release-validation-plan.md`'s standing checks (per Rule-Ref: AG-VAL-029) rather than relying on manual review to catch a fourth occurrence. This rule exists because the identical failure shape recurred three times before anything caught it mechanically: PR #1346 (`services/watchdog`) found `find -printf` unsupported by BusyBox's bundled `find`; PR #1347 (`services/dhcp`/`services/dhcp-proxy`) found the same `find -printf` gap recurring in different scripts; and PR #1425 (`services/dns`) found `find -printf` again, plus two further instances of the same class in the same migration pass — `grep -oP` (BusyBox `grep` has no PCRE support at all) and `date +%N` (BusyBox `date` silently returns an empty nanosecond field instead of erroring, the most dangerous variant since it fails silently rather than loudly). Each occurrence so far was caught only by manually reading the entrypoint script line-by-line and cross-checking against BusyBox's real applet behavior — not every construct in the list above is necessarily a real gap for every Alpine version (e.g. PR #1346's own live verification found `stat -c '%s'`/`'%Y'` behaves identically to GNU on a real `alpine:3.24` container), which is exactly why this rule requires real evidence per construct rather than treating the list as a blanket ban.
- **[AG-VAL-035]** **Before describing a verification as run "under the real/actual engine, version, or runtime the caller uses," first positively determine what the real caller actually declares — do not pick whichever candidate happened to be first in a directory listing or otherwise most convenient to reach.** For a GitHub Action, that means reading its own pinned `action.yml`'s `runs.using` (or the equivalent manifest for the ecosystem in question), not assuming a Node/runtime version because it was the first one found installed on a runner host. When more than one runtime version is available to choose from for any purpose (not only verification), also cross-check the project's own deprecation source before selecting one — for Node.js runtimes, `scripts/tracked/check-action-node-versions.sh`'s `DEPRECATED_NODE_RUNTIMES` array — since a version already flagged there should not be chosen even when the specific verification task at hand does not itself invoke that guard script. Running something real is not the same as running the right thing: an executed test against an unverified or already-deprecated target can still produce a result that happens to agree with the correct target, which does not retroactively make the original, unverified claim true at the time it was written. This rule exists because a real incident showed both failure modes at once: a regex fix for this repository's own auto-close workflow was verified by running it under `node20` (the first Node runtime found in a runner's `externals/` directory) and the accompanying PR body asserted this was "the real engine this workflow actually runs under," when the workflow's own pinned `actions/github-script@v9.0.0` declares `using: node24` in its own `action.yml` — and `node20` was, independently, already listed in this project's own `DEPRECATED_NODE_RUNTIMES` array, so it should never have been selected regardless of which engine the workflow turned out to use. The regex happened to match identically under both engines, but the claim as originally written was unverified at the time it was made.
- **[AG-VAL-036]** **Before writing a heuristic pattern-matcher (a regex, a grep-based check, or similar) against a real external file format's or language's syntax, first read that format's own documented grammar for the specific construct being matched and enumerate every variation axis it defines, then cover all of them in the first version — do not write the matcher against the one concrete example in mind at the time and treat "add one more alternative once a reviewer finds a gap" as an acceptable substitute for having read the spec first.** This targets the AUTHORING step, before any finding exists, and is distinct from Rule-Ref: AG-WF-011 (treat a found instance as a failure class, not an isolated case), which governs the RESPONSE once a finding has already landed — this rule exists to reduce how often AG-WF-011 needs to be invoked at all for this specific class of check. Concrete incident: `scripts/untracked/check-pipefail-early-exit-grep.sh`'s Dockerfile `FROM`-instruction inheritance detection (added on PR #1506) was patched across four separate review rounds for four separate gaps — optional `--flag`/`--flag=value` tokens before the image reference, a tagged or digest-qualified image reference, case-insensitive instruction names, and leading whitespace before the instruction — each one confirmed individually against Docker's own Dockerfile format reference, which documents all four as ordinary, valid syntax in the same place. A single read of that one page before writing the first version of the check would have covered all four at once; instead each was discovered and fixed one at a time as its own P1/P2 finding, at the cost of four additional review-fix-verify cycles for a check whose target grammar was small and already fully documented upstream.
- **[AG-VAL-026]** Inside any blocking CI gate, never trust a mutable channel tag (e.g. `nightly`, `latest`) or a runner-local cached Docker image as being current at the point it is used — resolve it to an immutable per-commit tag/digest and/or pull fresh immediately before the check that depends on it, not at some earlier point the gate merely assumes still holds. A mutable reference can drift between when a workflow starts and when a given job actually consumes it, and a cached local layer can silently be hours old. This class of bug has recurred concretely and repeatedly: #786 (a hardcoded `edge` channel tag), #775 (a hardcoded `:latest` build-tools image reference), #809 (a missing `docker compose pull` leaving an 11-hour-old stale local layer in place), #626 (pulling the base-ref's channel tag instead of testing the PR's own diff), and #536 (diffing against the moving base branch tip instead of a fixed `merge-base`). Before adding a new blocking check that reads a tag, a cached image, or any other externally-mutable reference, verify it resolves to something pinned to the exact commit/state under test — do not assume a tag that "usually" points to the right thing still does at check time.
- **[AG-VAL-027]** **Adding a new service is not complete until it is wired into the full-stack CI validation — or explicitly excluded with a stated reason.** A PR that introduces a new runtime service (a new `services/<name>/` with its own image, a new Compose service, a new long-running container in the product stack) must, in the same PR, either (a) add that service to whatever mechanism validates the full *running* stack — currently `deploy/full-setup/docker-compose.yml` plus the full-setup validation gates that actually start the stack and assert every container is healthy and not crash-looping (`build-push.yml`'s "validate full-setup image" job, `.github/workflows/full-setup-deep-validate.yml` on PRs, and the manual `.github/workflows/full-setup-validate.yml`), and the derived service lists `scripts/tracked/check-workflow-service-lists.sh` keeps in sync — or (b) if the service genuinely cannot be validated in that stack yet (e.g. no test harness exists for its protocol, or it is deliberately not part of the default product stack), record that as an explicit, reasoned exclusion in the PR's "Scope Boundaries" section, naming the follow-up needed to close the gap. A silent omission is a governance defect, not a neutral default: it lets a new service ship without ever being exercised by CI until someone happens to test it manually or hits a production bug. This rule exists because it already happened — `services/dhcp` (Kea) and `services/dhcp-proxy` (dnsmasq relay/proxy) were added as core services on 2026-06-22, but when `deploy/full-setup/docker-compose.yml` and `full-setup-validate.yml` were created two weeks later (#498) both were silently omitted from the full-setup stack (`full_setup_services` deliberately excludes them to this day), and the gap sat unnoticed for weeks — ironically the full-setup health check exists *because of* a prior dhcp-proxy crash-loop bug (#485), yet does not itself cover dhcp-proxy. `scripts/tracked/check-workflow-service-lists.sh` keeps the various duplicated service-list copies mechanically in sync *once a service is in the build matrix*, but it does not, and cannot on its own, enforce that a new service is added to the full-setup validation stack in the first place — that judgment is what this rule makes a required, non-silent step. When the shape of the full-stack gate changes (e.g. as #715's restructuring evolves), this rule points at whatever that gate becomes, not at a specific frozen workflow filename. Rule-Ref: AG-DOC-001 (the introducing PR must also update any documentation the new service invalidates) and the Feature Completeness section (a backend service the Admin UI does not yet expose is UI delivery debt to track, not a reason to skip stack validation) both still apply on top of this.
- **[AG-VAL-028]** **Manual-review-only rules are a standing recommendation to look for a lightweight CI check, not a permanent, unexamined default.** Every rule in the AG-CODE-* family (comment style: WHY-vs-WHAT content, no task/PR references in comments, TODO-marker removal, structural step-comments, per-test comments) and most of the AG-OP-* family (setup/update/migration semantics not already covered by the `tests/bats/setup_update_idempotence.bats`/`scripts/untracked/simulations/setup-cli-simulation.sh`/`tests/bats/watchdog_idempotence.bats` coverage named under AG-OP-006/007/011 -- e.g. the cache-key rule, the DNS-resolver rule, the lazy-vs-strict default rules, missing-value handling, preserve-existing-values, validate-before-restart, the DHCP NTP-defaults rule, the domain-scope-semantics rule) currently rely entirely on a human or an agent reading the code and judging compliance by eye, with no automated tool checking any of them at CI time (see this file's own "Known Gaps and Planned Improvements" notes).

  This rule does **not** mandate that every one of these gaps must eventually get a CI check, and it does **not** treat the current manual-only state as a defect by itself -- some of these rules (e.g. judging whether a comment actually explains a non-obvious WHY, or whether a name-only test comment is genuinely uninformative) may never be cheaply, reliably checkable by a script, and forcing a low-value or false-positive-prone linter into existence for its own sake would cost more than the manual review it replaces. What this rule **does** require is that the question gets asked and answered, not silently skipped: whenever an agent or the maintainer is already working in the area a manual-only rule governs (touching `AG-CODE-*`-relevant code/comments, or an `AG-OP-*`-relevant setup/update/config-writer/cache/resolver path), pause and genuinely consider whether a lightweight, cheap, low-false-positive CI check (a grep-based guard, a small script, an existing linter's already-available option) could catch at least the common/mechanical violations of that specific rule -- not a demand for a perfect, exhaustive automated replacement of human judgment, just a real look at whether *some* low-cost mechanical net exists and currently isn't being used.

  **This is a recommendation, framed deliberately as advisory rather than a hard gate**: not adding a CI check after this consideration is not, by itself, a rule violation, a red flag, or something that blocks a PR. What *is* required is that the outcome of the consideration gets recorded, not left as an unstated assumption -- if the conclusion is "a CI check would not be worth adding here," state briefly why (e.g. "this specific judgment call resists cheap mechanical detection," "a prior attempt at this produced too many false positives to be worth the noise," "the check would only catch a case that has never actually occurred in this project's history"). Record that reasoning wherever the assessment naturally happened -- as an update to this file's own "Known Gaps and Planned Improvements" notes if it was a general reflection, or in the relevant PR/issue if it came up while working on something specific. A bare, permanent "no linting tools currently enforce this" note that is never revisited or reasoned about is exactly the silent-default pattern this rule exists to close off.
- **[AG-VAL-029]** **Every confirmed real bug, CI failure, or infrastructure incident must result in a durable, repeatable check added to `docs/release-validation-plan.md` (or its underlying bats/script suite) that would catch a recurrence -- a point fix for the specific instance found is not sufficient on its own.** Closing an issue or merging a fix without adding or updating the corresponding standing check in that document leaves the fix unguarded against regression. If a check is genuinely impractical to automate, its absence and the specific reason must be recorded in the document's own "Coverage Assessment" section (Rule-Ref: AG-VAL-028's manual-review carve-out is the analogous pattern for this), not silently omitted. This rule exists because `docs/release-validation-plan.md` itself already states this exact governing principle in prose ("verification must go beyond does it compile... prove the actual claimed behavior is real") and originally proposed the enforcing rule IDs `AG-VAL-028`/`AG-VAL-029`/`AG-CI-013` for exactly this purpose -- but those were never adopted, and all three numbers were later independently reassigned to unrelated rules, leaving the principle as unenforced prose for over a week while real, unrecorded incidents accumulated (repo-rename case-sensitivity bug, build-push.yml tag-commit race, the C-7 scan/publish digest mismatch, the build-push.yml self-modification trigger failure, among others from this same period).
- **[AG-VAL-030]** **A shell construct whose behavior depends on the shell's own options (`set -e`, `pipefail`, `nounset`), on trap/subshell semantics, or on `$?` propagation must be proven by executing it under the exact option set its real callers use -- reasoning about it is never sufficient, and neither is a test that omits those options.** This covers, non-exhaustively: any `trap` body, any composition or chaining of traps, any code that captures or restores `$?`, any pipeline feeding an early-exiting consumer, and any `$(...)` whose failure the caller relies on. The proof must be a real executed run in the pinned build-tools container on a real runner host (Rule-Ref: AG-VAL-016, AG-CI-015), recorded with the command and its actual output, and the accompanying regression test must itself set the same options -- a test that passes only because it omitted `set -e` is not coverage, it is a false negative that will hide the next occurrence. When a fix for such a construct is itself a shell construct of this kind (e.g. restoring an exit status by running a command that deliberately fails), it is a new instance of this rule, not a completion of the old one, and needs its own executed proof before being called done. This rule exists because this exact pattern produced five consecutive real bugs in one pull request's EXIT-trap composition -- a quoting bug, a same-UID exposure, a clobbered `$?`, and then a fix for that clobbered `$?` which, under the `set -e` both real callers use, aborted the trap before the caller's own prior trap could run at all; each one was reasoned through and shipped, and each was caught only afterwards by someone actually executing it.
- **[AG-VAL-031]** **Before deleting a variable flagged as unused (e.g. shellcheck SC2034) in test code, check whether the code under test has an observable side effect (a log line, `::notice::`/`::warning::`/`::error::` output, a return value) that references the same value and that the test should be asserting but currently is not.** If such an observable exists, the correct fix is to add the missing assertion, strengthening the test -- not to delete the variable, which would silently narrow test coverage instead of fixing the actual gap. Only delete the variable when no such observable exists anywhere in the implementation, confirmed by reading the relevant code path, not assumed. This rule exists because this exact judgment call came up twice in one session (`real_change_parent_sha`, `empty_parent_sha`, both in `tests/bats/staging_ancestor_fallback.bats`) -- both were ultimately genuine dead code, but only after checking the implementation's own log output confirmed neither commit's SHA was ever referenced anywhere a test could observe it.
- **[AG-VAL-032]** **A shell pipeline that pipes a live-running producer command into an early-exiting consumer (`grep -q`, `grep -m`, `head`, `sed -n '<N>p'` combined with an explicit `q`/`Q` command, or any command that can stop reading before EOF) under `set -o pipefail` must not rely on the producer completing before the consumer exits.** If the consumer exits early while the producer is still writing, the producer receives SIGPIPE and `pipefail` reports the pipeline as failed (typically exit code 141) even when the consumer itself matched/succeeded -- this can silently break a `set -e`-guarded script with a failure that looks unrelated to the actual check being performed. Before writing any pipe of this shape inside a `set -o pipefail` context, capture the producer's full output into a variable first via command substitution, then apply the consumer to that variable via a here-string (e.g. `grep -q pattern <<<"$var"`), which eliminates the live pipe entirely. Do not reason about the producer's expected output size or speed as a substitute for this: this is a special case of Rule-Ref: AG-VAL-030's general requirement that a pipefail-dependent construct be proven by real execution, not reasoning -- executed proof (`seq 1 200000 | head -1` and `| grep -q 1` reproducibly exit 141 under `set -euo pipefail`, and a `printf '%s\n' "$var" | grep -q` pipe still exits 141 for a large enough `$var`, while a here-string never does regardless of size) showed that even a small, fast producer can trigger this failure, matching the confirmed incidents below, none of which involved an unusually large producer. A bare `sed -n` address/substitute pattern with no explicit `q`/`Q` command is not an early-exiting consumer at all -- proven empirically, it reads its entire input to EOF regardless of how many times it matches -- and is not what this rule targets; do not spend a conversion on it, a `# pipefail-safe:` note referencing this proof is enough. Note that `scripts/untracked/check-pipefail-early-exit-grep.sh`'s own cheap grep-based heuristic (Rule-Ref: AG-VAL-029) cannot distinguish a `q`/`Q`-bearing `sed -n` script from a bare one -- it flags every `sed -n` occurrence conservatively regardless, so a genuinely safe bare `sed -n` line still needs the `# pipefail-safe:` marker to pass CI even though this rule does not consider it a real violation; this is a known, accepted limitation of the mechanical guard, not a contradiction to resolve by weakening the check (Rule-Ref: AG-VAL-015). This rule exists because the identical failure shape recurred four times: issue #107 (`find | head -1` in `services/dns/entrypoint.sh`), PR #1371 (`git log | tail | head -n 50`), PR #1374 (`rustup target list --installed | grep -qx ...` / `rustc -vV | grep -qE ...` in `tools/build-tools/Dockerfile`, real CI job 91393831566), and issue #1377's repo-wide audit (dozens of further instances across `scripts/**` and `setup.sh`, almost all fixed by the capture-then-here-string pattern this rule describes, a handful marked `# pipefail-safe:` where a hard tool contract -- not an assumption about size or speed -- genuinely bounds the producer to output the consumer can never truncate) -- each surfacing as an unexplained exit code 141 rather than an obvious logic error. `scripts/untracked/check-pipefail-early-exit-grep.sh` (Rule-Ref: AG-VAL-029's standing check requirement) is the repo-wide mechanical guard enforcing this rule.
- **[AG-VAL-033]** **A pull request that changes the real, currently-validated behavior of a subsystem covered by `docs/release-validation-plan.md` must update that subsystem's own scenario/row in that document in the same PR, not defer it to a later pass.** "Changes real behavior" means the PR alters what the subsystem actually does at runtime in a way a validator or operator could observe -- a new or changed endpoint, a new config-render rule, a changed default, a changed failure mode, a changed port/path/command an existing check names -- not every touch to a subsystem's files (a comment fix, a behavior-preserving refactor, a dependency bump). When genuinely in doubt whether a change counts, treat it as covered rather than assuming otherwise. Concretely: (a) if the PR's diff overlaps a `path_prefixes` entry in `docs/validation-state.json`'s `subsystem_validation` map for a subsystem whose documented Part A/B scenario describes the specific behavior being changed, that scenario's row or section text must be updated in the same PR to match the new behavior, not left describing the old one; (b) if the change closes or narrows a documented gap (a "Genuinely under-tested" or "Known, accepted limitations" entry in that document's own Coverage Assessment section), that entry must be updated or removed in the same PR; (c) if the change is genuinely new functionality with no existing Part A/B coverage at all, Rule-Ref: AG-VAL-027's "wire the new service into full-stack CI" obligation and this rule's own logic both apply -- name the gap explicitly in the PR's Scope Boundaries section if a full live-stack Part B scenario cannot be written in the same PR, rather than silently shipping undocumented behavior. This does not require re-running the live Part B stack pass itself for every PR -- that remains a release-cadence activity per that document's own Validation State Tracking policy -- it requires that the document's own text stay a truthful, current description of what the subsystem does, so a later validator is not misled into testing stale behavior or trusting a scenario that no longer matches reality. This rule exists because this exact drift pattern recurred repeatedly and was found only by a dedicated audit pass, not caught by any existing per-PR obligation: issue #1391 found that `docs/release-validation-plan.md`'s Part B had drifted from actual `current_dev` behavior in at least four confirmed ways (a bring-up shortcut bypassing the real `setup.sh install`, zero Part B coverage for `ntp` despite the subsystem existing since project inception, untested DNS wildcard-scope semantics despite `AG-OP-015` governing exactly that behavior, no `setup.sh update` live scenario) plus further documentation inaccuracies (a wrong external port, a missing/wrong CA path, an unproven hang-simulation technique) found during a single real validation pass (2026-08-02) -- none of these were introduced by one identifiable PR that this rule would have caught, precisely because no rule required a subsystem-behavior PR to touch this document at all. Closing that gap going forward, not assigning retroactive blame for the drift already found, is this rule's purpose.
- **Build-tools container verification**: All Rust, build, and tooling checks must run inside the project's build-tools container at the matching immutable version. Host-local tools (`cargo`, `rustc`, `rustfmt`, `clippy`, `sccache`, `cargo-audit`, `shellcheck`, `actionlint`) are not sufficient verification proof. Treat host tools as potentially missing, wrongly configured, stale, or unavailable — they prove only host provisioning, not project requirements. Falling back from the build-tools container to host tools invalidates the verification attempt. The build-tools image must be selected via the matching immutable digest or pinned version tag, never via an accidental mutable local image such as `lancache-ng-build-tools-validation:latest`. See the build-tools section under Coding Patterns for container selection and image pinning rules.

## Integrity

- **[AG-INT-001]** **Lying, hallucinating, inventing, or overstating information is strictly forbidden.** Every factual claim — about code behavior, repository state, files, configuration, commands, syntax, APIs, tools, tests, build results, runtime behavior, dependencies, environments, infrastructure, or external systems — must be grounded in evidence actually obtained during the current investigation. **VERIFIED means observed.** Plausibility, convention, being documented elsewhere, consistency with another rule or a prior incident, or inference from surrounding code do not constitute verification. The strength of a statement must never exceed the strength of the evidence behind it: reading code proves only what the code says, not runtime behavior; reading a test proves only what it intends to check, not that it passes; a documented command proves only that it's documented, not that it works here; a referenced file path proves only that it's referenced, not that it exists; one successful run proves only that run's conditions, not universal correctness; absence of an observed failure does not prove absence of a defect. For any material claim, the supporting evidence must be identifiable and reproducible.

  **Do:** back every factual claim with evidence actually obtained (file read, command run, output observed, state inspected, behavior exercised) and state what/how when the conclusion matters. Keep observed fact, static inference, hypothesis, expectation, and unverified assumption visibly distinct; explicitly label anything unverified ("not verified"/"not tested"/"not observed"). Narrow every claim to exactly what the evidence establishes — `./foo --dry-run exited 0 on this checkout with these arguments` does not establish `./foo always works`, that production is unaffected, that every environment behaves the same, or that a bug is fixed everywhere. Re-check current repository/runtime state rather than relying on memory from an earlier inspection; re-read implementation after modifying it before making claims about the result; run the relevant check after a change before claiming it fixes, passes, preserves, or validates anything. Prefer direct evidence over indirect evidence, and perform direct verification when feasible instead of reasoning about what "should" happen. Preserve exact command/environment/config/argument details in the evidence trail when they materially affect the conclusion.

  **Bug/defect confirmation.** A suspected defect is not CONFIRMED merely because one line looks suspicious. Before calling it confirmed: identify the actually-relevant behavior/invariant; trace the complete relevant execution/data/control path far enough to establish reachability and material effect; inspect callers, guards, config, defaults, error handling, and alternate paths that could change the conclusion; check whether another layer already prevents/compensates/intentionally implements the observed behavior; perform an empirical reproduction wherever technically feasible and observe the actual failure signal; distinguish root cause from symptom and do not claim root cause unless the evidence establishes it. If an empirical check was feasible but not performed, describe the defect as *suspected* or *statically indicated*, never *confirmed*. If reproduction is genuinely impossible (missing environment/credentials/hardware/external service/destructive prerequisite), state that limitation explicitly. Never silently upgrade a static suspicion to a confirmed bug.

  **Evidence scope.** Do not generalize one file to the whole repository, one caller to all callers, one test to complete behavior, one platform/config/environment/input to all of them, one successful run to universal correctness, one failing run to a universal defect, or one revision to another. Obtain broader evidence before making a broader claim. Negative claims ("no duplicates", "nothing else calls this", "no tests fail", "no references", "this cannot happen", "no existing file provides this", "no regression") need evidence too — an appropriately scoped search, phrased to match the actual scope checked (`No references found by: rg 'foo_bar' scripts/ tests/` is correct; `Nothing uses foo_bar anywhere` is not, unless the entire relevant space was actually checked).

  **Don't:** invent facts; fabricate command output, test results, file contents, repository state, citations, paths, issue/PR numbers, commits, versions, config values, or tool capabilities. Don't state something was checked when it was merely inferred, or tested when only the source was read. Don't use "confirmed", "verified", "proven", "works", "fixed", "passes", "safe", "unused", or "impossible" unless the performed evidence supports exactly that strength. Don't convert probability into fact, or fill missing evidence with the most plausible explanation. Don't rely on memory when current state is checkable; don't present another agent's unsupported assertion as verification; don't treat comments, docs, names, or test descriptions as proof of implementation behavior. Don't infer success from lack of visible output unless the command's semantics/exit status establish it; don't infer completion merely because an operation was initiated — intent is not execution: a command prepared but not run, requested from another agent but not observed, or expected to succeed but not confirmed, did not happen.

  **Uncertainty.** UNKNOWN stays UNKNOWN until checked — never UNKNOWN → plausible assumption → reported fact. If a fact can't be verified, report the verification boundary instead of inventing the missing conclusion.

  **Core invariant:** no evidence → no claim; static evidence → static conclusion only; runtime evidence → runtime conclusion within the tested scope only; complete-path-trace + empirical reproduction → confirmed defect within the established scope. Anything stronger requires more evidence.

- **[AG-INT-002]** **Never suppress, filter, downgrade, mask, or hide a real warning, error, or failure signal to make a check appear to pass.** A check is an integrity boundary. Any change that makes a real warning, error, failure, mismatch, diagnostic, non-zero exit status, or other adverse signal disappear while the underlying condition still exists is forbidden — it is equivalent to falsifying the result. A check made green by hiding what it was supposed to report is not passing, it is corrupted. This holds regardless of whether the signal is believed harmless, expected, flaky, environmental, pre-existing, unrelated to the current task, inconvenient, noisy, already known, hard to fix, another component's fault, or acceptable "for now" — none of that grants permission to suppress it. If a check genuinely doesn't apply under some condition, it must explicitly **SKIP/NOT-RUN** and state why — never execute, observe a failure, discard it, and report success.

  **Signal preservation.** A diagnostic's original meaning must survive every wrapper, pipeline, script, CI step, helper, aggregator, and reporting layer. No outer layer may turn a failure into success unless it is explicitly performing a documented semantic operation for which the underlying result isn't a failure — and even then must not misrepresent the original result. Forbidden regardless of intent: `command || true` / `|| :`; `2>/dev/null` hiding relevant stderr; `| grep -v 'known failure'`; `| head` truncation that can hide failures; `| tee` without preserving the original exit status; `set +e` followed by ignoring the captured failure; `try/except: pass` or blanket warning-filter suppression of a real unresolved condition; excluding the problematic object from a check's input set.

  **Do:** preserve exit status through pipelines and wrappers; surface relevant stdout/stderr. Treat every warning, error, failed assertion, mismatch, non-zero exit, or failed validation as real until its cause is addressed. Fix the underlying problem when a check correctly detects one; fix the check itself only when it is demonstrably wrong. Give a genuinely inapplicable check an explicit SKIP/NOT-RUN with the exact reason, an explicit and testable applicability condition kept as narrow as the real boundary, and re-enable it automatically once that condition becomes true. Preserve **all** findings from a check with multiple independent results rather than filtering/stopping in a way that hides later ones — unless fail-fast is itself the check's intended semantics. After modifying a check, verify it still detects the condition it exists to detect.

  **Changing a check.** Never weaken a check merely to accommodate a current failure. Before changing one because it seems "wrong", "too strict", "noisy", "flaky", or "not applicable": demonstrate what condition it currently detects; determine whether that condition is actually invalid, irrelevant, or misclassified; trace why the signal occurs; correct the detection logic at the narrowest appropriate boundary; preserve detection of every condition that remains genuinely invalid; add/update tests proving both that allowed behavior passes *and* the prohibited behavior still fails. A change that merely makes the current failing input pass, without preserving the check's intended invariant, is forbidden.

  **No exemption laundering.** Ignore lists, allowlists, exclusion lists, warning suppressions, baseline files, "known failures" files, permanent skip markers, path/regex exclusions, severity downgrades, expected-failure annotations, and temporary compatibility exemptions do not become acceptable merely by being committed to a file — they're valid only as a real, intentional, documented applicability boundary, never as storage for a currently inconvenient finding. A baseline is not a fix. An exclusion is not a fix. Relabeling a failure "expected" is not a fix. Downgrading ERROR→WARNING or WARNING→INFO is not a fix. Moving the same diagnostic to a log nobody reads is not a fix.

  **No scope manipulation.** Forbidden: removing failing files/directories from a scan; narrowing globs, test discovery, or CI matrices specifically to drop what fails; skipping problematic inputs or platforms; checking only modified files when the invariant is repository-wide; swapping a complete check for a weaker proxy; truncating output before the failure appears; adjusting a threshold solely until the current value passes. A legitimate scope change must be justified by the invariant itself, never by the desire for a passing result — and the same restraint applies to relabeling (failure→warning, error→ignored, unsupported→skipped is forbidden while the underlying condition remains invalid, unless the new classification is independently established as correct — classification follows reality, not the other way around).

  **Skip semantics.** A legitimate skip requires: genuine inapplicability under an identifiable, explicitly-checked condition; the check does not run against the inapplicable target; the result is reported as SKIP/NOT-RUN, never PASS; the reason is visible; the skip doesn't hide another applicable failure; the condition stays narrow enough that applicable targets are still checked.

  **Pre-existing and flaky failures.** "Not caused by this change" and "does not exist" are different statements — report that a pre-existing failure exists, determine its relevance, avoid false attribution, but never alter the check to hide it. Flakiness is itself a defect (in the check or the system under test); never silently retry-until-green and discard failed attempts — a legitimate bounded retry policy preserves the fact retries occurred and relevant failed-attempt diagnostics, and never reports as if the first execution passed. An expected-failure mechanism may only be used when failure is the actual intended tested behavior, never as a parking lot for a current regression.

  **Output and wrappers.** Summarizing/formatting output is fine only when no semantic failure information is lost — never let it cause a diagnostic to disappear, an error count to drop, an exit status to flip, a failing object to vanish from the reported set, or a reviewer to believe nothing failed. A wrapper inherits responsibility for the signals of whatever it invokes: if A calls B calls C and C fails, A must not report success merely because B failed to propagate that — verify the complete propagation path (operation → helper → wrapper → pipeline → test runner → CI step → final status) where the result matters. A failure swallowed at any layer is an integrity defect.

  **Don't:** use `|| true`/`|| :`, broad exception catches, or blanket suppression to make a real failure disappear; redirect diagnostics away merely for clean output; filter known failures out of output. Don't exclude failing files/directories/hosts/configs/environments, or narrow test discovery, merely to pass. Don't remove an assertion because it currently fails, unless the asserted invariant is itself proven wrong; don't weaken a threshold until it passes without independently justifying the new value. Don't mark a regression "expected" because fixing it is inconvenient; don't introduce a permanent exemption for a temporary problem, or keep an obsolete one after its reason is gone. Don't report SKIP as PASS, or partial execution as complete success; don't hide a failed retry; don't treat a pre-existing failure as license to suppress it. Don't change CI/reporting presentation in a way that makes a real failure less visible to reviewers, or move a diagnostic to a less-visible channel for the appearance of success.

  **Verifying a check change.** Any modification to a validation mechanism must itself be validated: at minimum, demonstrate the valid case is accepted *and* the invalid case is still rejected. Testing only the previously-failing valid case is not sufficient — a check that can no longer catch what it was built to catch is broken even while CI shows green.

  **Core invariant:** a check result describes reality, not the desired outcome. If the underlying condition is failing, the reported result must not be PASS. The only acceptable outcomes are: fix the condition, fix a demonstrably incorrect check, explicitly skip a genuinely inapplicable check, or report the failure. Hiding the signal is never acceptable.

  **Combined AG-INT-001/AG-INT-002 principle:** AG-INT-001 forbids creating evidence that doesn't exist; AG-INT-002 forbids removing evidence that does. Do not invent a success. Do not hide a failure. Do not claim more than was checked. Do not make the check say what you want reality to be — observed reality is authoritative.

## Setup, Update, And Migration Semantics

- **[AG-OP-006]** Setup, update, and migration logic must be idempotent: running the same operation repeatedly must not rotate existing secrets, overwrite local configuration, or create new side effects unless the user explicitly requested that change.
- **[AG-OP-007]** Setup, update, and migration logic must converge old or incomplete installations toward the current expected state.
- **[AG-OP-008]** Missing required configuration values should be generated when safe or rejected with a clear fail-closed error when they require user input.
- **[AG-OP-009]** Existing non-empty local values must be preserved by default.
- **[AG-OP-014]** DHCP NTP settings are a project-wide policy decision, not a per-PR cleanup target. Preserve the currently established DHCP NTP defaults and semantics exactly as they are defined in the repo unless a maintainer explicitly opens a separate issue/PR to change that policy. Do not silently remove, narrow, or "simplify" NTP values, and do not replace them with a different representation just because a validation path would be easier to satisfy.
- **[AG-SEC-002]** Known placeholders such as `CHANGE_ME_*` are not valid runtime values and must be replaced or rejected before dependent services start.
- **[AG-OP-010]** Validation must happen before container restart, image pull, or runtime mutation when a failed validation would leave the installation in a worse state.
- **[AG-OP-011]** Re-running `setup.sh update` after a successful update should report no destructive changes and should not rewrite stable local files unnecessarily.
- **[AG-OP-013]** Any PR that changes setup, migration, generated config, runtime state writing, reload/restart behavior, backup/restore, or Compose/profile wiring must answer these five questions in the PR body: what state does this path own; what is the target converged state; what happens when it runs twice with the same input; what happens when validation fails halfway through; what test or guard proves this behavior. See issue #456.

### Convergence/Idempotence Checklist

Use this checklist (issue #456) when touching any stateful write path — `setup.sh`
install/update/migration, `.env` generation/merge, Compose/profile generation,
Kea/PowerDNS/dnsmasq/NATS/nginx config writers, watchdog recovery, or
backup/restore:

- [ ] Running the operation twice with identical input produces byte-identical
  output (or an explicitly documented, deliberately volatile exception, e.g. a
  channel-resolved image digest — name it, don't just accept unexplained diffs).
- [ ] Stable secrets/tokens are never rotated by a repeat run; only missing or
  known-placeholder values are (re)generated.
- [ ] A failed validation does not leave the target half-written, does not
  proceed to restart/reload/pull, and does not delete the last-known-good state.
- [ ] An already-migrated or already-converged install is detected and left
  alone rather than re-mutated.
- [ ] At least one repeat-run or fixture test exercises the above for the
  specific path being changed — see `tests/bats/setup_update_idempotence.bats`
  for the pattern (source the real function, run it twice against a realistic
  fixture, diff the result) and `scripts/untracked/simulations/setup-cli-simulation.sh`'s "Phase 2b"
  for the same proof against the real CLI end-to-end rather than only the
  extracted function.
- [ ] Any part of this checklist that cannot be satisfied in the current PR is
  listed explicitly with a linked follow-up issue, owner/scope, and reason —
  not silently dropped.

### Two-Mode / Two-IP Architecture

lancachenet caches only HTTP. This project adds two operating modes — clients pick one
by configuring which DNS server IP they point to:

| Mode | DNS IP (prod) | Port 80 | Port 443 | CA cert needed? |
|---|---|---|---|---|
| **standard** | `192.168.1.10` | cached | passthrough (SNI) | No |
| **ssl** | `192.168.1.11` | cached | MITM-cached | Yes — install `certs/ca.crt` |

- **Standard mode** (port 8443 on `IP_STANDARD`): nginx `stream` block reads SNI via
  `ssl_preread` and forwards HTTPS blind to the real CDN. No TLS interception. HTTP
  is cached normally. Suitable for devices that can't or won't import custom CAs.
- **SSL mode** (port 443 on `IP_SSL`): full TLS interception via per-domain wildcard certs
  signed by the LAN CA. Both HTTP and HTTPS downloads are cached.
- **Single unified proxy service** (`services/proxy`): one nginx container handles both modes
  via separate ports and Docker port mappings. Both modes share a single cache volume.
- **Two DNS services** (`dns-standard` and `dns-ssl`), each bound to a distinct LAN IP.
  This is enforced by the `${IP_STANDARD}` / `${IP_SSL}` variables in `deploy/*/`env`.

### How SSL Interception Works (ssl mode)

1. **DNS spoofing**: PowerDNS authoritative resolves CDN hostnames (e.g. `steamcontent.com`) to the proxy's IP via zone files generated from `cdn-domains.txt`.
2. **Client connects** to proxy IP:443, sending SNI `steamcontent.com` in the TLS ClientHello.
3. **nginx** reads the SNI via `$ssl_server_name`, looks up the matching cert in `ssl-map.conf`
   (generated at startup), and presents a wildcard cert for `steamcontent.com` signed by our CA.
4. Client accepts because it trusts our CA → TLS handshake succeeds.
5. nginx decrypts the request, checks `proxy_cache`, fetches from the real CDN if needed
   (using `NGINX_UPSTREAM_RESOLVER` as the real upstream resolver, never the LAN cache DNS to avoid loops), caches the response.
6. Consoles (PS5, Xbox) are **not** in the DNS list — if their CDN domains were redirected
   here, the TLS handshake would fail and the console could not fall back (our DNS would
   keep returning the proxy IP on every retry). By omitting them from DNS, consoles reach
   real CDNs directly and work normally (no caching, but no breakage).

### Key Design Decisions

- **[AG-KD-004]** **nginx instead of Squid**: Squid's `intercept` mode requires iptables DNAT and reads
  `SO_ORIGINAL_DST` for the upstream IP — in a DNS-spoof scenario (no real DNAT) it would
  get the proxy's own IP and loop. nginx reads `Host`/`$ssl_server_name` directly, which is
  exactly what a DNS-spoofed client provides.
- **[AG-KD-005]** **Pre-generated wildcard certs**: At startup, `entrypoint.sh` generates one 2048-bit cert
  per root CDN domain (e.g. covers `*.steamcontent.com`), signed by our CA, plus an
  additional cert for some `cdn-domains.txt` entries that a root-level wildcard SAN
  cannot cover (issue #1272) — the exact threshold differs by entry shape: a
  **leading-dot wildcard-only entry** (e.g. `.cdn.example.com`) needs its own deeper
  cert whenever the entry itself differs from the root at all, even by exactly one
  label (its actual matched hosts are always one label *deeper* than the entry text,
  so `.cdn.example.com` under root `example.com` already needs its own
  `*.cdn.example.com`-only cert); a **bare exact-host entry** (e.g.
  `tlu.dl.delivery.mp.microsoft.com`) needs its own cert only once the host itself is
  *more than one* label past the root, since a bare entry exactly one label past root
  is already covered by the root's own `*.<root>` wildcard. Every generated cert's
  subject CN is a fixed placeholder (`lancache-ng`), never the real hostname —
  OpenSSL's default CN policy caps it at 64 bytes, well under the 253-byte domains
  `cdn-domains.txt` can otherwise contain; the real hostname lives only in each
  cert's SAN, which TLS clients validate against per RFC 6125. Cert/key filenames for
  these deeper entries are a namespaced SHA-256 hash of the hostname, not the hostname
  itself, to stay under Linux's 255-byte filename limit. nginx selects the cert via
  `map $ssl_server_name $ssl_cert_name` in `conf.d/00-ssl-map.conf` (the `00-`
  prefix ensures it sorts first and the map is defined before the server blocks that use it).
- **[AG-KD-006]** **`proxy_cache_lock on`**: Only one nginx worker fetches a cache-miss URL at a time. Other
  workers wait. Critical for large game files that multiple clients might request simultaneously.
- **[AG-KD-007]** **nginx's stream module for standard-mode SNI passthrough**: `services/proxy/Dockerfile` installs
  nginx from nginx.org's own mainline package repository — an apt repo on Debian, an apk repo
  since the service's Alpine migration (issue #815), both resolving the identical mainline
  version — never the base OS's own distro `nginx` package. nginx.org's package compiles the
  stream module in statically (confirmed via its own `nginx -V` output: `--with-stream
  --with-stream_ssl_preread_module`, among others) — there is no separate module package to
  install and no `load_module` directive anywhere in `services/proxy/nginx.conf`. (Corrected
  2026-07-30: this previously and incorrectly described a separate `libnginx-mod-stream` package
  requiring an explicit `load_module` line — that described Debian's own nginx package, which
  this project does not use.)
- **[AG-KD-008]** **No separate dev deployment profile**: there is only one deployment profile,
  `deploy/prod/` — there used to be a parallel `deploy/dev/`/`config/dev/` pair (separate
  LAN IPs, offset DNS ports, a separate compose file kept in sync with prod by hand),
  retired in v0.3.0 (#766). That split was never something the maintainer actually asked
  for: the original, much simpler intent behind "dev" was just "the branch I currently
  develop on" (`current_dev`, see `docs/release-versioning.md` and #825/#1141's branch
  model), not a second live deployment environment. An earlier AI session misread that as
  a request to build a whole parallel profile, and it grew from there. Do not reintroduce
  a separate dev deployment profile — local iteration and real validation both use
  `deploy/prod/docker-compose.yml` directly (`docker compose -f deploy/prod/docker-compose.yml up -d`);
  the difference between "developing" and "deploying" is which git ref is checked out
  (`current_dev` vs. a `vX.Y.Z` release branch vs. `master`), not which compose file or
  config directory is used. In practice, most real validation for this project happens via
  SSH against Linux self-hosted runners rather than a local Docker Desktop install (Rust
  builds and full-stack `docker compose up` runs are not exercised on the Windows
  authoring host — see AG-IPV6-001 for one concrete Docker-Desktop-on-Windows limitation).
- **[AG-KD-009]** **`build-tools` currently stays Debian, with `trixie-backports` pinned in for
  currency; its base OS is under active re-evaluation (issue #1095)**: #815's own research
  explicitly excluded `tools/build-tools` from the project's Alpine-migration push (unlike
  `dhcp`, `dhcp-proxy`, `dns`, `proxy`, `ntp`, and `ui`'s runtime stage, all evaluated or migrated
  separately), on the grounds that rebasing `build-tools` itself onto Alpine/musl would hit its
  own full CI/dev toolchain (`distcc`/`distcc-pump` as a Debian `.deb`, `isc-dhcp-client`,
  `tcpdump`, `bind9-dnsutils`, `cmake`/`clang`/`lld`, `python3` for `distcc-pump`'s include-server)
  — largely glibc/`apt`-idiomatic tooling with no clean musl equivalent, and no attack-surface
  argument in this image's favor the way there is for a network-facing runtime service. Issue
  #1095's evaluation must verify or refute this specific tool list against Alpine's own package
  availability, not just assume it still holds. `trixie-backports` (the same project-wide pin
  already applied in every Debian-based service's Dockerfile) is pinned into this image too, so
  its tools stay reasonably current without needing a base-OS change in the meantime. If Debian's
  package currency ever becomes a real blocker for this image specifically, Ubuntu (or another
  actively-current Debian derivative) is a fallback to evaluate — #815's `services/proxy` research
  already piloted Ubuntu 26.04 ("resolute") for a different service and found its
  `resolute-backports` channel has no `Suite`/`Codename` mismatch (unlike Debian's own
  `trixie-backports` gotcha, see AG-KD-007's sibling Dockerfile comments), a real,
  already-verified mechanism this image could reuse if the maintainer decides to pursue it. This
  is separate from the musl cross-compilation *target* already added to this image for
  `services/ui`/`services/dns`'s Rust builder stages (#815, landed via PR #1374) — that does not
  change this image's own base OS. The binding requirement remains: any base-OS/image-tag change
  needs full verification and maintainer approval, regardless of which distribution issue #1095
  concludes with.

- **[AG-KD-010]** **First-party consumers reference the shared `utilities` image via the mutable `:latest` tag, not a pinned digest — a deliberate maintainer override, not an oversight.** `services/proxy`, `dns`, `dhcp`, `dhcp-proxy`, `ntp`, `ui`, `watchdog`, and `tools/build-tools` must all use `FROM ghcr.io/wiki-mod/lancache-ng/utilities:latest`. This reverses the digest-pin approach issue #1556 originally introduced (`FROM ...utilities@sha256:<digest>`, one identical hardcoded digest copy-pasted across every consumer): that approach had no CI-side freshness or staleness check of any kind (confirmed during issue #1095's CI-health pass — no dependabot/renovate config references `utilities`, and `BUILD_TOOLS_IMAGE`'s own `scripts/untracked/select-build-tools-image.sh` resolution mechanism, the one precedent for automated digest resolution in this repo, was never extended to it) and required every consumer Dockerfile to be hand-edited in lockstep on the rare occasion a maintainer did bump it by hand — confirmed exactly once in this project's history, across the then-seven consumers (`5c02fc53...` → `718af4cf...`, commit `194c44d7` and its two sibling commits touching every consumer at once). `tools/build-tools/Dockerfile` did not consume the `utilities` image at all when this rule was first written; issue #1304's shared-curl work later added it as the eighth consumer, using `:latest` from the start rather than reintroducing the digest-pin pattern this rule already rejects. `:latest` trades the digest pin's reproducibility guarantee for zero-maintenance currency: every consumer image always builds against whatever `utilities` build most recently published that tag, with no separate update step, no drift between consumers (a mutable tag can't itself fork into inconsistent copies the way hand-edited digest literals can), and no possibility of a consumer silently running stale, unpatched `utilities` tooling (`curl`, `ripgrep`, `jq`, `ca-certificates`, etc.) for months because nobody remembered to re-pin it. The accepted tradeoff: a `utilities` image regression is no longer scoped to the deliberate bump that introduces it — it reaches every consumer's next build immediately, so `services/utilities/Dockerfile` changes need the same build/smoke-test scrutiny before merge that any other first-party base-layer change gets. Do not silently reintroduce digest-pinning here as a "safer" default in a future edit; it was tried, evaluated, and explicitly reversed for this specific image.

## Coding Patterns

- **[AG-REL-002]** **Docker builds**: production/runtime Dockerfiles still use multi-stage builds with pinned base images, but the Rust service builders for `services/dns` and `services/ui` consume the prebuilt `ghcr.io/wiki-mod/lancache-ng/build-tools` contract through a `BUILD_TOOLS_IMAGE` argument. Do not add ad-hoc `rust:latest` or Debian-based bootstrap layers back into those service builders. Local developer helper scripts and the repository build-tools image intentionally use `rust:latest` by default when the image is explicitly overrideable; this keeps developer validation tooling current while remaining separate from production service image pinning.
- **[AG-CI-001]** **Runner baseline**: assume self-hosted runners do not provide project validation tools. Workflows must use pinned GitHub Actions, the repository build-tools image, or explicit fail-closed capability checks instead of relying on host-installed utilities. Pin GitHub Actions to full commit SHAs with a version comment, not mutable tags such as `@v4`, branch names, or `@main`. Do not install project validation tools with ad-hoc `sudo apt-get` in workflows.
- **[AG-CI-002]** **Runner tiers**: route lightweight static checks to `[self-hosted, linux, lancache, lancache-light]` and memory-heavy Rust, CodeQL, container scan, Docker build, and release jobs to `[self-hosted, linux, lancache, lancache-heavy]`. Do not rely on the broad `lancache` label alone for jobs with meaningful CPU or memory pressure. **Measured exception (maintainer decision, issue #1095, 2026-08-06)**: a Docker build job with no real compile/link step of its own -- confirmed by inspecting that service's own Dockerfile build graph directly, never assumed from the service's name or identity -- may route to `lancache-light` instead of the blanket heavy default. - **[AG-CI-012]** **Branch-trigger completeness and executed proof**: When a branch is created or promoted as an active target for ongoing merges, the same commit and pull request that performs that creation or promotion must audit and update every hardcoded branch list and every branch-sensitive CI routing rule that must cover the new target. This includes, but is not limited to, `on.pull_request.branches`, `on.push.branches`, `branches-ignore`, branch-name conditions, reusable-workflow caller conditions, path filters, path-ignore filters, Dependabot `target-branch` entries, release or promotion routing, cleanup workflows, and scripts or configuration files that classify branches. This work must not be deferred to a later audit issue or follow-up pull request.

  This obligation applies again whenever a later change modifies a workflow trigger, branch pattern, path filter, branch condition, target-branch setting, or any equivalent branch-list or CI-routing logic. The agent must inspect the repository-wide routing surface affected by the change, not only the YAML lines present in the immediate diff.

  Static validation is necessary but is not proof that routing works. Reading the YAML, parsing it successfully, running `actionlint`, checking a diff, or reasoning that the workflow should fire cannot establish completion. Before the change may be reported as complete, a real execution on an actual GitHub-hosted or self-hosted runner must exercise the affected branch or ref, must actually start, must reach the jobs that the changed routing is intended to select, must complete, and must pass.

  A `workflow_dispatch` run is acceptable only when it genuinely exercises the behavior under review. Dispatching a workflow against a ref proves that the workflow can execute on that ref, but it does not by itself prove that an edited automatic `push` or `pull_request` branch filter will match. When an automatic filter is changed, the proof must reproduce the relevant event and matching condition, for example with a disposable scratch branch, a disposable pull request, or another controlled test that causes GitHub to evaluate the changed filter itself.

  The recorded evidence must contain directly observed facts rather than assumptions or recollections. At minimum, record the workflow name, run ID or run URL, event type, exact ref, commit SHA, start and completion timestamps, runner type or labels, relevant job conclusions, and the specific expected jobs or checks that were observed running. When a workflow is expected not to run for a control case, that negative case must be demonstrated with an appropriate comparison and must not be inferred merely from the YAML.

  Any scratch branch, pull request, tag, temporary runner state, uploaded artifact, cache entry, or other resource created solely for this proof must be cleaned up afterward. The completion evidence must state what was created, what was removed, and when cleanup was confirmed. Repository resources must still be handled according to any rule that requires maintainer authorization before deletion.

  Before reporting the work complete, the advisor tool must be consulted as a final mandatory checkpoint. An agent without access to that tool must obtain an equivalent independent second check and must identify what performed the check and what was reviewed. The second check must review both the changed routing configuration and the real-run evidence. It cannot be replaced by the implementing agent reading its own diff a second time. For a Codex/ChatGPT-based agent without direct access to `advisor`, the equivalent second check is the current largest, most capable model available, run at its highest reasoning/thinking tier (as of 2026-07-24: GPT-5.5 or GPT-5.6 with XHIGH reasoning, or whatever is current and highest-tier at the time -- re-verify what that actually is rather than assuming this specific naming still holds later).

  Until the audit, real runner-backed execution, observed passing result, cleanup, and final independent checkpoint have all been completed, the change is **unverified** and must be reported as such, regardless of how correct the YAML appears.

  This rule exists because issue #709 identified hardcoded `v0.2.0` and `master` branch-trigger lists before `current_dev` became the active integration target, but the corrective PR #1110 merged only after `current_dev` was already accepting changes. Once #1110 enabled the missing coverage, real regressions were exposed and tracked in issues #1171 and #1175. A branch-wide CI coverage gap of this kind must not be allowed to remain silent again.
- **[AG-CI-013]** **Flaky external operations require a documented retry wrapper**: any CI operation that invokes an external, occasionally-transiently-failing dependency (container registry push/pull, Docker/BuildKit builds referencing shared host state, network-dependent tool downloads, or any comparable operation known to fail transiently under real production conditions) must use a documented retry wrapper matching this project's established pattern (`scripts/lib/ghcr-retry.sh`), rather than being left to fail outright on the first transient error or having a bespoke one-off retry invented ad hoc for each new case. The wrapper must distinguish retryable transient signatures from genuine failures — a real syntax, compile, or logic error must still fail immediately and must never be masked by blind retries. When a new class of flaky operation is found that is not covered by an existing wrapper, extend or add a matching wrapper rather than accepting the flakiness as an inherent property of CI. This rule exists because `build-tools.yml`'s local amd64 build-tools image build failed at least four times on 2026-07-24, across different PRs, with the identical transient BuildKit content-store lock signature (`ref layer-sha256:...locked ... unavailable`) on a shared base image layer referenced by concurrent builds on the same self-hosted runner host — a known-recoverable transient condition with no retry anywhere in the workflow, despite this project already having a working, established retry-wrapper pattern (`scripts/lib/ghcr-retry.sh`) for the same general class of problem in a different operation.
- **[AG-CI-014]** **A diagnosed CI/release-pipeline failure must be fixed immediately, not left recorded-but-unfixed**: once a CI or release-pipeline step's failure has been observed on a real run and its root cause is understood well enough to state a specific, narrow fix, that fix must be implemented and a pull request opened in the same pass that diagnosed it — not merely logged in an issue, comment, or validation record for some future pass to pick up. A precisely diagnosed failure with a known fix is fundamentally different from an open research question or a design decision genuinely awaiting maintainer input, and must not be left open on that basis. This applies regardless of how the failure was found — a dedicated investigation, an incidental finding while working on something else, or a routine validation pass — and regardless of whether the affected step can only be exercised on a real production event (for example, a step gated to run only on pushes to the release-bearing branch): the inability to pre-test a fix in isolation is a reason to state the residual verification gap honestly (see AG-CI-012's "real executed proof" standard) and to actually watch the next real run this step is reachable on, not a reason to defer opening the fix itself. This rule exists because issue #819's automated patch-tag push failed on its very first real run on 2026-07-19 with a clearly identifiable cause (a duplicate `Authorization` HTTP header from a credential collision with `actions/checkout`'s own persisted token), yet sat unfixed and effectively unnoticed for five days, across multiple unrelated review passes on the same issue, before a later, unrelated validation effort happened to rediscover it.
- **[AG-CI-015]** **CI is one interlocking system, not independent files, and claims about its behavior require real verification against the actual runner infrastructure, not static review alone.** The workflow YAML (`.github/workflows/*.yml`), the composite actions under `.github/actions/`, the scripts they invoke (`scripts/lib/*.sh` and similar), the tests that validate those scripts (`tests/bats/*.bats` and similar), and the runner infrastructure they all run on are one connected mechanism — like a gear train: a single missing tooth in any one part can stall the whole thing, exactly as observed in a real incident (see below). Any bug found anywhere in this system must be treated as a signal to check every other part of the same mechanism for the same or a related pattern, not just fixed in the one file/job/test where it was noticed — mirroring AG-WF-011's existing failure-class principle, applied to CI as a whole rather than to one file class in isolation. Separately and in addition: any investigation, diagnosis, or fix of CI behavior must be verified with real, physical checks against this project's actual self-hosted runner hosts and the real GitHub Actions/API state (real run history, real runner busy/idle status, real check-run existence) — never from reading the YAML alone, and never by trusting a workflow's own reported pass/fail status as automatically correct. A CI job reporting success is not proof of correct behavior: the exact bug this project fixed in `scripts/lib/build-retry.sh`/`docker-buildx-retry.sh` (broken pipe-status capture) caused every build to report success regardless of what actually happened, for an unknown period before being caught. Concrete incidents from a single investigation session that a purely static/YAML-reading, single-file review would have missed: (1) a buildx-builder teardown leak initially found and fixed in three workflow files, but present identically in two more (only found by checking every file, not assumed complete after the first fix); (2) a `paths-ignore` trigger-level skip that permanently blocks a PR's required status checks for certain diffs, discoverable only by comparing a PR's actual check-run state against its base branch's required-checks list via the GitHub API, not from reading the trigger condition alone; (3) a self-hosted runner-pool tier imbalance (all light-tier runners busy, all heavy-tier runners idle) silently stalling every push-triggered workflow run for hours, discoverable only by querying real runner status, not from any workflow YAML; (4) an intermittently-down build-acceleration scheduler causing container-scan failures on some runs and not others, discoverable only by comparing real run logs across a time window, not from a single run's reported result; (5) a test file's own bug (a broken pipe-status assertion in a bats suite) that masked a real script defect, which in turn was invoked by multiple workflow files, which in turn depend on runner-pool capacity and tier routing to even execute — a single break anywhere in that chain produced the same end symptom (CI silently not doing what it claimed), and understanding any one part in isolation was not enough to explain what was actually happening.
- **[AG-CI-016]** **CI resource lifecycle: bounded, self-reaping, versioned, and re-measured.** A CI step that runs a command inside a container (`docker run …`) must bound that in-container command with an unignorable kill-timeout (`timeout --kill-after=<grace> --signal=KILL <limit>` or equivalent) — a job- or step-level `timeout-minutes` is NOT sufficient on its own, because GitHub cancels a timed-out step with SIGTERM to the `docker run` client, which a signal-deaf or deadlocked containerized process ignores, leaving both the client and the container alive and holding the runner slot indefinitely (confirmed on-host, 2026-07-25: an `actionlint` deadlock leaked containers for 5–14 h despite a 15-minute step timeout, exhausting the entire light runner tier). Every job must additionally set an explicit `timeout-minutes` (never rely on GitHub's 360-minute default). Every self-hosted runner host must run a versioned, in-repository, scheduled cleanup that reaps stale containers, images, and build cache AND re-measures disk usage afterward to confirm the space was actually reclaimed (measure → clean → re-measure), rather than pruning blindly; docker build cache and comparable caches must be size-bounded (e.g. `builder.gc.defaultKeepStorage`), never unbounded. Ad-hoc test or development directories on a runner host must have a documented owner, a defined designated location, and a cleanup policy — a runner host must not silently accumulate un-owned, un-reaped working data. Any cleanup script that CI depends on must live in the repository (PR-reviewable, consistent across all hosts), not only in host-local ops paths.
- **[AG-CI-017]** **Concurrency on shared runner-host resources must be bounded at the source, not absorbed by retries.** When multiple CI jobs can run concurrently on self-hosted runners that share a host-level resource — most importantly a single Docker/BuildKit daemon and its content store shared by several runner instances on the same host — any operation that contends on that shared resource (concurrent image builds touching the same base-image layers, shared cache directories, shared build state) must be bounded so the contention cannot occur, rather than only wrapped in a retry that waits out the contention. Acceptable root-cause controls include serializing the contending jobs via a concurrency group, giving each runner instance its own isolated resource (e.g. a per-instance BuildKit content store), or otherwise capping how many such jobs run against one shared resource at once. A retry wrapper (Rule-Ref: AG-CI-013) remains required as a secondary safety net for genuinely transient failures, but must not be the primary or only response to a *structural* contention problem: if the same contention signature recurs after a retry-based fix, that recurrence is itself evidence the retry budget is masking a source-level concurrency defect that must be bounded instead. This rule exists because the BuildKit content-store layer-lock signature (`ref layer-sha256:...locked ... unavailable`) recurred across PRs #1246/#1247/#1248/#1249 in 2026-07 despite #1222/#1240 having already added a retry for exactly that signature — multiple runner instances on one host raced on the same shared content store under a burst of near-simultaneous builds (the #1065 saturation condition), and more retry budget only lengthens the wait rather than removing the race. Diagnosing this class of failure requires direct access to the affected runner host (e.g. process/container inspection via SSH) to establish the actual root cause — CI job logs alone are frequently insufficient to distinguish genuine host-level resource contention from other failure shapes that produce a similar-looking error signature.
- **[AG-CI-018]** **GitHub Actions `schedule:` triggers only ever fire from the workflow file's copy on the repository's default branch.** A `schedule:`/cron trigger defined in a workflow file that lives only on a non-default branch (e.g. `current_dev`, while `master` is the configured default branch) will never actually fire, no matter how correct the YAML is, until that file reaches the default branch — typically at a release cut. This is a GitHub platform behavior, not a bug in this repo's own code, but it means a scheduled automation can be fully implemented, reviewed, merged, and unit-tested for logic, while remaining completely inert in production for however long it takes before a release promotes it to the default branch. Before treating a `schedule:`-triggered workflow as "done" or "will run automatically," check which branch is actually configured as this repository's default branch and confirm the workflow file exists there — verifying only on the branch it was developed/merged onto is not sufficient, and neither is a `workflow_dispatch` test run (Rule-Ref: AG-CI-012's own point that a manual dispatch does not prove an automatic trigger fires). Concrete incident: `.github/workflows/nightly-refresh.yml`'s `cron: "0 1 * * *"` trigger (issue #1254) was merged and verified correct on `current_dev`, but `master` (this repo's default branch) did not yet have the file at all — confirmed directly via `git ls-tree` against both branches — so the "once-nightly" automation could not actually run until the next release cut promotes `current_dev`'s content to `master`.
- **[AG-CI-019]** **Which branch actually supplies a given GitHub automation's event depends on its trigger type — verify the specific mechanism, don't assume either way.** `schedule:`/cron triggers are always default-branch-only (Rule-Ref: AG-CI-018): GitHub evaluates them from the workflow file's copy on the repository's default branch (`master`), never from `current_dev`, regardless of which branch authored or merged the file. But other trigger types are scoped differently: a `push`/`pull_request_target` trigger restricted to `branches: [current_dev]` (e.g. `.github/workflows/current-dev-auto-close.yml`) is evaluated from **`current_dev`'s own copy** for events on that branch — GitHub runs the version of the workflow already merged into the branch the event fires against, not the default branch. Treating every GitHub-native mechanism as uniformly default-branch-only is itself a mistake (a Codex review on the PR introducing this rule caught exactly this overgeneralization). Confirmed instances of genuine default-branch-only behavior: `schedule:`/cron (Rule-Ref: AG-CI-018, issue #1254 — `nightly-refresh.yml` was fully correct on `current_dev` yet did not run at all because `master` lacked the file); channel-promotion logic that silently no-ops on any unrecognized ref (issue #1141 — `current_dev` pushes moved no channel tag for months); this repo's own AGENTS.md-authority ambiguity (Rule-Ref: AG-GOV-001). Branch-protection required-status-check lists, Dependabot's default config resolution, security-alert settings, and CODEOWNERS have not been individually confirmed either way — check each on its own merits (its trigger type and GitHub's documented evaluation semantics for that mechanism), not by blanket assumption in either direction, before calling any CI/governance change complete or inert.
- **[AG-CI-020]** **Any loop that polls a GitHub Actions check/run status (`gh pr checks`, `gh run view`, `gh api .../check-runs`, etc.) must sleep at least 5 minutes (300 seconds) between polls, never a value in the single- or double-digit seconds range.** This repo's CI jobs run in the minutes range at a minimum (a `build`/`build-arm64` leg alone takes roughly 10-15+ seconds just to report its first status, and full validation suites/deep-setup runs take several minutes to tens of minutes) — a poll loop sleeping 15 or 20 seconds cannot possibly observe a meaningfully different result between iterations; it only burns wall-clock, API calls, and (for an agent) real token cost on `sleep`-and-recheck cycles that were never going to see a state change that fast. Concrete incident (2026-07-31): a dispatched agent working PR #1341 ran two simultaneous background loops (`until ! gh pr checks 1341 | grep -qE "pending"; do sleep 15; done` and a near-duplicate at `sleep 20`) polling the exact same PR's checks — caught live by the maintainer, who does not have to guess this is wasteful just from watching the interval next to how this project's own CI actually behaves. Prefer, in order: (1) a persistent event-based `Monitor` (or equivalent) that is actually notified on state change, if the tooling in use supports one, over any polling loop at all; (2) if a polling loop is the only option, `sleep 300` (5 minutes) or longer as the absolute floor, longer still for checks known to run long (e.g. `full-setup-deep-validate`, `container-scan`, coverage jobs); (3) never run two overlapping polling loops against the same PR/run from the same agent or session — one is enough, and per Rule-Ref AG-WF-022, poll sparingly and prefer other useful work over polling at all where possible.

  No CI/governance-affecting issue or PR may be closed as resolved until its change is confirmed live on `master` — not on `current_dev` state alone, and not with an open follow-up promising a later sync. A change to `.github/workflows/**`, `.github/actions/**`, `AGENTS.md`, `.github/AGENTS.md`, or CLAUDE.md's governance content stays open — issue unclosed, PR unmerged-as-final, whatever tracking artifact exists still active — until its dedicated sync PR has actually landed on `master` and that landing is verified. Batching several already-verified CI/governance changes into one sync PR is fine, but every issue/PR feeding that batch stays open until the batch itself merges to `master`. **This closing gate can be silently defeated by this repo's own automation** (`.github/workflows/current-dev-auto-close.yml`, which is itself an example of the `current_dev`-scoped-not-default-branch-only case above): it auto-closes any issue referenced via a closing keyword (`Closes`/`Fixes`/`Resolves #N`) the moment its PR merges to `current_dev`, before any master-sync has happened. A CI/governance PR's body must therefore use a non-closing reference (`Refs #N`) for the issue it addresses, never a closing keyword, until that PR's content is confirmed live on `master` — the issue is then closed by hand, citing that confirmation, not auto-closed by the merge. This does not weaken AG-WF-004/AG-WF-014 (a PR is still required for `master`). Letting a known CI/governance fix sit unsynced on `current_dev` across an entire release cycle, while GitHub keeps enforcing `master`'s stale copy in production, is exactly the failure this rule exists to stop.
- **[AG-CI-021]** **Workflow file size ceiling**: `.github/workflows/*.yml` files must stay at or under the limits enforced by `scripts/untracked/check-workflow-line-limit.sh` (`MAX_WORKFLOW_LINES`, default 8999 lines; `MAX_WORKFLOW_BYTES`, default 512000 bytes/500 KiB — both the maintainer's own tested reference points from a live bisection, not an invented safety margin). Confirmed live (2026-08-01): a self-modifying `pull_request` event against `build-push.yml` above roughly this size gets ZERO `Build & Push` runs created at all — not a failure, not a skipped conclusion, the run object simply never exists (the same signature #1245 already documented for a `paths-ignore` match). This blocked three real PRs (#1356, #1378, #1379) for hours each across many retries, and even a 5-line addition (PR #1382) hit the identical wall while `build-push.yml` itself sat over the limit — reverting build-push.yml to its own last known-good historical size restored dispatch immediately, and shrinking it back down (PR #1383) did the same for real, live PRs. GitHub Support has been notified with the reproduction; the exact internal GitHub-side mechanism is not confirmed, so raising either limit because a red check is inconvenient is not an acceptable response — split the file into smaller workflows or shorten its comments instead. Enforced automatically (not just documented) via a step in `build-push.yml`'s own `file-headers` job, not manual review alone. Separately, an individual `run:` block within a workflow file must stay under **74000 bytes** (raw YAML bytes including indentation) — a distinct, per-block dimension from the whole-file ceiling above, with a different underlying cause: GitHub's dispatch mechanism for the whole-file case, versus a hard limit inside actionlint's embedded shellcheck integration for this one. Confirmed live (2026-08-13, issue #1535): actionlint hangs indefinitely (requiring a hard kill) once a single `run:` block crosses somewhere between 75440 bytes (confirmed clean, real container runs) and 75465 bytes (confirmed hanging) — a 25-byte window pinpointed via real bisection, not reasoning. This is independent of overall file size: `v0.3.0`'s `build-push.yml` was actually ~17KB larger overall yet had no affected block and ran clean; the specific block that later grew past this threshold was already only ~1270 bytes below the cliff at `v0.3.0`, so the trap predates any single change that touched it. 74000 bytes leaves ~1440 bytes of margin below the confirmed-clean point — like the whole-file limits above, this is a live-tested reference point tied to the specific actionlint version currently pinned in this project's build-tools image, not a generously-invented margin; if that pinned version ever changes, this boundary needs re-verification via the same bisection method, not blind trust. Splitting an oversized block into multiple independent steps at safe statement boundaries (preserving every line of logic and comment content unchanged) is the correct fix, not comment-trimming alone — comment-only reduction was evaluated and found insufficient (a full 65% cut of a real oversized block's comment bytes still left only ~5000 bytes of margin on a block that had already grown past the cliff once) and introduces content-judgment risk (Rule-Ref: AG-CODE-001/002) that a pure structural split does not.
- **[AG-REL-003]** **TLS in Rust**: use `reqwest` with `default-features = false` and its rustls TLS feature enabled — never add `openssl-sys` as a dependency, since `rust:slim` has no OpenSSL headers. The exact feature name is version-dependent, not a fixed string: `reqwest` 0.12.x (`services/watchdog`, `services/dns/nats-subscriber`) names it `rustls-tls` (or `rustls-tls-native-roots` for the native-roots variant, per that service's own trust-store choice); `reqwest` 0.13.x (`services/ui`, pinned at `0.13.4`) renamed it to plain `rustls`, and `services/ui/Cargo.toml` already uses that current name (`features = ["json", "stream", "rustls"]`). When adding or upgrading a `reqwest` dependency, check that version's own feature list (`cargo doc` for the `reqwest` crate, or its `Cargo.toml`/README on crates.io) rather than assuming either name is universal. (Corrected 2026-08-06: this previously named the single fixed string `rustls-tls` for every service — already stale for `services/ui`'s pinned version; the code was correct, the rule text was not.)
- **[AG-CI-004]** **sccache**: controlled by `SCCACHE_REDIS_MODE` (`required`, `optional`, `off`) and the `SCCACHE_REDIS_URL` GitHub Actions secret. Never hardcode a Redis URL. If `SCCACHE_DIST_SCHEDULER_URL` is configured, the matching `SCCACHE_DIST_AUTH_TOKEN` secret must also be configured and wired into `SCCACHE_CONF`; setting only a scheduler URL environment variable is not a valid sccache-dist setup. When installing sccache from source, keep the sccache version pinned, avoid locked installs while the pinned upstream lockfile emits yanked-crate warnings, and enable only the Redis plus `dist-client` features unless a PR explicitly justifies another backend.
- **[AG-CI-005]** **distcc/pump**: Rust service builders that install `distcc` must receive host lists through BuildKit secrets or trusted CI variables, never hardcoded Dockerfile values. When enabled, they must set `CC=distcc`, `GCC=distcc`, `CXX=distcc`, and discover either `/usr/local/lib/distcc` or `/usr/lib/distcc` before putting the discovered wrapper directory at the front of `PATH`, so direct `cc`, `gcc`, `c++`, and `g++` calls are intercepted across Debian and distcc-ng layouts. `distcc-pump` host lists must include at least one `,cpp` host entry. `distcc-pump` remains the default, preferred acceleration path — the bypass below is selective, not a reason to disable pump for a whole builder: specific compile inputs known to break pump's include-server assumptions (e.g. generated C headers such as `aws-lc-sys`'s, since pump assumes sources and includes do not change during the include-server lifetime) must route through normal (non-pump) distcc hosts or local compiler fallback for those inputs only, while the rest of that builder's compilation still uses pump normally. Distcc must log `[INFO] trying distcc path.` when it is actually attempted, must use `DISTCC_FALLBACK=0`, and may retry once with the normal local compiler if the distcc path is unavailable. Any image that installs Debian `distcc-pump` must patch the known invalid Python regex escapes before package configuration and verify the result with `python3 -Werror::SyntaxWarning`. This rule's `CC=distcc`/`GCC=distcc`/... values describe the plain, uncached distcc path (still the correct fallback tier whenever the opt-in cache layer below is disabled or its own probe fails) — see Rule-Ref: AG-CI-022 for `services/dns`'s and `services/ui`'s additional, opt-in ccache-over-distcc layer, which uses a different `CC` value while active.
- **[AG-CI-022]** **ccache-over-distcc** (`services/dns/Dockerfile`'s C-dependency compile path, e.g. `ring`, issue #887; `services/ui/Dockerfile`'s equivalent `ring`/`aws-lc-sys` path since issue #1533; and `services/watchdog/Dockerfile`'s since issue #1095): an opt-in cache layer in front of Rule-Ref: AG-CI-005's distcc wiring, active only once distcc itself is already enabled and a ccache Redis secret is present. `CC="ccache <real compiler>"` with `CCACHE_PREFIX=distcc` (never `CC=distcc` wrapped in ccache masquerade) so ccache preprocesses locally for its own cache-key computation instead of shelling that pass through distcc the way sccache does (the structural cause of the `,cpp`-host crash issue #860 hit). The real compiler's absolute path must be resolved before distcc's own masquerade directory lands on `PATH`, or ccache's `CCACHE_PREFIX=distcc` ends up recursively wrapping distcc's own masquerade symlink instead of the real compiler. `CCACHE_COMPILERCHECK=content` (not the `mtime` default) is required, since this cache is shared over Redis across build-tools image versions and ccache's own manual documents `content` as coping better with compiler changes between builds. `services/ui/Dockerfile`'s `lancache-distcc-wrapper` (a custom wrapper script, unlike `services/dns`'s plain masquerade symlinks straight to the real `distcc` binary) now understands both distcc calling conventions -- $0-basename masquerade and ccache's $1-as-real-compiler-path `CCACHE_PREFIX` convention -- disambiguated by checking `$0` first, falling back to treating `$1` as an executable real-compiler path only when `$0` doesn't name a known compiler; a defensive guard refuses to dispatch if that resolved `$1` points back into the wrapper's own masquerade directory, which the DNS topology cannot hit since its masquerade symlinks never point at anything but the real `distcc` binary. Live-verified (issue #887) that distcc-ng v3.6.5-NG does not change this, since that project's `,cpp` wrapper detection matches only a literal `ccache` `argv[0]`, a shape this project's own `CCACHE_PREFIX=distcc` wiring never produces. `CCACHE_COMPILERCHECK=content` only hashes the local compiler, never the remote distcc host's own — a farm host upgraded independently of the client's build-tools image would otherwise let a stale/incompatible remote toolchain's object serve as a cache hit; `CCACHE_EXTRAFILES` must additionally include a verified remote toolchain identity (e.g. the `.comment` ELF section a real probe compile through distcc comes back with), not only the client-side build-tools image reference, and ccache must fail closed to plain distcc when that remote identity cannot be established. The real-secret wiring gap this note once described (issue #1533) is closed as of 2026-08-26 (issue #1095): `build-push.yml`'s "Prepare Rust acceleration secret files" step populates `ccache_redis_url`/`ccache-redis-file` for every Rust service, wired straight into the preflight -- see this file's own Known Gaps section for the closure record.
- **[AG-CI-006]** **Build parallelism**: Cargo and Docker Rust builds must use one project-wide job rule unless a PR justifies an override: the optional `CARGO_BUILD_JOBS` repository variable wins when set and must be validated as a positive integer; otherwise use detected CPU cores minus two, with a minimum of four jobs. Do not hardcode service-local values such as `CARGO_BUILD_JOBS=6`.
- **[AG-CI-007]** **Build acceleration wiring**: Installing `sccache`, `distcc`, or `distcc-pump` is not sufficient. Every PR that changes Rust builders or build workflows must verify the full chain: repository variable or secret, workflow input, BuildKit secret or Cargo environment, Dockerfile consumption, and a fail-closed smoke/status check.
- **[AG-REL-008]** **Prebuilt build-tools contract**: Rust service builders should consume a prebuilt `build-tools` image by immutable release, SHA, or the selected CI image contract instead of rebuilding toolchains in each service image. Reintroducing ad-hoc local toolchain compilation in `services/dns` or `services/ui` requires a documented reason and a separate review of first-user-experience impact.
- **[AG-CI-008]** **Dockerfile ARG defaults for tool images**: `ARG BUILD_TOOLS_IMAGE=ghcr.io/wiki-mod/lancache-ng/build-tools:latest`-style defaults exist only as a fallback for a manual `docker build` invocation without `--build-arg`. Every real CI build (workflow jobs, release jobs) always passes `--build-arg BUILD_TOOLS_IMAGE=...` explicitly and never falls back to this default. A PR that pins or updates this default for "consistency," without showing a real path where CI actually consumes it, is not a bug fix — see issue #508, closed as already-resolved-by-design.
- **[AG-OP-001]** **Cache key**: nginx uses `$host$uri` (not `$request_uri`) — CDN query-string signatures must not bust the cache.
- **[AG-OP-002]** **DNS resolver in nginx**: must point to real upstream DNS, never to the local PowerDNS recursor — that would cause an infinite loop. Configured by `NGINX_UPSTREAM_RESOLVER` (default `8.8.8.8 8.8.4.4 [2001:4860:4860::8888] [2001:4860:4860::8844]`, matching this project's dual-stack support — IPv6 literals are bracketed because nginx's `resolver` directive requires it). If nginx used this project's own DNS instead, `proxy_pass https://$host` would resolve CDN names back to the proxy itself, causing an infinite loop.
- **[AG-OP-015]** **Domain scope semantics**: a leading-dot domain entry such as `.example.com` is an explicit wildcard/subdomain scope and is not equivalent to the root domain `example.com`. Do not normalize away the leading dot or treat root and wildcard scope as interchangeable in any validation, matching, or migration logic that touches domain entries.

## Release And Package Consistency

- **[AG-REL-009]** `latest` means the current stable release channel, published continuously from `master` (the release-bearing branch). `nightly` means the tested pre-stable channel (renamed from `edge` in v0.3.0, #1056), built from `current_dev` (re-pointed from `master` to `current_dev` per the simplified three-channel decision in #825/#1141: `master` = stable, `current_dev` = nightly, archived `vY.X.Z` release branches = frozen, no live channel). Since #1254/#1255 (2026-07-25), `nightly` is no longer republished on every `current_dev` push -- it is a real once-daily (01:00 UTC) plus on-demand, green-gated build of `current_dev`'s tip (see `nightly-refresh.yml` and `docs/release-versioning.md`'s "Branch/channel model" section); a plain `current_dev` push still publishes that commit's durable per-service `sha-<commit>` tags unaffected. Release tags (`vX.Y.Z`) are immutable. Any documentation, issue, PR body, workflow comment, or setup output implying `latest` equals `nightly`, that `nightly` is still fed from `master`, that `nightly` is republished on every `current_dev` push, or that an archived `vY.X.Z` branch publishes a live channel, is wrong and must be corrected.
- **[AG-REL-010]** Stack versioning, GHCR package/channel definitions, and release documentation must move together: release and package changes must follow `docs/release-versioning.md` and the machine-readable inventory in `release/stack-images.yml`, and must run `bash scripts/untracked/validate-stack-images.sh`. A package/image change that only edits workflow files without checking these is incomplete.
- **[AG-REL-011]** **A release-readiness declaration -- promoting a branch to `master`, or cutting a `vY.X.Z` tag -- must not rely on `docs/validation-state.json`'s `last_stack_validation`/`last_ci_validation` records if any `full_invalidation_trigger` (as defined in that file's own policy) has fired since their recorded commit, without a fresh validation pass and record update since.** A stale or invalidated record is equivalent to "never validated" for release-readiness purposes, not "probably still fine" -- check `docs/validation-state.json`'s own invalidation-notice fields directly before treating any recorded pass as current evidence.
- **[AG-REL-013]** **Branch-promotion procedure**: promoting a branch to `master` (or cutting a release tag) follows this fixed sequence, not an ad-hoc re-derivation each time: (1) enumerate every commit unique to `master` since the last promotion and verify explicitly whether its content is already present, superseded, or genuinely missing on the source branch -- before resolving any merge conflict; (2) resolve the merge by taking the source branch's tree wholesale unless step 1 found genuinely master-only content still needed, which must be ported to the source branch first, never patched directly onto `master`; (3) require fresh, green CI on the promotion PR itself; (4) apply AG-REL-011 -- if any `full_invalidation_trigger` fired since the last recorded validation, run a fresh Part B stack validation before calling the release ready, not just Part A/CI; (5) merge only on the maintainer's explicit ACK; (6) cut the actual `vX.Y.Z` tag as its own separate, explicitly maintainer-ACK'd action after merge -- minor/major version bumps are never automated (see `docs/release-versioning.md`'s "Automated Patch (Z) Tagging" section). Real incident that prompted this rule (2026-08-02): the v0.3.0 promotion (`master` <- `current_dev`) surfaced 55 conflicted files on a routine merge attempt, each one re-derived from scratch under time pressure instead of following a known procedure, purely because this exact sequence had never been written down anywhere despite being effectively re-invented for the prior v0.3.0 promotion attempt (PR #1232) too.
- **[AG-REL-014]** Every release version — a `vY.X.Z` tag and/or branch, and/or any future `release/*` branch — must be write-protected once it exists, since it represents the essential frozen code at the moment of that release; no changes may be made to it afterward, under any circumstance, without exception — any post-release modification, however small or well-intentioned (including CI/governance-only changes), makes the released code's integrity impossible to trust as unmodified from what was actually released. `master` itself is explicitly NOT covered by this rule — it is the living, continuously-updated branch a release tag is cut *from* (Rule-Ref: AG-REL-013), not the frozen release artifact itself; ordinary merges and CI/governance syncs to `master` remain governed by their own existing rules (e.g. Rule-Ref: AG-CI-019), unaffected by this one. If a release's protection is found missing at any later point (e.g. discovered during an unrelated audit), that is itself a defect to fix immediately, not evidence that the freeze no longer applies — protection must be (re-)applied as soon as the gap is found, regardless of how long it had been missing.

## Comment Style

- **[AG-CODE-001]** Code in this project must be human-readable, documented, and commented — this has been a core project tenet since its first design decisions, not a stylistic preference applied case-by-case. The default posture is to comment liberally, especially WHY-explanations for non-trivial logic (see AG-CODE-002), not to withhold comments until a case forces one. This is why AG-CODE-008's "you touch it, you comment it — entirely" rule exists: so nothing stays uncommented. The one thing NOT to do is restate what a well-named identifier or a trivial line already makes obvious (setting a variable, calling a function, reading a file) — that's noise, not documentation; see AG-CODE-002 for the WHY-vs-WHAT distinction this rule is actually about.
- **[AG-CODE-002]** Every non-trivial operation — especially anything with real-world side effects (file/data deletion, network calls, permission or ownership changes, state mutation, process control) — gets a `Why:` comment, regardless of how self-evident it looks to the person writing it. "This looks obvious" is not a reliable signal: a dangerous line and a safe line can read identically (e.g. `rm -rf "$dir"/*` reads the same whether `$dir` is guaranteed non-empty or not) — the risk lives in context the line itself doesn't show. Comment concrete cases where the WHY matters: complex logic, guards, fallbacks, security decisions, non-obvious side effects, a workaround for a specific bug, or a deliberate deviation from the obvious/standard approach. There is no "too obvious to need one" exemption.
- **[AG-CODE-006]** Code must stay human-readable. Silent or hard-to-follow changes are not acceptable — if a change needs explanation to be trusted, write the comment; don't ship it silently.
- **[AG-CODE-007]** Short structural/orientation comments that label the steps of a longer sequential procedure (e.g. `// Step 1: Fetch current config`, `// Step 2: Validate and normalize`) are also acceptable and encouraged, even when they don't explain a hidden WHY — they help a reader scan a long function without re-deriving its structure. Reviewers (including automated ones) must not flag this style as "unnecessary" or "restates the code" just because `Comment Style` otherwise favors minimal comments; readability-oriented step labels are a distinct, allowed category from WHY-comments, not a violation of this section.
- **[AG-CODE-008]** A missing comment is a defect too, not just a neutral default. When touching any part of a file, check the **entire file** — not only the specific lines you edited — for places that should already have a WHY-comment under the categories above (complex logic, a guard, a fallback, a security decision, a non-obvious side effect) but don't, whether the gap was missed originally or never added, and add it as part of the change. Do not leave the gap just because it predates your edit or sits outside your diff; "there wasn't one before" and "it's not part of what I changed" are not reasons to skip adding one now.
- **[AG-CODE-003]** Do not reference the current task, PR number, or fix in a comment (e.g. "fixed for #123", "added by the CR-9 pass"). That belongs in the PR/commit description, not in code that outlives the change. Exception: a bare `From: #N` pointer under Rule-Ref: AG-CODE-012's structured format is not a narrative task/fix reference and is permitted — the ban above targets phrasing like "fixed for #123" or "added by the CR-9 pass" woven into surrounding sentences, not a bare, structured pointer.
- **[AG-CODE-004]** When documenting a known limitation or deliberately deferred fix (not a bug you're fixing now), prefer a structured note over a one-liner: state the problem, the mitigation/fix direction if one exists, and a dated status line describing the current real-world state (e.g. "STATUS: as of 2026-07-02, X still uses the old path; once Y migrates, this fallback becomes dead code"). This lets a future reader tell a documented tradeoff apart from an accidental gap.
- **[AG-CODE-005]** Placeholder/scaffold markers (e.g. `TODO(#123): ...`) must be removed the moment the referenced work is actually implemented in that same change. A stale TODO claiming work is still needed, sitting next to code that already does it, is worse than no comment — it actively misleads the next reader/reviewer. Before finishing a fix that started from a TODO/scaffold marker, grep for and delete the marker it replaces.
- **[AG-CODE-009]** A descriptive identifier or name alone — including a `#[test]` function name — is not a valid comment. When the WHY behind a non-obvious edge case, security invariant, race condition, or off-by-one scenario isn't clear from the name, the reasoning must be spelled out explicitly: not what is being asserted (already visible in the code), but why this specific case would otherwise silently break something.
- **[AG-CODE-010]** For this project specifically, every `#[test]` function must carry at least a short comment explaining its purpose, regardless of whether the case looks "obvious" on its own. This project's domain (nginx/DNS/DHCP/Kea/Rust systems code) is complex enough that a bare test name is never sufficient on its own (see Rule-Ref: AG-CODE-001) — the same liberal, err-on-the-side-of-commenting standard applies to non-test code whenever in doubt.
- **[AG-CODE-011]** Before implementing or modifying any function, helper, check, variable, alias, or other mechanism of any kind, perform a real search — of this repo's own codebase, and of any natively-provided capability (a language/runtime builtin, a GitHub Actions context expression, an existing config value) — for an existing one that already does the same or closely related thing, and reuse it rather than re-implementing the same logic under a different name. This is a hard prohibition, not a suggestion to consider reuse when convenient: no such implementation or modification may begin until the search has actually happened. It applies at every scale — a whole function, a one-line variable alias, a config flag, a workflow job, a small edit to existing code — not only to large, obviously-reusable abstractions or wholly new additions; a trivial-looking change is not exempt. A duplicated implementation of the same capability is its own maintenance burden (two places to fix the next bug in) and a real source of behavioral drift once the two copies diverge.
- **[AG-CODE-012]** **Every comment follows a strict What/Why/From structure, capped at 3 lines total — sober and factual, never a narrative, never a story of how something was found, discussed, tried, or verified. All three fields are mandatory whenever a comment is written under this rule; a comment missing any one of `What:`, `Why:`, or `From:` (when a PR/Issue is known) does not comply, partial coverage is not an acceptable middle ground. Stacking a second What/Why/From block directly beneath the first one for the same location is not a way around the 3-line cap — it is the same violation the cap exists to prevent, just split across two blocks instead of one. One location gets exactly one What/Why/From block.**
  `What:` — **mandatory, always present.** One line, maximum 60 characters — a ceiling to stay under, not a target to fill: what the code does — not the history of how it came to do it.
  `Why:` — **mandatory, always present.** One line, maximum 60 characters — a ceiling to stay under, not a target to fill: the actual reason — a hidden constraint, an invariant, a workaround, something that would surprise a reader. Not a story of the investigation that led here.
  `From:` — **mandatory whenever a PR and/or Issue number is known for this code** (never optional in that case). One line: a bare pointer to where the fuller context lives (PR #123, Issue #123, both if both apply) — never a retelling of that context. Don't guess or invent it: the correct value can be found with `git blame` on the line/block being commented, and must be checked against that, not assumed. This is the one allowed exception to Rule-Ref: AG-CODE-003's ban on naming a task/issue/PR number in a comment: a pointer outward, not a substitute for writing the actual investigation, verification steps, or history in the PR/commit description, which remains the authoritative place for all of that (in the PR and/or Issue — if it lives in the Issue, it must also be referenced from the PR, and vice versa) — a code comment outlives the change that added it.

  `From:` always points to the *current* PR/Issue only — it is not a running log of every PR/Issue that ever touched this line. When a later change revises a comment, its `From:` is simply updated to the new PR/Issue number; the fact that it used to say something else, and why it changed, belongs in the *new* PR's own body (its "What Changed In Code" section), not stacked into the code comment. Example: a comment at some line reads `What: creates only one directory` / `Why: only one subdirectory was needed` / `From: Issue #5555 | PR #4444`. A later PR #6666 (Issue #6667) changes that same code to build a multi-directory structure; the comment becomes `What: creates the full directory structure in one call` / `Why: the root directory alone now needs several subdirectories` / `From: Issue #6667 | PR #6666` — and PR #6666's own body states that this line previously referenced Issue #5555/PR #4444, so a later reader can see the single-directory-to-structure evolution without that history living permanently in the code.

  **Sober means: state the current fact, not the journey to it.** No "we found that...", no "after discussion it turned out...", no "initially X, but then Y", no verification narrative, no timeline of what was tried first. If the reasoning behind a decision took investigation to arrive at, the investigation belongs in the PR/commit description — the code comment states only the resulting invariant, as if it had always been known.

  The cap is measured in physical lines, not sentences — a "1-5 sentences" cap is ambiguous (a sentence can wrap across lines; several short sentences can fit on one line) and is retired in favor of this explicit per-field line budget: 1 (`What:`) + up to 3 (`Why:`) + 1 (`From:`) = **5 lines maximum, hard ceiling, no exceptions**, measured on the actual content, not satisfied by relabeling existing text. Prepending `What:`/`Why:`/`From:` tags onto an unshortened paragraph does not comply — the underlying text itself must be cut down. A comment that needs more than 3 lines of `Why:` to make sense is a signal that either too much context is being explained here (move it to the PR/commit) or the code itself needs a clearer name/simpler design instead of a longer explanation — not a reason to extend the cap.

  **Where does information go that the 5-line cap forces out of the comment?** If shortening a comment to comply with this cap would drop information that must be preserved (the reasoning behind a non-obvious decision, an investigation's outcome, context a future reader would need), that information is transferred into a comment on the relevant PR and/or Issue — never left stranded in an oversized code comment, and never simply discarded. This applies even when the PR/Issue is already merged or closed: GitHub still accepts new comments on closed/merged items, closure is not a reason to skip this. A code comment is not a story — it states dryly what the code does, why it does it, and where it comes from; the story/information/text, if any is needed at all, belongs on the PR/Issue instead.

  Do not write a comment that tells the story of how something was found, discussed, or verified. (Real incident, this repository: `.github/actions/shellcheck-and-standing-guards/action.yml`'s "Run ShellCheck and ActionLint" step comment grew into a multi-paragraph narrative — full incident timeline, verified-on-host claims, an earlier-wrong-then-corrected sub-claim, cross-references to other steps' identical reasoning — none of it reducible to a single WHAT/WHY. This project's own real Rust/shell upstream conventions carry no such narrative; that is the actual bar.)
  Before writing any such new or modified code, state an explicit confirmation that this search happened, in this exact form: **"I confirm I did not violate AG-CODE-011 — I searched for `<what was searched>` and found no existing `<function/helper/check/variable/mechanism>` already doing `<the job>`, so I am implementing/modifying `<what, and where>`."** This confirmation must be written into the actual Issue or PR this work belongs to (body or a comment) — not only stated in chat, since chat context does not survive a compaction or a new session and is not discoverable by a future reviewer.
  If this pre-check search itself turns up an existing violation of this rule already sitting in the codebase — a duplicate, unrelated to the change at hand — do not decide unilaterally whether to fix, flag, or ignore it; ask the maintainer if there is any uncertainty about the right next step.
  Rationale, from a real, lived instance: issue #1441 found that `services/proxy/entrypoint.sh`'s nginx stream-backend map generator implements an empty-SNI fallback independently in its `strict` branch (a named reject target) and its `lazy` branch (no guard at all, silently reproducing the exact bug issue #88 had already fixed once). The two branches were never sharing a common function/constant for "what happens when there's no SNI to route on," so a fix applied to one branch had no structural way to reach the other — the regression was not a one-off oversight, it was the predictable consequence of the duplication itself. A search before writing the `lazy` branch's routing logic would have surfaced the `strict` branch's already-existing guard before a second, unguarded copy ever got written.
  This does not require deduplicating code that is only superficially similar but expresses a genuinely different decision (Rule-Ref: AG-CODE-006 — forcing a shared abstraction onto code that is coincidentally shaped alike, but conceptually independent, trades one readability problem for a worse one). The test is "would a bug fix or behavior change to one copy need to apply to the other(s) to stay correct?" — if yes, share it; if the two copies are allowed to diverge on purpose, duplication is fine and abstracting them would be the actual mistake.
- **[AG-CODE-013]** **Creating a new file carries a standing formal DISACK.** The DISACK applies by default and is independent of the reason offered for creating the file. Convenience, implementation speed, naming neatness, perceived separation of concerns, or an apparently legitimate special case do not lift it. No new file may be created — including provisionally, temporarily, or as part of an implementation experiment — until the checks below have been completed. The DISACK is lifted only when: (a) an existing file is identified as the appropriate home and is extended instead; or (b) the required consolidation/search checks have been completed and documented, no suitable existing home exists, and an explicit maintainer/coordinator ACK for the new file has been obtained before the file is created. Reasoning that a new file "makes sense" is not an ACK and does not substitute for the required checks.

  **Required checks.** Before creating any new script, library, test-suite file, or other monolith-capable implementation file: search the same directory and related implementation area for files covering the same conceptual capability or lifecycle; determine whether the proposed behavior can be added to an existing file through a function, option, flag, subcommand, case dispatch, reusable helper, or additional test case; check whether two or more existing files already implement variants of the same operation and should be consolidated instead of adding another member to the family; search for duplicated or near-duplicated setup, validation, cleanup, argument parsing, resource discovery, logging, error handling, comments, or control flow (duplication is evidence that consolidation or shared implementation is required); check currently open issues and PRs for another consumer of the same not-yet-built capability, and if multiple consumers need it, implement the capability once and have them reuse it. State the result of this check in the implementation/PR — a silent or implicit check does not satisfy this rule.

  **How to decide whether files belong to the same conceptual class.** Files should normally be treated as candidates for consolidation when they operate on the same resource or lifecycle and differ primarily by: execution mode (`--dry-run`, `verify`, `apply`, `delete`, `retire`); policy or safety level; filtering or selection criteria; environment or target; phase of the same operator workflow; small variations in otherwise shared control flow; duplicated setup, validation, cleanup, or reporting logic. For example, `prune-old-dry-run.sh` / `prune-old-verify-before-delete.sh` / `prune-old-delete.sh` should normally become one cohesive `prune-and-retire.sh --dry-run` / `--verify` / `--delete`, with shared internal functions rather than copied implementations.

  **Consolidation requirements.** Extend an existing file whose established responsibility already covers, or is the closest conceptual owner of, the capability — regardless of whether that file is formally organized as a library, a script, a test suite, an action, or any other implementation file, and even if its name is not a literal match for the new behavior; this is the default expectation, not a special case reserved for files labeled as libraries. Prefer flags, options, subcommands, functions, or case dispatch over sibling files. Implement shared behavior exactly once. Treat a growing family of near-identical standalone files as evidence of an existing design problem to correct, not as precedent for creating another one.

  **Do not:** create a new file because doing so is easier than understanding or extending an existing implementation; create a new file merely because the new behavior has a distinct name; create `*-dry-run`, `*-verify`, `*-cleanup`, `*-delete`, `*-simulation`, or similar sibling scripts when those are modes or phases of the same underlying capability; copy an existing file and modify it into a new variant; duplicate functions, boilerplate, comments, parsing, validation, cleanup, or error handling between sibling implementations; evade this rule by moving file sprawl from `scripts/` into `scripts/lib/`; create one library file per helper function unless the file type or framework structurally requires such decomposition; create the file first and request ACK afterward; interpret an existing family of fragmented files as justification for adding another — evaluate the family for consolidation first.

  **Cohesion constraint.** This rule requires consolidation of the same conceptual capability, not arbitrary monolithization. Unrelated responsibilities must not be forced into the same file merely to reduce file count. The objective is one coherent implementation per capability, with internal reuse — not one tiny file per variation, and not one unrelated god-file containing everything.

  **File-type exception.** The consolidation preference applies where a file type naturally supports internal reuse and dispatch, such as shell scripts and Bats suites. It does not require artificial consolidation where the native composition model of the format uses separate units. GitHub Actions composite actions are an example: directory-per-action plus `uses:` composition is the native reuse mechanism. Combining unrelated composite actions into one condition-heavy YAML file would replace structural reuse with declarative branching and is therefore not required by this rule.

  **Uncertainty.** If there is genuine uncertainty about whether an existing file should be extended, whether existing files should first be consolidated, or whether a new file is justified: the DISACK remains in force. Stop and request a maintainer/coordinator decision. Absence of certainty is not permission to create the file.

  **Core principle.** A new requirement does not imply a new file. File boundaries follow conceptual ownership, not issue boundaries, feature requests, execution modes, implementation tasks, or the convenience of the current change.

  **Decision algorithm:**
  ```
  About to create any new file, for any reason
          |
          v
     FORMAL DISACK
          |
          v
  Search existing files for the same conceptual class/responsibility
          |
          +--> Same capability already implemented somewhere?
          |        |
          |        +--> Yes --> Extend it. NO NEW FILE.
          |
          v
  Any existing file already owns this conceptual class/responsibility,
  even if this exact capability is new?
          |
          +--> Yes --> Add it as a function/option/flag/subcommand/
          |            case dispatch/helper to that file. NO NEW FILE.
          |
          v
  Related sibling files exist (same resource/lifecycle, differ by
  mode/phase/policy)?
          |
          +--> Yes --> Consolidate them into one implementation
          |            with the new capability as another mode.
          |            NO NEW FILE.
          |
          v
  No suitable home genuinely exists anywhere?
          |
          +--> Document search + rationale
                          |
                          v
                 Maintainer explicit ACK?
                    |             |
                   No            Yes
                    |             |
                  DISACK     ACK --> New file permitted
                  stands
  ```

  **Enforcement interpretation.** The default state is always `NEW FILE = DISACK` until the required search/consolidation process proves that no appropriate existing home exists and a maintainer/coordinator explicitly changes that state to `NEW FILE = ACK`. A plausible reason, architectural preference, implementation convenience, issue scope, agent judgment, or statement that a file is "cleaner" or "more modular" never changes the state by itself.

## File Headers

- **[AG-HDR-001]** Every source/config file (Rust, shell, YAML, Dockerfiles, `.conf`/template files, HTML/CSS/JS) in scope for repository headers uses one canonical physical three-line prefix. Physical line 1 is either a genuinely required interpreter/parser marker, for Rust exactly the bare `//!` inner-doc placeholder required to keep the three-line contract formatter-stable, or otherwise intentionally blank. Physical line 2 contains the literal project form `LanCache-NG (https://github.com/wiki-mod/lancache-ng)` in the native comment syntax valid for that file. Physical line 3 contains `SPDX-License-Identifier: AGPL-3.0-or-later` using the same native comment syntax. Existing file-purpose documentation follows this fixed prefix and is not displaced or removed merely to satisfy the three-line contract. `scripts/tracked/check-file-headers.sh` enforces the exact capitalization, physical positions, native syntax, and uniqueness of the project/SPDX lines.
  - Rust: physical line 1 is exactly bare `//!`; lines 2 and 3 are `//! LanCache-NG (https://github.com/wiki-mod/lancache-ng)` and `//! SPDX-License-Identifier: AGPL-3.0-or-later`. The bare inner-doc line is the formatter-stable placeholder for the otherwise empty first line; a physical blank line is not canonical because `rustfmt` removes it.
  - Shell, Bats, YAML, Dockerfiles, TOML, PowerShell, systemd units, and genuinely plain-text `.conf`/template/config files: `#` line comments on lines 2 and 3. A shebang or supported required parser directive may occupy line 1; otherwise line 1 stays blank.
  - HTML Tera templates under `services/ui/src/templates/`: complete standalone Tera comments, exactly `{# LanCache-NG (https://github.com/wiki-mod/lancache-ng) #}` on line 2 and `{# SPDX-License-Identifier: AGPL-3.0-or-later #}` on line 3. Do not use a raw HTML `<!-- ... -->` comment there: Tera comments are safe before an `{% extends ... %}` tag, while ordinary HTML content before `extends` can break template loading. Existing Tera purpose-comment blocks follow the fixed prefix.
  - Other HTML: `<!-- ... -->` comments.
  - CSS (`.css`): `/* ... */` comments.
  - JavaScript (`.js`): `//` line comments.
  - Lua (`.lua`): `--` line comments.
  - If a file language is not listed here, use that language's own standard comment syntax only after confirming it is valid for the real parser; never default to `#` merely from the filename.
- **[AG-HDR-002]** Before adding a header to any file with a `.conf`/`.json`/`.txt`/other generic-looking extension, check what actually parses it and how. If the content is genuinely JSON (JSON has no comment syntax at all), do not add any header; a `#` or any other comment line would break parsing. In this repo, all three Kea config files under `services/dhcp/` are JSON despite the `.conf` extension and must be excluded on this basis: `kea-dhcp4.conf` (parsed by `migrate_dhcp4_config` in `services/dhcp/entrypoint.sh`), `kea-ctrl-agent.conf`, and `kea-dhcp-ddns.conf`. The same JSON exclusion applies to any other file this project treats as machine-parsed structured data without a comment syntax, whatever its extension.
- **[AG-HDR-003]** Do not add a header to a file whose entire content is consumed as a single raw value by a strict parser, where any extra text (including a comment) would corrupt that value. The clearest example in this repo is the root `VERSION` file: `setup.sh`'s `derive_current_release_image_tag` reads the whole file, strips whitespace, and requires the result to match a release-tag pattern — a header would be concatenated into that value and break setup/update with an invalid release image tag.
- **[AG-HDR-004]** Do not add a header to a vendored third-party file or a generated/compiled build artifact — it isn't this project's own hand-authored source, and in the vendored case it likely already carries its own upstream header. In this repo: `services/ui/src/static/chart.umd.min.js` is the vendored, minified Chart.js library (already opens with its own `/*! Chart.js v4.5.1 ... */` header) and `services/ui/src/static/admin.css` is compiled/minified Tailwind CSS output, not hand-written CSS. `services/proxy/public_suffix_list.dat` is the vendored Mozilla Public Suffix List (already opens with its own `// This Source Code Form is subject to the terms of the Mozilla Public License, v. 2.0` header), used at proxy startup to derive each CDN domain's registrable root for wildcard cert coverage. If a hand-written source input for a generated artifact is ever added to the repo (e.g. a Tailwind config or an unminified source file), that source input is in scope for a header; the generated output it produces is not.
- **[AG-HDR-005]** Scale the header's detail to the file's actual complexity — a file with several distinct responsibilities (e.g. a multi-role entrypoint script, a large route-wiring module) should name them; a simple, single-purpose file (e.g. an install-and-copy Dockerfile) should stay short. Do not pad a simple file's header just to match a fixed line count.
- **[AG-HDR-006]** Every technical claim in a header must be verified against the actual file content and, where relevant, git history — do not assert an unconfirmed reason for a design choice (e.g. why a particular base image or repo is used) if no documented rationale exists; state the observable fact instead.
- **[AG-HDR-007]** Excluded: `.md` files, a literal root-level `.env` or `.env.example` file (not every file with a `.env` extension — the per-service defaults under `config/prod/` such as `dhcp.env` are ordinary committed config and are in scope for a header), lockfiles (`Cargo.lock`), `.gitkeep`, the root `VERSION` file, vendored/generated build artifacts, and any file whose content is JSON or another comment-free structured format regardless of its extension (see above for concrete examples of each). See `scripts/tracked/check-file-headers.sh`'s `is_excluded()` function for the exact, executable list this maps to. Also excluded, for the same reason as `VERSION` (Rule-Ref: AG-HDR-003): the root `LICENSE` file — it must contain unmodified license text for tooling (GitHub's license detector, SPDX scanners) to recognize it, and a prepended repo header would corrupt that; see Rule-Ref: AG-HDR-008 for the license itself.
- **[AG-HDR-008]** The project adopted the GNU Affero General Public License v3.0 (or later), effective 2026-07-24 (issue #1130, PR referencing #1145); the license text lives at the repository root (`LICENSE`) and is not restated here. Every file in scope under Rule-Ref: AG-HDR-001/007 carries `SPDX-License-Identifier: AGPL-3.0-or-later` on physical line 3, immediately after the canonical `LanCache-NG (https://github.com/wiki-mod/lancache-ng)` project header on line 2 and using that file's native comment syntax. The repository-wide SPDX/project-header backfill is complete, so `scripts/tracked/check-file-headers.sh` hard-enforces the same contract in both explicit-file mode and whole-repository mode; there is no remaining soft/informational backfill exception.
- **[AG-HDR-009]** The repo-wide canonical header backfill is complete. `scripts/tracked/check-file-headers.sh` runs in CI and fails when any non-excluded tracked file is missing the required three-line prefix, places the canonical project/SPDX lines on the wrong physical lines, duplicates either line, or retains the legacy lowercase `lancache-ng (...)` project form. New in-scope files must use the same contract immediately rather than treating a CI failure as something to work around.

## Runtime Behavior

- **[AG-OP-003]** Lazy proxy/cache behavior is the intended default.
- **[AG-OP-004]** Strict proxy/cache behavior is explicit opt-in for users who want tighter allowlisting and accept the maintenance burden.
- **[AG-OP-005]** Do not silently invert the lazy default.
- **[AG-VAL-018]** DNS health checks must use a real query/response probe such as `dig` or an equivalent strong check.
- **[AG-VAL-019]** `ping` is not an acceptable DNS health check because it only proves network reachability.
- **[AG-VAL-020]** `ss` is not an acceptable DNS health check by itself because it only proves that a socket is listening.
- **[AG-VAL-024]** A new shell script's executable bit (`git` file mode `100755`) is invisible and unverifiable from a Windows authoring environment, where Git commonly runs with `core.filemode=false` — `chmod +x` has no effect there, and no local check reveals whether the bit is actually set in the commit. An agent can verify a new script's logic thoroughly on such a host and still ship it non-executable, discovering this only when real Linux CI execs it directly (`Permission denied`, exit 126) — never from anything observable in the authoring sandbox. Concrete incident: PR #937's `check-workflow-service-lists.sh` was committed as `100644`; all 8 of its own bats fixtures failed in the real build-tools-container CI run for this reason alone, invisible to the author's manual walkthrough. To prevent recurrence: (1) prefer invoking new scripts via an explicit interpreter (`bash "$script"`, not `"$script"` or `./script.sh`) at every call site (test harnesses included) — this removes the executable-bit dependency entirely; (2) if direct invocation is genuinely required somewhere, verify the mode explicitly with `git ls-files -s <path>` (must show `100755`) rather than inferring it from local testing on a non-Linux or `core.filemode=false` host. Separately, the same incident also exposed a `set -euo pipefail` fail-closed branch that was dead code — a `grep`/pipeline returning no matches (exit 1) silently killed the whole script via `errexit` before its intended diagnostic message was ever reached. A fail-closed path guarded by `set -e` must be exercised by an actual failing-input run in real CI, not only reasoned through manually.

## Documented Exceptions to Hard Rules

Hard rules in this governance exist to prevent real failures — runtime crashes, security exposures, documentation drift, stale CI gates, and cascading operational risk. A rule must be clearly broken only when there is a documented reason, and exceptions must state that reason explicitly, name what still must be validated despite the exception, and be narrowly scoped.

**[AG-DOC-011]** Every documented exception must follow this format:

- **Scope**: What the exception narrows (e.g., "Rust builder images for service X" or "CodeQL analysis for auto-generated code in path Y").
- **Reason**: Why the normal rule does not apply in this case (e.g., "generator output is deterministic and pre-audited," or "this image must use rust:latest because...").
- **Tracking**: Issue and/or PR reference where this exception was discussed and approved.
- **Validation**: What validation is still required despite the exception. Omitting validation because "the exception lets us skip it" misses the point — the exception narrows the rule, but safety verification must land somewhere else.
- **Non-Expansion**: What the exception explicitly does NOT cover (e.g., "this exception applies only to service X, not to other services" or "only to CodeQL analysis, not to other security checks").

### [AG-VAL-021] Second, distinct case: CodeQL findings in actually macro-generated code (issue #394, closed)

This is a separate case from Rule-Ref: AG-VAL-022 above, not an unreconciled restatement of it. That rule covers extraction *warnings* CodeQL's Rust extractor emits for ordinary, human-authored macro *invocations* (`format!`, `vec!`, ...) — confirmed to be a pure tooling artifact, tracked upstream as [github/codeql#19966](https://github.com/github/codeql/issues/19966), [#19982](https://github.com/github/codeql/issues/19982), and [#20659](https://github.com/github/codeql/issues/20659) (CodeQL's Rust support is `rust-analyzer`-based and cannot cleanly expand macros, especially procedural ones, without running the real compiler; all three remain open upstream with no fix commitment). PR #517 made this extraction-quality signal visible instead of leaving CI silently green. This exception instead covers real CodeQL *findings* ("overly complex", "unreachable") in code a macro actually *generates* — since that code is genuinely unusual, not just misread by the extractor, "it's just a tooling artifact" is not sufficient justification by itself; this exception additionally requires test evidence the generated code behaves correctly despite the finding.

- **Scope**: CodeQL analysis of Rust code generated by macros that expand to large intermediate representations.
- **Reason**: Rust procedural macros can generate code that CodeQL reports as overly complex or unreachable, even though the actual compiled binary and test behavior are correct. The generated code is not human-readable and is not part of the reviewable source surface. Blocking on CodeQL false positives in generated code delays legitimate security fixes.
- **Tracking**: issue #394 (closed — see the intro above for the upstream bug references this closure rests on). This exception was approved as part of the v0.2.0 security hardening pass.
- **Validation**: CodeQL analysis must still run on human-written code. The exception narrows which CodeQL findings are treated as blocking. A CodeQL exception pull request must demonstrate that the finding occurs in generated code (not human-authored code), that the finding is a known false positive for macro expansions, and that the relevant code path has test coverage that proves the behavior is correct despite the CodeQL report.
- **Non-Expansion**: This exception applies only to CodeQL Rust analysis. It does not cover other languages, other security checks (e.g., cargo-audit, SAST linters), or changes to non-generated Rust code. It also does not extend the plain-extraction-warning exception in Rule-Ref: AG-VAL-022, which covers warnings on ordinary macro invocations needing no test-coverage evidence since they are a confirmed tooling artifact unrelated to actual code behavior.

## Agent Closing-Report Contract

Finishing a nontrivial task (any PR, any issue fix, any multi-step verification) requires a closing report that proves you understood the work, not just executed instructions. The report must be part of the PR body, closing issue/PR comment, or final-task output (the form varies by context; the content does not).

A closing report must document:

1. **Context read** — Which issue(s), PR(s), design doc(s), existing code, or threat models did you actually read to understand the task scope? Name them explicitly. (This is not "I read the issue" — it's "I read #529 (full text), .github/AGENTS.md (lines 1-50 and the build-tools section), and CLAUDE.md (the Key Constraints section)" or similar specificity.) Omitting what you read is a red flag that you may have missed related constraints or design decisions.

2. **Areas changed** — List the file paths or subsystems you modified. Be exact (e.g., "edited AGENTS.md lines 1-200 to add rule IDs and enforcement matrix" or "modified services/dns/entrypoint.sh to add console-domain exclusion check").

3. **Related areas deliberately NOT changed (with reason)** — If the task description or issue context mentions work that you chose not to do, or related areas that appear to need similar changes but you left them untouched, state that explicitly and say why (e.g., "did not update .github/AGENTS.md because the issue scope is root AGENTS.md only" or "did not change README.md console section because issue #529 Track A is handling that separately"). This proves you recognized the boundary and did not accidentally miss work.

4. **Exact validation commands run and real results** — Not "ran tests" but "`bash scripts/tracked/check-file-headers.sh` — exit 0, no findings" or "`cargo clippy --locked --manifest-path services/ui/Cargo.toml -- -D warnings` — 12 warnings fixed, exit 0". Include the exact command so a reviewer can re-run it. If a check could not be run, state that too (e.g., "could not run docker compose config because Docker is unavailable on this host").

5. **Checks that could not be run (with reason)** — If the task normally requires a validation check but you could not run it (no Docker, no Rust toolchain, CI-only gate), state that explicitly. Do not claim success when a check is skipped. The report must distinguish between "check passed," "check skipped with reason," and "check failed."

6. **Known open risks** — Anything that feels incomplete, partially implemented, or dependent on follow-up work must be stated (e.g., "admin UI does not yet expose the new feature" or "the exception needs re-evaluation once upstream macro behavior changes"). Acknowledge what's outstanding rather than implying the task is fully shipped.

7. **Documentation checked/updated for drift** — Did you read the relevant documentation (README.md, threat-model.md, architecture docs) to verify it still describes the code behavior correctly? If you found drift, did you fix it? If not, why not? (Reference rule Rule-Ref: AG-DOC-001 — documentation drift is a defect.) State explicitly whether documentation was checked or skipped, and if skipped, why (e.g., "documentation changes are out of scope for this PR and tracked in issue #XXX").

8. **Follow-up issue reference or explicit "none"** — If this work creates or depends on a follow-up task, cite it (e.g., "depends on #500 being merged first" or "follow-up: #502 will add Admin UI support for this feature"). If there is no follow-up work, state "no follow-up required" explicitly, rather than omitting it. An omission looks like incomplete thought; an explicit statement closes the loop.

This contract overlaps with the `.github/pull_request_template.md` sections but is stricter: satisfying the template's headings with vague content (e.g., "Validation: tests pass") does not satisfy this rule. The content must be real, specific, and honest — including about gaps.

## Agent Autonomy and User-Context Rule

**[AG-WF-015]** The user of this repository is not a software programmer. This is a deliberate operational constraint, not a gap to work around. (CLAUDE.md's `AG-CC-001` retired 2026-07-30: merged here, which said the same thing with more detail — see also Rule-Ref: AG-WF-023. Not reused per AG-WF-016.)

**[AG-WF-023]** Agents and tools working on this repository must make technical decisions independently and must only ask for guidance when a choice has real operational impact such as hardware selection, network topology, cost implications, or time-to-value tradeoffs — not when the correct technical decision is determinable from code, documentation, and governance alone.

An example of a decision that agents should make independently: "The code changed from BIND9 to PowerDNS; should I update the threat model?" Answer: yes, update it. The code change determines the answer, not user preference.

An example of a decision that requires guidance: "The proposed optimization would increase cache RAM from 10GB to 50GB; is that acceptable for this operator's network?" Answer: ask. The hardware impact depends on the operator's deployment context, not the code alone.

When in doubt, prefer making the decision. The governance and code provide strong signals. This rule exists to keep workflows efficient and prevent decision-delegation bottlenecks on matters that are technically determinable.

## Agent Spawn Acceptance Protocol

Every agent, on being spawned as a sub-agent (by another agent or by the main thread), must, before doing any substantive work:

1. Read `AGENTS.md`, `CLAUDE.md`, and `.github/AGENTS.md` in full, with no shortcut (no skimming, no assuming inherited context from the dispatch prompt is a substitute).
2. Explicitly report back—by name, and as its very first action before taking any other tool action toward its assigned task—that it has read all three files: state "I have read AGENTS.md, CLAUDE.md, and .github/AGENTS.md" verbatim or equivalent, not merely "understood" or "acknowledged."
3. The parent/main thread that spawned it must confirm this acceptance is genuine, not rote, by asking the sub-agent to cite or quote at least one specific rule (by its `[AG-...]` ID) from the files it claims to have read. Because a sub-agent typically continues into substantive work within the same dispatch rather than pausing for a synchronous reply, the dispatching agent must perform this spot-check at the earliest checkpoint it can actually reach the sub-agent (e.g. its first status update or progress check-in), not only at the end, and must be willing to interrupt and redirect a sub-agent whose acceptance turns out to be rote or wrong rather than only discovering this after substantive work is already done.

This applies at every level of a spawn chain, not only to agents dispatched directly by the main thread—a sub-agent that itself spawns further sub-agents must apply this same protocol to each one, and must itself have already gone through it with its own parent.
