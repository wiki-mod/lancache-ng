# lancache-ng - Repository Governance
# **Repository**: https://github.com/wiki-mod/lancache-ng
This file contains the repository-wide rulebook and MUST apply to all repository paths and all repository work.

## AG-LAW
* **[AG-LAW-001]** `AGENTS.md` MUST be treated as one unified rulebook. All applicable rules MUST apply simultaneously to every affected part of the project and to the change as a whole. Compliance with one applicable rule MUST NOT establish overall compliance. Every touched file, asset, generated output, behavior, or other affected part of the project MUST be checked against every applicable rule. A task MUST NOT be declared complete until the complete affected change has passed this audit. Partial verification followed by a completion claim MUST itself violate this rule.
* **[AG-LAW-002]** Every time stated in maintainer-visible communication under `[AG-CC-002]` MUST use Berlin local time (`Europe/Berlin`) and MUST include the seasonally correct `CEST` or `CET` abbreviation immediately after the time. Fixed UTC offsets MUST NOT substitute for `Europe/Berlin`. External times MUST be converted before being stated and MUST be verified against an independent authoritative source rather than relying only on session environment, local `TZ`, or tool defaults. Raw machine output and non-visible internal reasoning MAY be exempt.
* **[AG-LAW-003]** Every binding requirement or prohibition in this rulebook MUST use RFC 2119 terminology. Binding requirements MUST use `MUST`, `REQUIRED`, or `SHALL`; binding prohibitions MUST use `MUST NOT` or `SHALL NOT`. `SHOULD`, `SHOULD NOT`, and `MAY` MUST be used only for genuine recommendations or optional behavior. Bare imperatives, ambiguous equivalents, or negated `MAY` constructions MUST NOT replace the applicable RFC 2119 keyword.
* **[AG-LAW-004]** Every rule reference MUST use the stable rule identifier in the form `[AG-XX-XXX]`. `AGENTS.md` line numbers MUST NOT be used or treated as authoritative rule references. This requirement MUST apply to humans, agents, AI systems, bots, automated reviewers, tools, and integrations.
## AG-CC
* **[AG-CC-001]** RETIRED -> `[AG-WF-015]`. This ID MUST NOT be reused.
* **[AG-CC-002]** Maintainer-facing chat and session communication, including visible reasoning or thinking presented to the maintainer, MUST be in German. Content that is or becomes GitHub-visible MUST instead follow `[AG-GH-001]`.
* **[AG-CC-003]** `[AG-CC-002]` MUST apply recursively to every dispatched agent and every further spawn level. Dispatch prompts and reports returned to a dispatcher MUST use German instructional prose. Literal code, logs, commands, paths, commit messages, and GitHub-bound content MUST remain in their required original or English form. Every spawning agent MUST propagate this rule.
* **[AG-CC-004]** Third-party automated tools MUST apply `[AG-GH-001]` to GitHub-bound output and `[AG-CC-002]` to local maintainer-facing output. Tool identity MUST NOT change the governing language rule. If GitHub content produced by such a tool violates `[AG-GH-001]`, this rulebook MUST remain the repository-controlled enforcement mechanism because the repository does not control the tool's internal configuration or system prompt. Compliance with this rule MUST be manually spot-checked against third-party automated-tool output. Repeated violations MUST be handled under `[AG-WF-025]`, and practical durable enforcement MUST be reassessed under `[AG-VAL-028]` and `[AG-VAL-029]`.
## AG-DOC
* **[AG-DOC-001]** A pull request that changes architecture, security, setup, DNS, release behavior, Admin UI authentication, services, or other user-facing behavior MUST verify that all relevant documentation matches the resulting implementation. Relevant documentation MUST include every applicable repository governance, architecture, release, security, threat-model, setup, and user-facing document. A pull request MUST NOT be complete while relevant documentation is objectively incorrect or contradictory. Stale documentation MUST be a blocker and MUST NOT be deferred. Manual consistency review MUST remain required where automated enforcement does not cover the relevant claim.
* **[AG-DOC-002]** Current executable checks and verified code behavior MUST be treated as ground truth. Documentation MUST NOT contradict behavior verifiably enforced by code or CI and MUST be treated as stale when it does.
* **[AG-DOC-003]** `AGENTS.md` MUST define repository-wide hard rules for agent behavior, workflow, validation, and governance. Rules MUST be sober, direct requirements, prohibitions, permissions, or conditions and MUST NOT contain storytelling, origin history, review history, discovery history, or other non-normative narrative content.
* **[AG-DOC-004]** Area-specific `AGENTS.md` files, including `.github/AGENTS.md`, MUST take precedence over general repository rules within their explicitly stated scope.
* **[AG-DOC-005]** `SECURITY.md` MUST take precedence for security-specific behavior and constraints within its stated scope.
* **[AG-DOC-006]** Architecture, release, threat-model, and other explicitly authoritative technical documentation MUST govern its stated system-design or procedure scope unless a higher-precedence applicable source conflicts.
* **[AG-DOC-007]** `README.md` and other user-facing documentation MUST have the lowest precedence among the documentation sources defined by `[AG-DOC-004]` through `[AG-DOC-007]`.
* **[AG-DOC-008]** Conflicting applicable requirements or interpretations MUST NOT be resolved by silently choosing one. Affected work MUST stop until the conflict is resolved.
* **[AG-DOC-009]** A conflict that cannot be resolved from verified source precedence and behavior MUST be escalated to the maintainer. The escalation MUST identify the conflicting sources and verified behavior. Recording the conflict without obtaining the required decision MUST NOT resolve it.
* **[AG-DOC-010]** A confirmed conflict MUST be resolved by correcting the stale source or by changing implementation when the documented behavior is established as intended. Technically determinable decisions MUST follow `[AG-WF-023]`; ambiguous or operationally significant decisions involving hardware, cost, network topology, services, or availability MUST require maintainer resolution.
* **[AG-DOC-011]** Every exception to a hard rule MUST define `Scope`, `Reason`, `Tracking`, `Validation`, and `Non-Expansion`. An exception MUST be narrowly scoped and MUST NOT weaken requirements outside that explicit scope.
## AG-GH
* **[AG-GH-001]** All GitHub-visible content, including issues, pull request bodies, comments, automated review output, commit messages, code, code comments, and documentation, MUST be written in English regardless of producer. This rule MUST take precedence over `[AG-CC-002]`, `[AG-CC-003]`, and `[AG-CC-004]` for GitHub-bound content.
* **[AG-GH-002]** Issue bodies MUST include correct links to known related pull requests, issues, or parent tracking items.
* **[AG-GH-003]** Pull requests MUST reference their tracking issue in the pull request body whenever one exists.
* **[AG-GH-004]** Closing keywords such as `Fixes #123` or `Closes #123` MUST be used only when merging the pull request is intended to close that issue.
* **[AG-GH-005]** Non-closing references such as `Refs #123` MUST be used for parent trackers, design discussions, drafts, partial work, or other relationships that MUST remain open.
* **[AG-GH-006]** Known issue or pull request relationships MUST NOT exist only in chat history and MUST be persisted in GitHub.
* **[AG-GH-007]** SUPERSEDED BY `[AG-GH-001]`. This ID MUST NOT be reused.
* **[AG-GH-008]** Every pull request MUST have at least one label, Project-board assignment, and a Milestone when applicable. A pull request closing exactly one issue through `Closes #N` or `Fixes #N` MUST mirror that issue's labels and Milestone and MUST NOT derive metadata from a non-closing `Refs #N` target. A pull request without a tracking issue MUST still receive its own required metadata. Required metadata MUST be applied when the pull request is opened and MUST NOT be deferred until CI detects the omission. `scripts/tracked/check-pr-tracking-metadata.sh` and its workflow integration MUST remain the authoritative mechanical enforcement for the portions they support and MUST run inside the pinned `build-tools` environment under `[AG-VAL-016]`. Dependabot pull requests MUST NOT be exempt. Project-board automation requiring privileged Projects v2 access MUST use `PROJECT_AUTOMATION_PAT`. If that token is absent, only the Project-board sub-check MAY skip with a visible warning; label and Milestone enforcement MUST remain active. A configured token returning authentication, authorization, or GraphQL errors MUST fail the applicable check. Fork pull requests MUST skip only checks that genuinely require unavailable repository secrets. They MUST remain subject to all webhook-payload-based metadata enforcement, and required Project-board placement MUST be performed manually when automation cannot run. `pull_request_target` MUST NOT be introduced merely to expose repository secrets to fork-controlled code. Metadata-changing pull request events MUST rerun the applicable enforcement.
* **[AG-GH-009]** Issues SHOULD carry labels, an issue Type, an applicable Milestone, Project-board assignment, and GitHub's native parent/sub-issue relationship when genuinely subordinate. An issue lacking applicable metadata SHOULD NOT be treated as fully triaged.
* **[AG-GH-010]** Every pull request body MUST include what changed, user-visible impact, validation performed, known risk, and follow-up work. A pull request missing this information MUST NOT be considered integration-ready.
* **[AG-GH-011]** Scaffold or partial-fix pull requests MUST identify themselves as scaffold or partial, MUST reference remaining scope with `Refs #N`, and MUST NOT use closing keywords for unresolved remainder.
* **[AG-GH-012]** After a pull request lands, completion MUST be checked against the merge commit or current `master` state and the original issue. Pull-request-head state alone MUST NOT establish completion.
* **[AG-GH-013]** Every agent working on an issue or pull request MUST maintain a durable work record throughout the task. A `/loop` or equivalent mechanism MUST run every 15 minutes and MUST reference the applicable issue or pull request. Real progress MUST be committed and pushed at each checkpoint. GitHub progress comments MUST NOT substitute for checkpoint commits. A checkpoint with no diff MUST be recorded in the next commit message. A completed task with no diff MUST create an empty marker commit using `git commit --allow-empty`.
* **[AG-GH-014]** Every issue MUST be independently actionable from its body alone. It MUST identify affected files, functions, or paths, define concrete verifiable acceptance criteria, and provide evidence through reproduction, logs, code references, or equivalent proof. An incomplete issue MUST be expanded before assignment.
* **[AG-GH-015]** A successor or follow-up issue MUST state whether it covers all original acceptance criteria or only a subset. A subset successor MUST identify remaining criteria, and the original issue MUST remain open until all remaining criteria are satisfied.
* **[AG-GH-016]** Before an issue is closed as resolved, superseded, or duplicate, its complete acceptance criteria MUST be compared with the covering pull request, issue, and current repository state. Topic, title, or scope similarity MUST NOT establish equivalence.
* **[AG-GH-017]** Before branch-based work begins, scope MUST be defined and checked against all existing branches, pull requests, and issues using `git fetch --all --prune && git branch -r`, `gh pr list --state all --limit 200 --search <keywords>`, and `gh issue list --state all --limit 200 --search <keywords>`. Open-only searches, default limits, or stale remote refs MUST NOT satisfy this check. Each distinct scope MUST use a separate branch. Unrelated work MUST NOT be added to an existing branch. Every new branch MUST be linked to its scope through a pull request or issue comment identifying branch and purpose.  A branch that will not become a pull request MUST be recorded as abandoned, superseded, exploratory only, or duplicate work with its reason. Deletion MUST be explicitly flagged and MUST follow `[AG-WF-005]`.
* **[AG-GH-018]** Pull request titles MUST follow `type(scope)!: subject` and MUST be validated by `scripts/tracked/check-pr-title-convention.sh`. The checker MUST be the authoritative mechanical source for the current allowed type and scope sets.  `feat` MUST produce a minor release. `fix`, `security`, and `perf` MUST produce a patch release. `docs`, `refactor`, `test`, `build`, `ci`, `chore`, and `style` MUST NOT independently require a version bump. `revert` MUST inherit the reverted change's release impact. Breaking changes MUST use `!` or a `BREAKING CHANGE:` footer. Below `1.0.0`, breaking changes MUST produce a minor release. Promotion to `1.0.0` MUST require explicit maintainer approval.  `PR_TITLE_LINT_MODE` MUST control enforcement and MUST default to `warn`. In `warn` mode, a non-draft non-compliant title MAY leave CI green with a warning but MUST be corrected before merge. In `block` mode, it MUST fail. Draft pull requests MAY receive non-blocking warnings. Pull request title compliance MUST NOT be treated as sufficient release-automation integration. Existing merged history MUST NOT be rewritten solely for retroactive compliance.
* **[AG-GH-019]** Before acting on, summarizing, reporting, closing, or determining scope or status of any issue or pull request, the complete title, body, and comment history MUST be read in chronological order. The body alone, latest comment, or dispatcher summary MUST NOT be sufficient. Large histories MAY be processed in complete consecutive chunks. Later comments MUST govern points they change, supersede, narrow, expand, or contradict. Stale body information MUST be corrected.
* **[AG-GH-020]** When new information makes a GitHub comment outdated, duplicate, resolved, or off-topic, the comment MUST be minimized using the matching GitHub classifier. A correction MUST NOT substitute for minimization. Minimization MUST NOT substitute for preservation under `[AG-WF-026]`. After minimization, the surviving body and history MUST be verified as one current consistent state.
* **[AG-GH-021]** Issue or pull request bodies that document or modify a closing-keyword scanner MUST NOT contain an unmasked closing keyword immediately followed by a real `#N` unless an actual closing instruction is intended. Examples or descriptions MUST break the scanner pattern.
* **[AG-GH-022]** When issue or pull request history is no longer clear from title and body alone, the body MUST maintain a chronological atomized Live checklist. Each substantive comment MUST have its own entry with the originating `#issuecomment-<id>` permalink. Checked state MUST be independently verified, and every `[x]` entry MUST identify supporting evidence. Every substantive new comment that changes current understanding MUST update the checklist in the same pass. A superseded entry MUST remain visible and MUST reference the governing later comment.  Routine `[AG-GH-013]` checkpoints MUST NOT receive individual checklist entries and MUST instead be consolidated using `.github/issue-checklist-response-template.md`, which MUST be treated as the authoritative format for that consolidation. Comments MUST NOT be deleted or have original content removed merely because they are stale, superseded, or incorrect. A superseded comment MUST retain its original content and MUST receive a visible `SUPERSEDED` or `NO LONGER CURRENT` marker plus an appended update identifying the superseding information.
* **[AG-GH-023]** `gh stack` MUST NOT be used to create, join, link, reorganize, rebase, synchronize, push, or merge pull requests unless the maintainer explicitly requests it for the specific pull request or stack.  Every `gh stack init` and `gh stack link` targeting the development trunk MUST explicitly use `--base current_dev`. A legitimate `master` target MUST use `--base master`. A pull request entering a stack MUST first be opened against its applicable trunk and MUST NOT initially use another feature branch as its base.  Conflict resolution for a stack-managed branch MUST remain inside the `gh stack` workflow. Manual `git rebase` or `git merge` MUST NOT replace stack-management operations. A failed `gh stack rebase` MUST be aborted with `gh stack rebase --abort` and the affected pull request MUST be re-imported through `gh stack checkout <pr-number>` before stack reconstruction continues. Obsolete already-merged local lower-stack branches MAY be removed when necessary for that re-import. Force-variant operations performed by `gh stack push` or `gh stack sync` MUST satisfy `[AG-WF-024]`. `gh stack` MUST NOT bypass branch protection, checks, reviews, or merge requirements. Administrative bypass remains governed by `[AG-WF-039]`.  Absence of an explicit maintainer request MUST mean `GH STACK = DISACK`.
## AG-WF
* **[AG-WF-001]** Before starting or continuing branch work, or making readiness, mergeability, or integration-order claims, current remote branch and base MUST be fetched, the working branch MUST be rebased onto the current remote base, and resulting head MUST be verified. This MUST be repeated after restart or continuation and whenever freshness is uncertain. A failed rebase MUST block readiness, mergeability, or integration-order conclusions.
* **[AG-WF-002]** Every pull request, issue, and dispatched-agent task MUST use its own worktree under `<repo-root>\.claude\worktrees\<issue-nr>_<shorttext>` and MUST NOT use another naming or location scheme. The coordinator MUST create and bind the worktree before dispatch, and the executing agent MUST verify the assigned worktree before commands are run.  Before substantive work, the worktree branch MUST be verified against its current base.  The first action in a newly created worktree MUST be `git commit --allow-empty`, recording task, issue number, and the executing agent's reachable internal task or session ID. For dispatched work, both agent and coordinator MUST record that internal ID in a commit on the agent branch. Indirect IDs MUST NOT substitute.  The worktree MUST be removed after completion using `git worktree remove`.  Worktree cleanliness, ownership, reset, and force-push safety MUST follow `[AG-WF-024]`. Governance acceptance MUST follow `[AG-WF-035]`.
* **[AG-WF-003]** Bounded independent work MUST use fanout when delegation lowers main-thread cost without lowering quality. The cheapest suitable model and reasoning level MUST be preferred. Spark MUST be evaluated first while available. If unavailable, rate-limited, or unsuitable, `gpt-5.4-mini` MUST be evaluated before delegable work remains in the main thread. Keeping delegable work in the main thread MUST have a concrete reason.
* **[AG-WF-004]** Direct pushes to `master` MUST be DISACK by default and MUST NOT occur without the exact maintainer phrase `ACK for merge to master`. All changes MUST be integrated into `master` through a pull request. Authorization MUST satisfy `[AG-WF-029]`.
* **[AG-WF-005]** Repository work MUST NOT be merged, closed, or deleted without explicit maintainer authorization satisfying `[AG-WF-029]`. Merge additionally MUST require the exact phrase `ACK for merge`.
* **[AG-WF-006]** A pull request MUST remain Draft until all required validation passes, all known review findings are resolved, and the complete change passes `[AG-LAW-001]`. Any unresolved validation failure, finding, or applicable rule violation MUST block Ready status.
* **[AG-WF-007]** A review thread MUST NOT be resolved until the finding satisfies `[AG-WF-011]` and is fully corrected or has a maintainer-approved explanation. Every fixed finding MUST then satisfy `[AG-WF-008]`.
* **[AG-WF-008]** Every fixed review finding MUST receive a factual reply describing the correction and MUST then be resolved through GitHub's `resolveReviewThread`. An outdated thread MUST still be explicitly resolved. Resolution MUST NOT delete thread content.
* **[AG-WF-009]** If GitHub does not permit resolution of a stale or outdated thread, a factual pull request comment MUST identify the finding, explain why it is fixed, and state that GitHub prevented thread resolution.
* **[AG-WF-010]** Before changing, reviewing, or resolving an issue or pull request, `[AG-GH-019]` MUST be satisfied and the surrounding file and project-wide impact MUST be evaluated. Every identified problem MUST be processed under `[AG-WF-011]`.
* **[AG-WF-011]** Every defect, review finding, or comparable failure MUST be treated as a failure class rather than an isolated instance. The root cause MUST be identified before the finding is considered fixed. The complete affected scope MUST be searched for other occurrences and consequences, including matching install, update, secondary, release, CI, documentation, and test paths where applicable.  A correction MUST eliminate the root cause across that affected scope and MUST NOT be limited to the reported line, file, symptom, example, or occurrence. If a behavior change or bug fix would also be required elsewhere to keep another implementation correct, that other implementation MUST be considered part of the same failure class.  Evidence required to claim a root cause MUST satisfy `[AG-INT-001]`.
* **[AG-WF-012]** GitHub bodies or comments written from local files MUST use temporary files under `$TMPDIR` and MUST NOT use hardcoded `/tmp` paths. The write MUST upload file content and MUST NOT submit a literal file path. All GitHub writes MUST satisfy `[AG-WF-031]`.
* **[AG-WF-013]** Every change MUST be evaluated in its complete affected context, including dependencies, impact, resulting behavior, and foreseeable consequences. The entire affected file MUST be the minimum correctness unit. Directly connected inconsistencies or applicable violations MUST be corrected before completion, and the resulting change MUST pass `[AG-LAW-001]`.
* **[AG-WF-014]** SUPERSEDED BY `[AG-WF-004]`. This ID MUST NOT be reused.
* **[AG-WF-015]** The maintainer MUST NOT be treated as the default source for technically determinable implementation decisions. Agents MUST follow `[AG-WF-023]`. Conversational wording MUST NOT substitute for authorization governed by `[AG-WF-029]`.
* **[AG-WF-016]** `AGENTS.md` content, including rules, values, requirements, exceptions, and governed information, MUST NOT be silently removed, narrowed, simplified, or changed in representation or meaning without explicit maintainer consent. Modifications MUST preserve complete semantic content unless a meaning or scope change is explicitly authorized and MUST pass `[AG-LAW-001]`. Rule IDs MUST identify exactly one rule and MUST NOT be silently reused. References MUST follow `[AG-LAW-004]`.
* **[AG-WF-017]** Every agent-authored commit message, GitHub comment, issue or pull request body, review reply, and agent-initiated closing or labeling action MUST begin with `<PREFIX>-<unix-timestamp>`. The timestamp MUST be freshly obtained with `date +%s` and MUST NOT be reused.  Claude MUST use `CLD-`, Codex `CDX-`, GitHub Copilot `CPT-`, Gemini `GEM-`, and other AI systems their own stable self-identifying prefix. `AI-` MAY be used only when actual identity cannot be determined. The marker MUST NOT appear in issue or pull request titles.
* **[AG-WF-018]** New issue creation MUST be DISACK by default. Before creation, all issues including closed issues MUST be searched for identical or materially overlapping scope. Existing coverage MUST be reused. Uncertainty about coverage, ownership, scope, or need MUST stop creation and MUST be escalated through the coordinator to the maintainer when unresolved. Creation authorization MUST satisfy `[AG-WF-029]`.
* **[AG-WF-019]** A Bash working directory MUST NOT be assumed to persist across tool invocations. Directory-dependent commands MUST run in the same invocation using `cd "<path>" && pwd && <command>`. The printed `pwd` MUST be the authoritative location check. State-mutating commands MUST NOT proceed after a failed or mismatched directory verification.
* **[AG-WF-020]** RETIRED -> `[AG-WF-001]`. This ID MUST NOT be reused.
* **[AG-WF-021]** Subagent results MUST be treated as stale until verified against the current remote base and pull request head. Before such results are used for readiness, conflict resolution, review comments, or merge guidance, reported commit and base MUST be compared with current GitHub state and applicable checks MUST be rerun against the current head.
* **[AG-WF-022]** The main thread MUST NOT block on subagents while useful non-overlapping work remains. Subagents SHOULD be polled sparingly and MUST be closed after their result is reviewed or superseded.
* **[AG-WF-023]** Agents and tools MUST make technically determinable decisions independently. Guidance MUST be requested only when a choice has real operational impact involving hardware, network topology, cost, services, availability, or time-to-value. Technically determinable consequences MUST NOT be delegated back to the maintainer as preference questions. Source conflicts MUST follow `[AG-DOC-008]` through `[AG-DOC-010]`.
* **[AG-WF-024]** Every agent spawning subagents MUST assign each one an explicitly assigned and verified clean worktree.  Before substantive work, the subagent MUST fetch and verify current branch and `HEAD` against expected `origin/<base-branch>`. A mismatched worktree SHOULD be replaced with a fresh one. If reset in place is required for a verified scratch worktree, `git reset --hard origin/<base-branch>`, then `git clean -fd`, then an empty `git status --porcelain` MUST be used as the complete clean-state check. `git clean -fdx` MUST NOT be used. This exception remains subject to `[AG-WF-042]`.  A subagent MUST NOT overwrite, rebase onto, or push over another agent's branch or in-flight work. Before a force-variant push, current branch, `HEAD`, exact remote ref, overwrite reason, intended content, and exclusive ownership MUST be verified. A rejected non-fast-forward push MUST trigger re-verification and MUST NOT be reflexively bypassed with force. Before any action that could silently destroy data or overwrite another branch's history, the subagent MUST consult its dispatching agent and MUST NOT decide the action autonomously. Any uncertainty about worktree, branch, base, ownership, push target, destructive action, or applicability MUST stop work and MUST be escalated until conclusively resolved.
* **[AG-WF-025]** A second occurrence of the same underlying failure pattern MUST trigger assessment for a new or strengthened `AGENTS.md` rule and MUST NOT be handled only by fixing the repeated instance. Recurrence MUST be determined by underlying cause, not symptom.   Before proposing or assigning a new rule ID, the complete existing rulebook MUST be searched for a rule that already governs, overlaps with, or can canonically own the failure class. If an existing rule covers the failure class or can be strengthened without creating unrelated scope or ambiguity, that rule MUST be strengthened and a new rule ID MUST NOT be created. If multiple rules contain overlapping requirements for the same failure class, the overlap MUST be consolidated into one canonical owner while every unique requirement remains preserved. A new rule ID MAY be proposed only for a genuinely distinct invariant that cannot be incorporated into an existing rule without unrelated scope or ambiguity. The proposal MUST identify the existing rules checked, MUST explain why strengthening or consolidation is insufficient when a new ID is proposed, and MUST be presented to the maintainer with canonical English text and a German translation before adoption.
* **[AG-WF-026]** This rule MUST be the canonical durable-persistence contract. `Substantive knowledge` MUST include material findings, verified facts, evidence, reproductions, decisions, rejected alternatives and rationale, assumptions, constraints, limitations, unresolved questions, acceptance criteria, dependencies, risks, rollback information, implementation state, and required follow-up. A `durable record` MUST be a surviving repository or GitHub record that remains independently understandable without access to the originating chat, session, temporary environment, or worktree. Before an issue, pull request, branch, review thread, investigation, agent task, worktree, or comparable source is closed, merged, resolved, superseded, abandoned, deleted, cleaned up, handed off, or otherwise ended, all substantive knowledge not already present in the surviving durable record MUST be consolidated there. A link to a transient source MUST NOT count as consolidation. Chats, agent reports, local notes, temporary files, CI output, unpushed commits, branches, worktrees, or review discussions MUST NOT remain the only copy of substantive knowledge. Consolidation MUST preserve provenance, accepted and rejected decisions, current implementation state, and unresolved remainder. Summaries MAY be used only when all material conclusions, constraints, rationale, risks, rejected alternatives, and follow-up remain preserved. Significant state MUST be persisted during work and MUST NOT be deferred until final cleanup. Before an agent ends, hands off, removes its worktree, or allows its environment to terminate, substantive local work MUST be committed where appropriate, pushed to a named remote branch, and linked or summarized in a durable tracking object. Durable persistence MUST be verified before the lifecycle action through successful readback, expected commit and remote-branch verification, or equivalent proof. If transfer cannot be completed and verified, the source MUST remain active and completion or handoff MUST NOT be declared.
* **[AG-WF-027]** Every real defect, gap, missed edge case, inconsistency, or other problem found during work MUST be fixed in the same pass regardless of original scope or discovery path. A known problem MUST NOT be ignored, deferred, scoped out, or only recorded as a limitation, review finding, issue, or future task.  If resolution requires a maintainer decision or separate authorization, materially changes intended behavior, creates significant new risk, or causes another problem that cannot safely be resolved, affected work MUST stop and the maintainer MUST be contacted with the problem, impact, required decision, and available choices. The problem MAY remain unresolved only until that decision. 
* **[AG-WF-028]** No branch, commit, comment, file, or other artifact MAY be classified as dead, stale, unsalvageable, trivial, or superseded based only on aggregate diff size or file count. Its unique contribution MUST be inspected first. Deletion MUST follow `[AG-WF-005]` and `[AG-GH-017]`.
* **[AG-WF-029]** This rule MUST be the canonical maintainer-authorization contract. A request for an opinion, preference, recommendation, or analysis MUST NOT authorize execution. When a rule requires maintainer authorization, authorization MUST come directly from the maintainer, MUST apply only to the specific action for which it was requested, and MUST NOT be inferred, substituted, reused, generalized, delegated, or transferred. Unless a more specific rule requires an exact phrase, authorization MUST use the literal token `ACK`. `DISACK` MUST prohibit the action. Tone, enthusiasm, implication, silence, elapsed time, contextual consent, or absence of objection MUST NOT substitute. When a specific rule defines an exact authorization phrase, that phrase MUST override generic `ACK` and MUST be matched exactly. If authorization is unclear, the intended action MUST be stated and explicit authorization MUST be obtained before execution.  A required maintainer decision MUST be recorded on the relevant GitHub issue or pull request as a structured statement identifying the exact decision and concrete options.
* **[AG-WF-030]** Documentation MUST NOT be treated as authoritative when it conflicts with verified code, architecture, or governance. Such conflicts MUST be handled under `[AG-DOC-002]` through `[AG-DOC-010]`.
* **[AG-WF-031]** This rule MUST be the canonical GitHub-write verification contract. GitHub writes SHOULD use GraphQL through `gh api graphql` where practical. Every GitHub write, regardless of method, MUST be read back immediately and MUST be verified against intended content before work continues.
* **[AG-WF-032]** Markdown sent through GraphQL string variables MUST pass raw file content using CLI file-upload mode and MUST NOT be pre-encoded as JSON. Leading JSON quotes, escaped newlines, or literal file paths MUST be treated as malformed writes. All writes MUST satisfy `[AG-WF-031]`.
* **[AG-WF-033]** Automated reviewer findings MUST be treated with the same obligations as human findings under `[AG-WF-007]`, `[AG-WF-008]`, `[AG-WF-009]`, and `[AG-WF-011]`. Severity MUST NOT reduce those obligations. Automated rule citations MUST identify both Rule ID and Rule Name and MUST be independently checked against current rule text. Automated review and verification MUST explicitly apply `[AG-CODE-011]`, `[AG-CODE-012]`, and `[AG-CODE-013]`, including applicable duplicate searches. Before resolution, the strongest verification capability supported by the applicable orchestration tooling MUST be used. Claude-based agents MUST use `advisor`; GPT-based agents MUST use the largest current selectable model at its highest supported reasoning tier; other providers MUST use their strongest selectable capability. Tool support MUST be verified. If the current thread cannot perform that verification, it MUST dispatch an agent that can. The resolution response MUST identify applicable Rule IDs and Rule Names, the established root cause, completion of the `[AG-CODE-011]` through `[AG-CODE-013]` checks, and the stronger verification actually performed. Private or undocumented verification MUST NOT satisfy this rule.
* **[AG-WF-034]** A cohesive unit of work MUST NOT be split across multiple pull requests using only copied snapshots or prose merge-order instructions. Related pull request dependencies MUST be mechanically enforced through actual branch or rebase relationships, Draft state, disabled auto-merge, or equivalent controls. If mechanical enforcement is genuinely unavailable, the dependency MUST also appear prominently in title and body. Downstream work MUST NOT merge before required upstream dependencies.
* **[AG-WF-035]** This rule MUST be the canonical agent-acceptance contract. Before substantive work, every participant MUST read `AGENTS.md`, `CLAUDE.md`, and `.github/AGENTS.md` in full. Summaries, inherited context, prior sessions, prior knowledge, or another agent's interpretation MUST NOT substitute. Files too large for one pass MUST be read sequentially without omission. Every participant MUST explicitly state that all three files were read and MUST accept the unified-lawbook requirement of `[AG-LAW-001]`.  Every spawned agent MUST additionally identify, cite, or quote at least one applicable `[AG-...]` rule ID. The parent MUST verify that comprehension at the earliest reachable point and before substantive work where synchronous verification is possible. Compliance MUST be established independently for every participant and every spawn level and MUST NOT be inherited.
